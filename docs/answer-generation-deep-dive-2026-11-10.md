# 回答生成の根本的な改善案と、仕様どおりに動いていない機能（2026-11-10）

[現状と方針](answer-generation-plan-2026-11-10.md)の続きである。文献調査、Recipe の具体化、Lean パネルのホバー、仕様と実装の差の4点を調べた結果をまとめる。

調査はコードと文書を読んで行った。Lean の実行、有料モデルの呼び出し、本番画面の確認はしていない。コードの位置は、本番が指す `pals-agent` e1b26c5、`pals-api` 430aa19、`pals-webfront` c4593de のものである。「推定」と書いた数値は未測定である。

## 1. 根本的な改善案

効果が大きいと見る順に並べる。

### 1.1 具体化を Lean の単一化に任せる

一般形の Recipe を1つ検証しておき、具体的な依頼は「命題を形式化して、Recipe を当てはめる」だけで答える。新規生成（138〜148秒、平均0.070ドル）が、20〜35秒、約0.01ドルになる見込みである（推定）。

原型はすでにある。`pals_agent/recipe_instantiation.py:565-613` が、Recipe の後ろに `theorem pals_recipe_instance : <命題> := by first | exact G _ …` を足して Lean に具体化させる。ただし次の理由で本番では動いていない。

- `PALS_RECIPE_INSTANTIATION` が既定で無効である（`pals_agent/factory.py:59`）。infra の許可リストにもない。
- コンパイルを受ける API 側の実装が、`origin/claude/recipe-specialization-reuse` にしかない。
- `pals-agent` の main には、このファイル自体がない。

現状の限界は次のとおりである。

- 閉じ方が `exact` だけである。`x*x` と `x^2`、`x-1`、奇数冪（`2*?n+1 = 3`）、`Continuous` から `ContinuousAt` のように、定義として一致しない形は通らない。
- 仮定を閉じる手段が `(by norm_num)` と `(by decide)` しかない（`recipe_instantiation.py:546-561`）。「連続関数の和は連続」を `x²+x` に当てることができない。
- Recipe 同士を合成できない（`x²+3x+1`）。
- 候補の Recipe を、Lean の前にモデルが1件に絞っている。
- 毎回 Recipe 全文をコンパイルし直す（暖機後で約10秒、冷えた状態で約48秒）。
- 説明が一般の `n` のままである。仕様 PIR-011 が、値を置き換えた回答を禁じている。
- 再利用の審査プロンプトが、特殊化と代入を一致と扱わないよう指示している（`pals_agent/proof_reuse.py:1096-1105`）。ここで `dsp_scope_mismatch` になり、新規生成へ進む（#287、#298）。

設計案は次の5点である。

1. **Recipe をライブラリにする。** `PalsRecipes/<id>.lean` として事前にコンパイルし、依頼ごとのファイルは `import` と数行にする。
2. **閉じ方を段階にする。** `exact G _…`、`simpa using G …`、`convert G … using 2 <;> norm_num` の順に試す。命題の宣言は固定で kernel が検査するので、tactic を広げても誤った命題は通らない。
3. **使った定数を検査する。** 証明項が Recipe の定理を含み、許可していない Mathlib の補題（`continuous_pow` など）を含まないことを確かめる。これがないと、`simpa` が Recipe を使わずに閉じ、説明と学習順序が実際の証明と食い違う。
4. **候補選びと合成を Lean に任せる。** 上位の候補を `first | exact R1 _ | exact R2 _ …` で1回のコンパイルにかける。次の段階として、Recipe に限定した `apply_rules` を用意し、仮定の解消と合成を行う。
5. **説明も具体化する。** カードに説明用の量を Lean の項で持たせ（例: `C := n*(|a|+1)^(n-1)+1`）、コンパイル時に単一化の結果を出力させてテンプレートに埋める。モデルを呼ぶのは、帰納法の段を具体的な `n` 向けに展開したいときなどに限り、結果は Recipe と束縛の組で保存する。

学習順序は、カードに水準と許可する補題の一覧を持たせ、依頼の水準以下のカードだけを具体化に使うことで守る。3 の検査が近道の混入を止める。

モデルに残る仕事は、命題の形式化1回と、その独立した審査1回である。Lean は誤って形式化した命題も正しく証明するので、審査は外せない。

最初の実験は、モデル費用0で行える。既存の一般形 kit 9件をライブラリにし、手書きの命題約40本（正例、定義として一致しない例、合成、負例）を4通りの閉じ方で試す。

判断が要る点は3つある。PIR-006（`simp` 系の禁止）を改めるか。PIR-011（説明の置き換えの禁止）を改めるか。カタログ追加は 2026-11-04 から停止中であり、既存カードの一般化を再開するか。

### 1.2 Mathlib を読み込んだままの Lean を使う

修復途中のコンパイルを、常駐の Lean プロセスに回す。毎回の `import Mathlib`（3.5〜20秒）が要らなくなり、途中のコンパイルは1秒未満になる見込みである（推定。PALS 自身の測定では、elaboration は1題40〜110ミリ秒である）。

- Kimina Lean Server（arXiv 2504.21230）は、import ヘッダーごとに REPL を使い回し、8コアで1証明あたり平均0.272秒と報告している。測定機は 72 vCPU、540 GB であり、PALS の 2 vCPU、16 GiB でのメモリは未測定である。
- `leanprover-community/repl` は、環境の再利用と、`sorry` ごとのゴールの返却を備える。LeanInteract は Lean 4.8 から 4.36-rc1 に対応し、PALS の 4.32.0-rc1 を含む。
- 最終の合否は、今の独立したプロセスでの検査だけで決める。古い REPL の tactic モードが誤った証明を12件通した報告（LeanTree、arXiv 2507.14722）があるためである。REPL は command モードだけを使い、依頼ごとにプロセスを作り直す。

これができると、1.4 と 1.5 が安く実現できる。

### 1.3 `import Mathlib` が遅い理由を調べる

他所の報告は暖機後で1〜2秒、PALS は7〜20秒である。Lean は `.olean` をメモリに写して共有する作りで、遅さはページキャッシュ、コンテナのメモリ制限、ディスクのどれかによる可能性が高い（PALS も 4 GiB の制限で21〜129秒を記録している）。原因が分かれば、設計を変えずに毎回のコンパイルが最大5秒ほど縮む。測定に費用はかからない。

### 1.4 `sorry` の穴を自動化 tactic で先に閉じる

Sketch の穴に、モデルを呼ぶ前に `grind`、`aesop`、`omega`、`nlinarith`、`simp_all`、`exact?` を順に試す。閉じた分だけ、67秒、0.04ドルの修復が減る。効果は未測定で、測るには失敗した Sketch の本文を保存する必要がある（現在は保存していない）。

### 1.5 最初の修復の代わりに、方針の違う2案を並行して試す

方針を変えた Sketch を2本作り、先に検証を通ったほうを採る。初回で失敗する3〜5割の依頼で、修復1回分（約67秒）が縮む見込みである。費用は1題あたり Sketch と Prove が1回ずつ増える。同じプロンプトで2本作っても効果がないという報告があるので、方針を変える。

### 1.6 修復に渡す診断を増やす

未解決のゴールと期待された型を、無害化して修復モデルに渡す。ゴールの文は、モデル自身のコードと、すでにプロンプトにある依頼文から導かれるので、新たに入り込む経路は狭い。文字列リテラルとコメントを除き、長さと文字種を制限し、区切ったデータ欄として渡す。

効果は未測定である。文献では、学習済みの証明モデルで1〜2ポイントの向上にとどまる。同じ汎用モデルで5%から51%に上がった報告（Ax-Prover、arXiv 2510.12787）は、約100回のツール呼び出しと1題4ドルの費用を伴うので、そのままは当てはまらない。

### 1.7 修復の上限を下げ、失敗しても Draft の証明を返す

修復は1回目で効果の84〜96%が出るという報告がある。PALS では36題のうち3題が、時間の22%、費用の29%を使った。上限を2にして、同じ診断が続いたら止め、Lean が通らなかったときは Draft の自然言語の証明を「未検証」と明示して返す。費用は2〜3割下がり、成功率は0〜3ポイント下がる見込みである（既存の記録からの推定）。

### 1.8 命題が依頼と合っているかの検査を強める

逆翻訳だけに頼らず、項目別の採点と、`plausible` や `decide` による反例探し、仮定が空でないことの確認を加える。速さではなく、「検証済み」の意味を守るためのものである。1.1 でモデルの仕事が形式化に寄るほど、ここが重要になる。

### 見込みについての注意

論文の大きな数字は、専用に学習したモデル、数百回の呼び出し、大きな計算機が前提である。PALS の最終成功率はすでに約9割であり、現実的に得られるのは、修復回数と遅い側の時間の削減である。成功率が大きく上がるとは見ていない。

すでに試して効果がなかったものは繰り返さない。Mathlib の命題ヒント、Recipe の few-shot、呼び出し回数の削減、検証済み補題のスタブ化である（改善ジャーナルに記録がある）。

## 2. Lean パネルのホバー説明

### 原因

現在の回答経路で使う `ReferencedLeanSourcePanel` が、説明の節を Lean パネルに渡していない（`pals-webfront/components/ReferencedLeanSourcePanel.tsx:138-146`）。節を渡しているのは `ProofExplanationThread` だけで（`components/ProofExplanation.tsx:218-226`）、これは証明ジョブを直接選ぶ古い履歴チャットでしか開かない。

worker は節ごとに行範囲と抜粋を出力し（`pals_agent/explanations.py:56-75`）、API は保存して `GET /v1/proof-jobs/{id}/explanation` で返している。Web 側でつなげば動く。

### ほかの欠け

- API は、回答を概要・各節・結論を空行でつないだ平文にして返す（`pals-api/app/infrastructure/repositories/proof_request_lean.py:273-287`）。本文のどの段落がどの節かを、Web は知ることができない。
- カタログ（Recipe）の回答は、行との対応を持たない。
- ゲストでは、API が返す説明を Web が真偽値に落として捨てている（`pals-webfront/lib/api/guestChat.ts:95`）。全行に同じ文が出る。
- 共有ページは、コードを `<pre>` で出すだけである。
- 本文の文にホバーして Lean の行を強調する方向は、仕様にも実装にもない。
- 行との対応を定めた仕様が `specs/` にない。あるのは `docs/lean-source-display-2026-10-02.md` と #232 である。
- 対応する行のすべてに `tabIndex=0` が付き、長い証明ではタブ移動が数十回以上になる。
- `simp` や `nlinarith` の行は対応が1つしかなく、行ごとの説明にならない。

### 作る順序

| 段階 | リポジトリ | 内容 |
|---|---|---|
| W1 | pals-webfront | 現行経路で説明を取得し、節をパネルに渡す |
| W2 | pals-webfront | ゲストでも、API が返す説明を使う |
| A1 | pals-api | 回答に、節ごとの本文と行範囲を持つ `segments` を足す |
| W3 | pals-webfront | 本文の段落から Lean の行を強調する。矢印キーで行を移動できるようにする |
| G1 | pals-agent | 節が行を飛ばさないようにし、行の分割規則を API・Web とそろえる |
| C1 | カタログ | Recipe の保存済み回答に、節と行範囲を持たせる |
| L1 | 全体 | 自動化 tactic の行に定型の説明を出す。詳しい説明は、利用者が求めたときだけ生成して保存する |
| S1 | 共有 | 共有ページにも節を含める |

回答と同時に全行の説明を生成する案は採らない。パネルを開かない利用者にも費用と時間がかかり、対応の粗い行に根拠のない説明を書かせることになる。

判断が要る点は3つある。本文から Lean への強調を正式な要件にするか。C1 を、カタログ追加の停止中に行うか。L1 の求めに応じた生成を、無料枠とゲストに開放するか。

7. 3750秒かかった1題（#313）の原因。コードからは特定できなかった。
