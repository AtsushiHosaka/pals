# 追加送信は同じ要求への訂正と次の質問に分ける

PALSの応答中も通常の送信を受け付け、訂正・補足は同じ要求に反映し、別の質問は保存して順番に答える。2026-10-07のユーザー回答を[仕様](../specs/proof-request-reuse/requirements.md)に反映した記録である。今回の対象は挙動の確定、仕様更新、仕様レビューまで。実装・本番配備は未実施。

基準は親リポジトリ `7c45dbb`、API `aa8b12c`、webfront `d436271`。既存の別ワークツリーを読み取りに使い、アプリ・コンテナは起動していない。参照するagent `7a6c343` は未展開で、実行中の外部処理を停止する挙動は未検証。作業ブランチは `codex/chat-interruption-spec-20261007`。

## ユーザーが確定した挙動

| 判断 | 確定した挙動 |
|---|---|
| 曖昧な追加発言 | 対象要求の回答公開を保留し、訂正か別の質問か確認する。 |
| 別の質問 | 保存し、同じチャットで先行要求の回答後に順番に答える。 |
| すでに公開された旧回答 | 旧条件の回答と明示して残し、訂正版を続けて表示する。 |
| 利用枠 | 同じ要求の回数枠は最終回答1回分。成功時の利用トークンには訂正前の実利用も含める。既存の最終失敗時の解放規則は維持する。 |
| ゲスト | 訂正も受理した1送信として、既存の日次3送信上限に数える。 |
| 残量・上限不足 | 訂正を保存し、旧回答の採用を止めて保留する。再開には有効な利用枠を要し、上限を自動で増やさない。 |
| 訂正と別の質問の混在 | 明確なら訂正を反映し、別の質問は次の要求として保存する。 |

## 二巡のレビューで公開と精算の競合を整理した

| 巡 | 入力・経路 | 結果と検証範囲 |
|---|---|---|
| 1 | 現仕様・実装を読み取り、意図・順序・履歴・利用枠をまとめて質問 | 現APIの改訂は前提回答・再試行に限られる。版・claimと現在のlinked jobの照合は使えるが、追加入力の受付口はない。7つの選択をユーザー回答で確定した。 |
| 2 | 要件→設計→タスクを更新し、2サブエージェントで仕様と実装上の制約を独立レビュー | 受付時の公開保留と訂正確定時の旧処理失効を分離した。解釈のcallは保留を解消する専用経路とし、未精算の既知実利用も累積上限から差し引く。意図確認を数学的前提確認から区別した。 |

受付と公開は同じ要求のロックで順序を確定する。受付が先なら旧回答を保留し、訂正確定後は採用しない。公開が先なら旧条件に対応する履歴として残す。独立質問だと判定した場合は保留を解除し、元の要求を再開できる。すでに動いているLLMやLeanの即時停止を完成条件にはせず、次の処理と結果の採用を制御する。
