# スキーム論の質問を、質問から検証済みの回答まで通す測定（2026-11-14）

## 利用者にとって何が変わるか

スキーム論の質問で、依頼とは別の弱い補題を証明して「検証済み」と返す事例が減る。今回の 10 題では、依頼どおりの命題をレビューまで通した題が 5 題から 8 題に増えた。検証済みの件数そのものは 9 題のままで、変わったのは中身である。検証済みのうちレビューが却下した題は 4 題から 1 題に減った。

ただし 10 題を各 1 回ずつ測っただけで、件数の差は誤差の範囲でもありうる。時間と費用は、題ごとの修復回数に左右されて大きくぶれる。

## 測定の条件

- 題: `pals-agent/testdata/algebraic-geometry-v1/manifest.json` の 10 題。学部上級から修士初年の水準で、アフィンスキーム 3、構造層 2、射の性質 4、層のコホモロジー 1。既存の評価セットに代数幾何の区分は無かったので、新しく作った。`generation-eval-v1` とは文面が重ならず、`held_out` は開いていない。
- 経路: worker と同じ生成の経路（Draft、Sketch、Prove、修復、意味レビュー、解説）を `scripts/eval/run_stages.py tier2` で実行した。モデルは本番と同じ役割割り当て、修復は最大 6 回、言語は ja。
- 検証環境: 既定のプロファイル `mathlib-4.32`（Lean v4.32.0-rc1、Mathlib 8b62164）。作業コピーのピン留めどおりの版である。
- 費用は 5 題ずつ 2 回に分けて、1 回の実行を 1 ドル以下に収めた（修正前 0.37 ドルと 0.21 ドル、修正後 0.13 ドルと 0.61 ドル。ランナーの計上値）。
- 負荷: 1 分平均は 4〜8、Lean の `import Mathlib` の探針は約 9 秒で、4 回の実行でほぼ同じ。
- 各題 n=1。修正前と修正後の違いを、この数だけで統計的に示すことはできない。

## 原因の分類

| 原因 | 題数（修正前） | 段 |
|---|---|---|
| A. 命題のすり替え（スキームの命題を環や位相空間の補題に弱めて検証を通す） | 5 | 生成（Sketch と Prove）。ローカル検証には、命題が依頼に合うかの検査がない |
| B. 宣言が見つからない、API の名前や書き方が分からない（`Spec (CommRingCat.of R)` の書き方、`affine_isIntegral_iff`、`Scheme.ΓSpecIso` など） | 3 と重なる | 生成。宣言の索引は生成の入力に接続されていない |
| C. ライブラリに概念がない（層のコホモロジー、高次順像） | 1 | 振り分け。質問から Stacks 用の環境を選ぶ処理が worker に無い |
| D. 時間 | 1 | Sketch が 300 秒 |

- 宣言の索引（pals-agent#72）は、調査用の道具で、`pals_agent` の生成にも worker にも接続されていない。
- 検証器の振り分け（pals-agent#74）は、`build_profile_verifiers` が定義されているだけで、worker のどこからも呼ばれていない。質問から環境を選ぶ処理も無い。さらに、本番の worker は検証をしない（API 側の検証器が `api_reconcile` で検証する）ので、worker の外から別プロファイルを選ぶ契約が要る。
- Stacks 用の検証環境（`stacks-4.35`）は、この Mac にビルド済みのものが無い。今回の測定は既定の環境だけで行い、Stacks 環境の起動や import の時間は測っていない。
- Frontier の補題を使う環境は、最初の 3 つの原因のうち C にだけ効く。A と B は、Mathlib の `AlgebraicGeometry` だけで解決できる範囲だった（2026-11-08 の測定と同じ結論）。

## 修正（pals-agent、1 つの変更）

1. `pals_agent/scheme_guidance.py`: スキーム論の質問（`Spec`、構造層、アフィン射、スキームなどの語）に限り、Draft、Sketch、Prove、修復のプロンプトに案内を足す。内容は、「命題は `Scheme` の命題で書く。環や位相空間の補題に置き換えない」という規則と、ピン留めした Mathlib のソースで存在を確認した名前の一覧。ほかの質問ではプロンプトは 1 文字も変わらない。
2. 検証前の決定的な検査 `pals.scheme_statement_weakened`: スキーム論の質問なのに、定理の宣言ヘッダ（束縛・仮定・命題の全体）のどれにもスキームの語彙（`Scheme`、`Spec`、`IsAffine`、`QuasiCompact` など）が無い、または定理が 1 つも無い候補を失敗にし、修復に具体的な理由を返す。この検査は通過の条件ではなく、通った候補も従来どおり Lean の検証と意味レビューを受ける。次の場合は検査しない。
   - 質問に数値解析・暗号などの語がある（日本語の「スキーム」は、環や射などの語と一緒のときだけスキーム論とみなす）。
   - 質問自体が「位相空間」を述べているときは、`PrimeSpectrum` での答えも許す。
   - `formal_statement` で命題を固定しているとき（命題の一致は別の検査が見る）。
   - 宣言のヘッダを切り出せないとき（判断を保留する）。
   - 環のレベルの語（`IsIntegral`、`IsReduced`、`Opens`、`stalk` の単独）は語彙に入れていない。
3. `ProofRunResult.library_trust`: 信頼の水準（次節）。

## 信頼の水準

- 検証器（`lean_audit`）は、`stacks-frontier-4.35` 系のプロファイルで `lean.library_trust` を診断として返す（`mathlib`、`core`、`frontier_proof`、`frontier_statement` と、使った Frontier のモジュールと定数）。人手で未レビューの定義が定理文に届くのは `frontier_statement` である。
- これまでは、この診断がエージェントの出力にも画面にも渡っていなかった。worker が API へ送る診断の形（`_diagnostic_payload`）は `metadata` を落とす。
- 追加したもの: `ProofRunResult.library_trust`（`trust_level`、`recorded`、`human_unreviewed`、`frontier_modules`、`frontier_statement_constants`）と、成果物のメタデータの同名のキー。未検証なら `null`。既定のプロファイルでは診断が無いので `trust_level=mathlib`、`recorded=false`。複数の定理があれば、最も弱い水準を返す。
- 画面の変更は別の作業。必要な契約は次のとおり。
  - 利用者向けの回答のデータに `library_trust`（上の 5 項目）を持たせる。`human_unreviewed=true` のときは「人手で未レビューの形式化に依存」と表示する。
  - 本番では API 側の検証器が検証する。そこで `lean.library_trust` の診断を保存し、worker の `_diagnostic_payload` の許可項目に `metadata` を足すか、API が検証結果から同じ要約を作る。worker 側の値は参考で、正本にしない。
  - 本番の worker に Stacks 環境で検証する経路は無いので、今は `frontier_statement` が実際に出る回答はまだ無い。
  - 本番（`api_reconcile`）では worker の検証が保留のままなので、worker の `library_trust` は `null` になる。API 側の最終結果に同じ要約を付ける実装が別途要る。
  - 診断が無いとき（既定のプロファイル）の `trust_level=mathlib` は「記録なし」を意味する（`recorded=false`）。Frontier のプロファイルで監査の記録が失敗した場合を、この値で「信頼済み」と扱ってはならない。

## 次に効く対策（優先順）

1. 質問から検証環境を選ぶ振り分け（原因 C、件数は今回 1 題だが、層のコホモロジーを含む質問の全てに効く）。worker が `library_profile` を選び、API の検証器の配備側が対応する環境を持つ必要がある。配備を伴うので、案としてここに書くだけにする。起動と import の時間は、Stacks 環境をビルドして測る必要がある（今回は未測定）。
2. 部分命題の検出（原因 A の残り）。語彙検査は弱い補題の主な型を弾くが、「依頼の一部だけを証明する」型は弾けない。形式化した命題と依頼の同値性を、固定した命題（`formal_statement`）で縛る方法が正攻法で、スキーム論の質問には Mathlib の定数で書いた命題を持つカードが必要になる。
3. 案内に載せる API の拡充。連結性、`PrimeSpectrum` と `Spec` の対応、準連接層など。ピン留めした Mathlib での存在確認を必ず行う。
4. Sketch が 180〜300 秒かかる題の短縮。誤った命題を Sketch に書かせるのが長引く原因で、1 と 2 が効けば減る見込み。
5. Lean の 1 回の検証は約 9 秒で、`import Mathlib` の読み込みが支配的。`import` を `Mathlib.AlgebraicGeometry.*` に絞る案があるが、今回の測定では差が見えなかった（修正後の検証も約 9 秒）。短縮の余地は小さい。

## 限界

- 測定は検査の最初の版で行った。独立レビューを受けて検査を狭めた版（宣言ヘッダ全体を見る、cue を絞る）は、保存済みの生成物 20 件で結果が変わらないことをオフラインで確かめただけで、再測定はしていない。

- 各題 n=1。修正前後で独立な再現は取っていない。
- 「依頼どおり」の判定は、意味レビュー（モデル）の承認と、定理文の語彙の確認による。人手のレビューではない。
- 修正前後の実行は別の日の負荷の下で行い、負荷は同程度だが同一ではない。
- Stacks 用の検証環境の測定は、環境が手元に無いため行っていない。
- ローカルの検証は、本番の API 検証より緩い。本番は定理が 1 つであることを要求し、「コメントだけの検証済み」は通さない。今回の修正は、その差を生成の側でも埋める。
