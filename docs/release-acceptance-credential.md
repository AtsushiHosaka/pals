# リリース受入リクエスト用の認証情報設計（提案）

状態: 提案。ライブのトランスポートは実装しない。`docs/release-reliability-policy.md` と `AGENTS.md` は現在「所有者がログイン済みのブラウザアカウント」だけを承認しており、本書の方式は所有者の承認後に適用する。参照: AtsushiHosaka/pals#318。

## 目的
`pals-scripts/release-post-request.py` が本番へ有償の受入リクエストを1件だけ作るための、最小権限で短命な認証手段を定める。ブラウザの sessionStorage の写しにはトークンのキー名の契約がなく、非対話で使えない。

## 冪等キーとサイクル
- キー = sha256(候補マニフェストsha256, シナリオID, サイクルID)。
- サイクルIDは release-cycle の1回の試行（attempt）ごとに、コントローラが `run()` の冒頭で UUID v4 を1度だけ発行し、`journal.jsonl` に記録して `post-request` へ `--cycle-id` で渡す（controller 側の対応は別PR）。それまでは、試行ディレクトリに保存した値を運用者が渡す。
- 同じ候補の再リリースは新しいサイクルなので新しいキーになり、古いリクエストを引き継がない。
- 失敗したリクエスト（`failed` / `needs_input`）は観測して報告し、同じサイクル内では再投入しない。再投入は新しいサイクルでのみ行う。
- journal の末尾が壊れた行（書き込み途中のクラッシュ）は捨て、途中の行が壊れていれば拒否する。

## 認証方式
1. 受入専用の非管理者ユーザーを1つ用意する。管理権限・課金管理・他ユーザーのデータへの権限を持たない。
2. 所有者が、明示的なローカル操作で有効期間5〜15分のアクセストークンを発行する。refresh token はランナーに渡さない。
3. トークンは継承した fd か stdin で渡す。argv、計画JSON、Git、SSM には載せない。ログ・journal・標準出力にも出さない。
4. サーバー側で、そのユーザーに「1時間あたり1リクエスト」と支出上限を課す。冪等キーを鍵にした監査行を残す。
5. アダプタは契約の `api_origin` に固定し、リダイレクトを辿らず、作成の試行は1回だけにする。応答が失われた場合の再試行は、同じ冪等キーでの観測として扱う。

## 未解決
- アクセストークンの発行手段（Cognito のどの操作か）と、1時間1件・支出上限を強制するサーバー側の実装は未着手。
- 作成APIが本番で同一キーを replay することの確認が必要（`replay_safe` を宣言する根拠）。

## 既存文書へ追加が必要な文（所有者への提案）
`docs/release-reliability-policy.md` への追加案:
> 本番の受入リクエストは、受入専用の非管理者ユーザーが、所有者の明示的な操作で発行した有効期間5〜15分のアクセストークンで1件だけ作成できる。refresh token はリリース実行環境に渡さない。トークンは継承したファイル記述子または標準入力でのみ渡し、コマンドライン引数、計画、Git、SSMに置かない。

`AGENTS.md` への追加案:
> 受入リクエストの冪等キーは候補・シナリオ・サイクルで決める。同じサイクルでは失敗したリクエストを再投入せず、再リリースは新しいサイクルとして新しいキーを使う。受入専用ユーザーにはサーバー側で1時間1リクエストと支出上限を設ける。

あわせて、現行の「ログイン済みのブラウザアカウントのみ承認」という記述は、上記の方式を選ぶ場合に限り、受入専用ユーザーの短命トークンを追加で許可する形へ改める必要がある。
