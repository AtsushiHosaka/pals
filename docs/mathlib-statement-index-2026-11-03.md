# Mathlib命題索引の検証

固定したMathlibの全定理から、数学的な命題で検索できる答えなしの索引を作り、新規証明の生成に使えるかを調べました。

索引の生成と、モデルを呼ばない検索は実用の水準に達しています。一方、生成へのヒントが修復回数と時間を減らすとは、この標本では言えません。Lunaの12問対比ではヒント群だけが成功した問題が4問あり、基準群だけが成功した問題はありませんでした。ただし、両群とも成功した問題では、修復回数も時間もヒント群のほうが増えています。本番のTerraで完了した対比は2問だけです。本番への組み込みはまだ判断できません。

実モデルの費用は合計約0.92 USDです。内訳はLunaの36実行が0.265 USD、Terraの6実行が0.659 USDです。別に、結果を保存できなかった試運転1回の費用が未記録で残っています。本番のプロンプトと検証器は変更していません。

## 索引の扱い

索引の検索結果は候補です。Lean検証を省略する根拠にも、利用者に「Lean検証済み」と示す根拠にもしません。ヒントの文面にも、未検証であり、Lean検証が判定することを明記しています。

命題が同じかどうかは文字列で判定しません。索引に保存する`type_hash`と整形済みの命題文は絞り込みにだけ使い、一致はLeanで確認します。この調査では`exact?`でLeanに閉じさせる確認だけを判定に使いました。

索引はカードでもRecipeでもありません。生成物は大きいため、リポジトリには入れません。

## 生成手順と版の管理

対象はLean `v4.32.0-rc1`、Mathlib `8b62164d808cd0f23b7d8cc28190a6c1a1bb483a`です。コードは`pals-agent/tools/mathlib_index/`にあります。

コンパイル済み環境を読むメタプログラムで宣言を取り出します。ソースを正規表現で読むことはしていません。手元では全12シャードの書き出しに約5分、索引の構築に約35秒かかりました。

```bash
PALS_INDEX_OUT_DIR=<raw> PALS_INDEX_SHARDS=12 LEAN_PATH=<lake env の値> lean tools/mathlib_index/ExportDecls.lean
```

```bash
python3 tools/mathlib_index/build_index.py --raw <raw> --out <out> --mathlib-rev <rev> --toolchain <toolchain>
```

出力は`decls.jsonl.gz`（41 MB）、`index.sqlite`（287 MB）、`manifest.json`の3つです。`manifest.json`にMathlibのrev、ツールチェーン、層ごとの件数、`decls_sha256`を記録します。今回の`decls_sha256`は`2d75c08dda82b33d4d16611d96a192fa3645c097266c05c8aefa8d7288bbd749`です。Mathlibを更新するときは索引も作り直します。

## 件数と層の分類

正規表現の単純な数え上げでは183,295件ですが、環境の定理定数は525,900件あります。環境の件数にはMathlib以外の由来が92,864件あり、内部名の層だけで230,001件あります。この2つは重なる場合があります。

分類は機械的な基準のみで、上から順に最初に一致した層へ入れます。

| 層 | 件数 | 基準 |
|---|---:|---|
| internal | 230,001 | 内部名、補完から除外された名前など |
| tooling | 24,479 | Init・Batteries・Mathlib以外の由来、または名前が`Lean`・`Std`で始まる |
| deprecated | 4,412 | 非推奨 |
| instance | 16,973 | インスタンス |
| generated_copy | 23,825 | `to_additive`の複製など、独立した位置を持たない宣言 |
| rewrite_api | 81,577 | `simp`・`norm_cast`・`push_cast`・`ext`属性、またはAPI的な名前（結果を名指しする信号があれば除く） |
| textbook | 20,560 | 次の信号のいずれかを持つ |
| general | 124,073 | 残り |

`textbook`の信号の件数は、説明文と仮定を持つ宣言が18,254件、説明文が結果の名前を挙げる宣言が5,669件、50以上のモジュールの証明で使われる宣言が788件、stacks・kerodonへの参照を持つ宣言が303件、名前自体が結果を表す宣言が154件です。同じ宣言が複数の信号を持つ場合があります。説明文と仮定を持つだけの宣言が大半を占めるため、この層は教科書の定理より広い集合です。

検索の標準範囲は`textbook`と`general`の144,633件、広い範囲はこれに`rewrite_api`と`generated_copy`を足した250,035件です。

分類の妥当性は、Mathlibの`docs/`にある名前付き定理の一覧で確かめました。`wikidata`属性は`1000.yaml`の項目と結びついているため、分類の信号から外しています。

| 一覧 | 定理を正解に持つ項目 | textbook | general | それ以外 |
|---|---:|---:|---:|---:|
| `100.yaml` | 61 | 52 | 8 | 1 |
| `1000.yaml` | 178 | 162 | 10 | 6 |
| `undergrad.yaml` | 124 | 78 | 37 | 9 |

## 検索方式の比較

依頼にあった`pals-agent/pals_agent/external_tools.py`は存在しません。既存の外部検索ツールは使わず、モデルを呼ばない次の方式を比べました。

- 名前の分解語、説明文、命題の語に対するSQLite FTS5とBM25
- Leanで解釈した命題の定数を使う、IDF重み付きJaccardの記号検索
- 上の2つのRRF統合

### 定理名からの検索

名前付き定理の題名で検索し、正解の宣言が上位に入る割合を測りました。標準範囲を対象にしています。

| 一覧 | n | @1 | @5 | @10 | @20 | @50 |
|---|---:|---:|---:|---:|---:|---:|
| `100.yaml` | 61 | .41 | .69 | .75 | .82 | .87 |
| `1000.yaml` | 178 | .36 | .70 | .76 | .81 | .86 |
| `undergrad.yaml` | 124 | | .31 | .38 | .44 | .49 |

比較として、外部サービスLeanSearchの`100.yaml`の結果は@1 .459、@5 .803、@10 .852、@20 .885でした。LeanSearchのMathlib版は固定できないため、参考値です。上位の精度はLeanSearchが高く、固定版に合わせて手元で動く点は今回の索引が優れています。

`undergrad.yaml`の再現率が低いことは未解決です。原因は調べていません。

### 証明の前提からの検索

検証済みカードの証明項から、証明文に名前が明示された定理を正解の前提として取り出しました。対象は713カードで、654カードに合計1,444個の前提があります。`-- manifest card:`の印がない3バンドルの51カードは除外しました。

カード名のハッシュでdevとtestに分け、方式はdevで選びました。testの結果を見た後の調整はしていません。索引はMathlibの環境だけから作り、カードも評価用の一覧も構築に使っていません。

| 方式（test） | 範囲 | n | Recall@5 | @10 | @20 | @50 | Hit@10 | Hit@20 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 記号検索 | 広い | 498 | .443 | .534 | .577 | .647 | .651 | .705 |
| 記号検索 | 標準 | 498 | | .438 | .475 | .525 | .528 | .578 |
| Lean語と記号の統合 | 広い | 498 | | | .552 | | | .697 |
| 英語の問題文と記号の統合 | 広い | 485 | | | .563 | | | .699 |
| Lean語の全文検索 | 広い | 498 | | | .261 | | | .331 |
| 英語の問題文の全文検索 | 広い | 485 | | | .147 | | | .192 |
| 日本語の問題文の全文検索 | | 13 | 0 | 0 | 0 | 0 | 0 | 0 |

正解は一つの証明が使った前提に限られ、別の証明で足りる候補は不正解に数えます。そのため、この再現率は下限です。

Leanで解釈した命題を使う記号検索が最も高く、統合しても上がりませんでした。問題文の全文検索だけでは大きく下がります。依頼された20カードでの記号検索は、Recall@20が.51、Hit@20が.625でした。

日本語の問題文では、testの13問でも依頼カードの16問でも全く当たりません。索引が英語だけだからです。日本語の入力には、先に英語かLeanへ変換する段階が必要です。

検索時間は1カードあたりの全方式の中央値で、標準範囲が0.648秒、広い範囲が1.338秒です。全文検索は1回0.02〜0.4秒です。記号検索の索引の読み込みには純粋なPythonで約13秒かかります。

### `exact?`による既知判定

カードの命題100問を抽出し、モデルを呼ばずに`exact?`で閉じるかを調べました。形式に問題のない88問のうち46問（52%）が閉じました。カタログは80問中39問が閉じ、古い形式の命題など12問はエラーでした。依頼カードは20問中7問です。処理時間は他のセッションと競合した状態で1問あたり中央値約34秒です。

この結果はカードの命題についてのものです。新しい入力では、先に命題をLeanへ形式化する必要があります。

## 生成への効果

本番と同じ生成・Lean検証・修復の流れを手元で実行し、ヒントなしの基準群とヒント群を比べました。ヒント群はSketchとProveのプロンプトにだけ候補を足します。失敗したコードか下書きをLeanで解釈して定数を得て記号検索し、未解決の識別子には近い名前を3件ずつ示します。

### 条件

- 修復の上限は6回です。本番は12回です。
- 同じ問題を同じ群で繰り返さず、各1回の実行です。
- `max_output_tokens`は12,000です。本番の既定は16,384です。
- Lean時間には他のセッションとの競合が含まれます。
- カード標本は、`exact?`が閉じなかったカタログカードをハッシュ順に12問選びました。カードのLean命題を固定したので、モデルは命題を変えられません。

### 過去の例題、Luna low、6問

過去に失敗または成功した例題6問でも同じ対比をしました。カードと違い命題を固定していないため、モデルが自分で形式化します。

基準群は6問中4問、ヒント群も4問が成功し、成否が分かれた問題はありません。localizationとnakayamaは両群とも失敗しました。これらの過去の失敗は`gpt-5.4-mini`での記録です。radicalは今のLunaで両群とも修復0回で通りました。形式化の忠実さを目視で確かめたのはradicalの両群とcompact_imageのヒント群だけで、すべての問題は確認していません。

1問目の証明はファイル全体で、基準群が165行、ヒント群が9行です。ヒント群は候補の`isLocalMin_of_deriv_deriv_pos`を使っていて、基準群の証明にこの名前はありません。この候補はヒント15件中の15位でした。2問目は両群とも命題の文字列照合で何度も失敗し、Lean検証まで届いていません。この問題で分かるのは、ヒントで命題の書き写しの失敗は減らないことだけです。

### 解釈の注意

ヒント群だけが成功した4問のうち、補題名の提示が成功の理由だと明確に言えるのは`clopen_unique_idempotent`だけです。基準群の7回の試行には`PrimeSpectrum.existsUnique_idempotent_basicOpen_eq_of_isClopen`が現れず、ヒント群は2回の試行の両方で使い、修復1回で終わりました。残りの3問では、基準群も同じ補題名を試行の中で使っています。理由は補題の発見ではなく、型の提示か、単なる試行のばらつきかもしれません。この実験では区別できません。

失敗と数えた試行には、Sketchの段階のLean検証失敗や、Proveの段階の`sorry`も含みます。これらも修復回数を消費します。Lunaのlocalizationの基準群は、7回の試行すべてがこの種類の失敗でした。ヒント以外の要因が多く混ざった指標です。

ヒントの作成には時間がかかります。カード12問では1実行あたり平均113秒で、ヒント群の全時間の21%でした。多くは、候補を作るたびにLeanの解釈を別に走らせる時間です。容易な問題では、この時間と追加の試行で遅くなります。入力トークンはヒントを足す分増えますが、修復が減った実行では合計が減りました。

## 判断材料

判断は次のとおり分けて提案します。

**索引の生成と検索を取り込みます。** モデル費用がなく、本番の動作を変えません。ヒントの候補としても、カード作成時の調査や既知判定の準備としても使えます。

**ヒントの本番組み込みは、確認の実行まで保留します。** 効果があるとすれば難しい問題の成功率である可能性があり、容易な問題では時間が増えます。本番はTerraなので、Terraでの対比が必要です。

確認の実行は次の条件を提案します。

| 項目 | 内容 |
|---|---|
| 標本 | `exact?`が閉じず、今回使っていないカタログカードをハッシュ順に12問 |
| 実行 | Terra medium、基準群とヒント群を各1回、計24実行 |
| 修復上限 | 6回 |
| 費用 | 見込み約2.6 USD（今回の1実行平均0.11 USDから算出）、上限5 USDで停止 |
| 続行の条件 | ヒント群だけの成功が基準群だけの成功より3問以上多い。両群成功の問題で修復の合計が増えない。 |

続行の条件は実行前に固定します。満たさない場合はヒントの組み込みを見送り、索引は調査用として残します。

#### 実行前に固定した内容

ユーザーの承認を受け、結果を見る前に次の内容を固定しました。標本は、機械的な選別で残った29問のハッシュ順で、13番目から24番目の12問です。

`calculus_supp_v5_ftc_point_spike_counterexample`、`mv_line_supp_v5_orientation_counterexample`、`mv_foundation_lagrange_multiplier_from_direction`、`calculus_v3_limit_order`、`calculus_supp_v3_geometric_boundary_counterexample`、`la_reuse_kernel_detects_zero`、`commalg_modules_exact_id_zero`、`la_v6_nonzero_maps_zero_composite`、`la_reuse_right_inverse_surjective`、`la_v6_basis_recognition`、`calculus_v4_gradient_direction_bound`、`calculus_v5_two_sided_limit_characterization`

成功はLean検証と公理検査を通った`verified`だけとします。費用の上限で止まった問題は、両群がそろわないので判定から外し、件数を報告します。判定に使う問題が12問未満になった場合も、条件の数値は変えません。条件は問題の差し替えや再実行で満たしません。

**`exact?`の事前確認は別の検討項目です。** カードの命題の52%がモデルなしで閉じました。Sketchで命題が固まった後に`exact?`を試せば、Proveと修復を省ける問題があるかもしれません。ただし、生成の流れの中での効果と遅延はまだ測っていません。

**組み込む場合の追加作業**として、SQLite索引の配布、記号検索の読み込み時間の短縮、Lean解釈の実行場所の決定が必要です。記号検索の前提であるLean解釈の負荷は、本番構成では測っていません。
