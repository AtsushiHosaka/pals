# 初回 Sketch の Lean 検査が落ちる原因と、モデルを呼ばない修復(2026-11-08)

Draft → Sketch → Lean 検査 → Prove の最初の Sketch が Lean 検査で落ちる原因を、診断の規則で分類しました。原因の大きいものから、モデルを呼ばずに直す処理を pals-agent に追加しました(既定オフ、本番プロンプトは変更なし)。

結論を先に書きます。

- 初回の Sketch 検査を通る割合は、同じ12カードで56%でした。失敗の大半は、Mathlib の import 不足と、Sketch 内の中途半端な証明です。
- 失敗した Sketch を `import Mathlib` への置換と `sorry` 化で直すと、同じ12カードの失敗14件のうち10件が直りました。別の12カードでは9件のうち5件で、通過率は50%から71%でした。
- ただし12カードの全工程では、初回に Sketch が通ったカードは6枚から12枚に増え、修復は26回から19回に減りましたが、成功数は10/12のままで、平均秒数は176秒から186秒でした。時間は短くなっていません。

## 分類の方法

`tools/mathlib_index/hint_ab.py --stop-after-sketch` で Draft、Sketch、Sketch の Lean 検査だけを実行し、最初の検査結果を記録しました。Terra medium で、12カード(2026-11-07 の `problems-luna12`)を3回、計36回です。

Lean の診断コードの多くは `lean.error` 1種類なので、メッセージを固定の正規表現で分類します(`tools/mathlib_index/sketch_failures.py`)。主原因は、位置が最も早いエラーの分類です。後のエラーは最初のエラーの連鎖であることが多いためです。記録には分類、コード、件数だけを保存し、Lean 本文と診断メッセージは含みません(`data/*.jsonl`)。

## 結果

| 検査の結果 | 件数 | 割合 |
|---|---:|---:|
| 通過 | 20 | 56% |
| Lean 検査で失敗 | 14 | 39% |
| Sketch が空(コードを取り出せない) | 2 | 6% |

空の2件の原因は調べていません。

Lean 検査で失敗した14件の内訳です。「直った」は、後述の処理で同じ Sketch が検査に通った件数です。

| 主原因 | 件数 | 割合 | 対象カード数 | 直った | 直した手段 |
|---|---:|---:|---:|---:|---|
| 未解決の識別子(`Unknown identifier/constant`) | 4 | 29% | 3 | 3 | import の置換のみ |
| `unsolved goals`(Sketch 内の証明が閉じない) | 4 | 29% | 4 | 3 | 置換のみ1、`sorry` 化のみ1、両方1 |
| `invalid field`(存在しない射影) | 1 | 7% | 1 | 1 | 置換と `sorry` 化 |
| 記法に `open` がない(`𝓝` など) | 1 | 7% | 1 | 1 | `open` の追加 |
| import したファイルが存在しない | 1 | 7% | 1 | 1 | import の置換 |
| 型の不一致 | 1 | 7% | 1 | 1 | 置換と `sorry` 化 |
| タクティクの失敗(`linarith` など) | 1 | 7% | 1 | 0 | 該当なし |
| 構文エラー | 1 | 7% | 1 | 0 | 該当なし |

読み方です。

- 手作業のラベルとして、「未解決の識別子」4件のうち3件は、実在する名前の import 不足です。`import Mathlib` に置き換えるだけで通ったことが根拠です。名前の幻覚と呼べるのは、Mathlib の名前でなく Sketch 内の局所名を使った1件程度です。
- 最初のエラーの位置は、定理本体が10件、命題部が3件、import が1件でした。命題部の3件は、いずれもモデルが選んだ import が足りず、固定された命題が読めなかったもので、`import Mathlib` で直りました。
- 今回の12カードでは、`formal_harness_mismatch`(モデルが命題を書き換える)は Sketch 検査では出ませんでした。Prove の後で出ます(後述)。
- 3回とも通ったカードは2枚、3回とも落ちたカードはありません。通過する確率はカードごとにばらつきます。

## 案ごとの見積もり

モデルを呼ばない計算を優先しました。基準は、36回の初回通過率56%です。

| 案 | 通過率の見積もり | 追加の費用と時間 | 状態 |
|---|---|---|---|
| import を `import Mathlib` に置換し、必要な `open` を足す(失敗時のみ) | 失敗14件のうち6件が単独で直る。56%→72% | モデル0回。Lean 再検査1回、約4秒 | 実装、測定 |
| 失敗した証明ブロックを `sorry` にして骨格を残す | 上の置換と合わせて10/14。56%→83% | モデル0回。再検査1〜2回、約4〜13秒 | 実装、測定 |
| 並列に k 個の Sketch を作り、最初に通ったものを採る | k=2で74%、k=3で84%(3回の通過率を独立と仮定した計算) | Sketch を1回余分に呼ぶ費用(Terra medium で1回あたり約$0.01台)。待ち時間はほぼ同じ | 実装のみ(有料の測定は予算のため未実施) |
| 生成された識別子を Mathlib 索引で事前確認する | 最大でも+3ポイント。未解決の識別子4件のうち3件は実在する名前だった | 索引の構築と保守 | 見送り |
| `exact?` / `aesop` / `grind` を葉のゴールで使う | この記録からは見積もれない。Sketch の失敗ではなく Prove の段で働く | 未計算 | 未実施 |
| Sketch の失敗を診断付きで Prove に渡す(PR #76 の既存フラグ) | 11-08 の測定で時間の短縮なし | なし | 既存 |

`sorry` 化は、Sketch が骨格であることを使います。モデルが本来 `sorry` にすべき段で書いた不完全な証明を、`have` の命題を残したまま `sorry` に置き換えます。Prove はその `sorry` を埋めるので、骨格の構造は保たれます。最終の可否は Lean の検証だけで決まります。

## 実装

pals-agent の PR [#82](https://github.com/AtsushiHosaka/pals-agent/pull/82)(#79 の上)です。

| フラグ | 動作 | 既定 |
|---|---|---|
| `ProofPipeline.sketch_mechanical_repair`(環境変数 `PALS_SKETCH_MECHANICAL_REPAIR_ENABLED`) | Sketch の検査が落ちたら、置換、`open` の追加、ブロックの `sorry` 化を最大3回の再検査まで試す。通らなければ従来の経路 | オフ |
| `ProofPipeline.sketch_parallel` | k 個の Sketch を並列に作り、最初に通ったものを採る | 1(無効) |

命題部、import、構文エラーは `sorry` 化では直せないので、`sorry` 化は定理本体のエラーだけを扱います。

## 測定: 別の12カードで通過率(対にした比較)

分類で見た14件に合わせて作った処理なので、同じカードでの改善は割り引いて読む必要があります。そこで、分類に使わなかった別の12カード(`problems-terra12`)を2回、Sketch の検査だけ実行し、検査に落ちた Sketch に同じ処理を当てました。同じ Sketch の前後なので、モデルの出力のばらつきは入りません。

| 指標 | 処理なし | 処理あり |
|---|---:|---:|
| Sketch 検査を通った回数(24回中) | 12(50%) | 17(71%) |
| 失敗9件のうち直った件数 | | 5 |

直せなかった4件の最初のエラーは、引数の不一致2件(同じカード)、型の不一致1件、構文エラー1件でした。Sketch が空だった3回(12%)は対象外です。再検査にかかった Lean 時間は、失敗1件あたり平均4.7秒でした。推計費用は約$0.35です。

## 測定: 同じ12カードの全工程

Terra medium、修復上限6、同じ12カード。ベースは 2026-11-08 の記録(`proof-pipeline-speed-2026-11-08`)です。処理ありは `--sketch-repair` のみ有効、各カード1回です。

| 指標 | ベース | 処理あり |
|---|---:|---:|
| 初回の Sketch が空にならなかったカード | 6 | 12 |
| 初回の Sketch 検査を直さずに通ったカード | 6 | 7 |
| Sketch の失敗を処理で直せたカード | | 5 |
| 修復の合計回数 | 26 | 19 |
| 修復なしで検証できたカード | 0 | 5 |
| 成功 | 10/12 | 10/12 |
| モデル呼び出しの合計 | 98 | 97 |
| 1枚あたり平均秒数 | 176.1 | 186.0 |
| 成功した10枚の平均秒数 | 122.1 | 115.2 |
| 推計費用(USD、Terra 入力1.25・出力5.00/百万token) | 1.16 | 1.19 |

読み方です。

- 初回の通過率と修復の回数は、はっきり良くなりました。12カードのうち、初回に Sketch を使えたものは6枚から12枚です。
- 成功数は同じです。モデル呼び出しは1回しか減らず、平均秒数は6%増えました。この差は、各カードの個別の差(例: `la_v3_polarization` は48.8秒が76.6秒、`la_v6_rectangular_determinant_transfer` は203.5秒が113.6秒)より小さく、偶然を排除できません。時間の短縮は確認できていません。
- 修復は7回減りましたが、モデル呼び出しは98回から97回にしか減りませんでした。原因は調べていません。
- ベースの記録で、初回に Sketch が空になったカード6枚の平均は165.6秒、そうでない6枚は186.5秒でした。Sketch の失敗が時間の主因だった、という仮説を、この記録は支持しません。
- 時間の約半分は失敗した2枚です。処理ありでは、`mv_foundation_exceptional_section_counterexample` と `commalg_v4_clopen_unique_idempotent` の2枚で1,080秒(全体の2,232秒の48%)でした。ベースでも891秒でした。どちらも修復のたびに `formal_harness_mismatch`(モデルが命題を書き換える)で止まります。次に効くのは、この種類への手当てです。

## 限界

- 各カード1回、n=12 です。成功数と秒数の差は偶然の範囲です。
- 分類と処理の設計は同じ12カードの36回から作りました。別カードでの確認は Sketch の検査だけで、全工程は測っていません。
- ベースは別の日の実行です。同じ日に処理なしを取り直していません。
- 並列 k の Sketch は、実装とテストのみです。費用を理由に有料の測定をしていません。
- 空の Sketch(36回中2回、別の24回中3回)の原因は調べていません。
- 12枚目の `calculus_v5_convex_derivative_monotone` は、予算上限で止まったため同設定で取り直しました。

## 費用

この調査全体の推計費用は約$2.4です(診断 約$0.78、別カードの対比較 約$0.45、全工程 約$1.19)。
