# 障害通知の本番設定と検証記録

2026年11月6日、説明生成の失敗、compute実行環境の異常、監視の停止、ALBの異常をメールで通知する設定を追加しました。本記録は通知経路の技術検証です。数学の回答成功率や、DBで確定した障害件数を測ったものではありません。

通知を有効にした本番アラーム5個、監視プログラムの毎分実行、実メトリクスの受信、専用アラームからSNSを経由したGmail受信トレイへの到達を確認しました。試験用アラームは削除し、不在を確認済みです。この確認は通知経路に限ります。説明生成の修正配備や数学の回答成功を示すものではありません。

## 実装と通知の意味

実装は[Infra PR #106](https://github.com/AtsushiHosaka/pals-infra/pull/106)にあります。確認対象のInfra commitは`52c9c3f2a8bf58ee436f9f67373b510e9291169c`、監視プログラムのSHA-256は`5cd70703ecefa691b715e012492e4a79bd3e359b52d13872171814077d3da5f4`です。既存の通知先を参照し、新たな受信者や購読は作成していません。

監視プログラムはcomputeホスト上で毎分実行し、`PALS/IncidentHealth`へdimensionなし、単位Countの0/1を送信します。アプリのコンテナ、DB、モデルの設定は変更しません。追加したIAM権限はホストの監督用ロールに対する、このnamespaceへのPutMetricDataだけです。

| 監視対象 | 判定 | メール |
| --- | --- | --- |
| 説明生成の失敗 | 直近5分のログで、形式を確認できた説明生成失敗を観測。Maximum >= 1、60秒、1/1。欠測は非異常。 | ALARM時のみ |
| computeの稼働 | 3 actorがすべてrunningかつhealthyなら1。Minimum < 1、60秒、2/2。欠測は非異常。 | ALARMとOK |
| 監視の完了 | 必要な読み取りがすべて完了したときだけheartbeat 1を送信。Minimum < 1、60秒、3/3。欠測も異常。 | ALARMとOK |
| ALBの正常ターゲット | 既存ALB・ターゲットグループのHealthyHostCount。Minimum < 1、60秒、2/2。欠測も異常。 | ALARMとOK |
| ALBまたはターゲットのHTTP 5xx | 2系列のSumをそれぞれ0補完して合計。合計 >= 1、60秒、1/3。欠測は非異常。 | ALARM時のみ |

ログはサンプル時刻の300秒前から5秒前までを読みます。clarificationの別イベントは対象外です。不明な失敗形式、不完全なログ、読み取り上限超過、読み取り中のactor変更などでは正常完了を報告せず、heartbeatの欠測監視で検知します。生ログは外部へ送信しません。

5xxはALBネイティブメトリクスの遅延を考慮して1/3としました。0補完と1/1の組み合わせでは最新点の遅延による見逃しがあり得るためです。[AWSのFILLに関する注意](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/using-metric-math.html)に従っています。アラームは5個、評価するメトリクスは6系列です。

通知は状態遷移時に送信します。ALARMが続く間の失敗ごとにメールを送る仕組みではありません。1分周期でも、評価と配送を含む1分以内の到達は保証しません。説明失敗が観測されなくなっても数学的な復旧は確定しないため、説明失敗と5xxにはOK通知を付けていません。ほかのOK通知も、それぞれ稼働、監視、ターゲット状態の復帰を示すものです。

## 通知有効化と専用試験の最終結果

saved plan v4のapplyは、追加0・更新5・削除0で完了しました。変更は新設5アラームの通知有効化と日本語の説明だけです。readbackで5個すべて通知有効かつOKを確認しました。計画のSHA-256は`cb4c5b471df7caafd3d55a43faa998aea931df20ae1cb7d185b7ba0c4c8de41a`です。

専用probeアラームで実メトリクスによるALARM遷移を起こし、CloudWatchのActionHistoryでSNSアクションの成功を確認しました。Gmailの実検索結果では試験メール1件が受信トレイにあり、SPAMラベルはありませんでした。直接SNS試験も同じ条件で1件を確認しています。

| 試験 | メール記録時刻 UTC | 確認した経路 |
| --- | --- | --- |
| 直接SNS | 04:50:29 | SNSからGmail受信トレイ |
| CloudWatch専用probe | 05:38:23 | 実ALARMからSNS、Gmail受信トレイ |

probe用メトリクスのクライアント発行時刻05:37:17.462103 UTCからメールの記録時刻までは約65.54秒でした。単発の参考値であり、端末通知や人が気づいた時刻ではありません。配送時間のp50・p95とは扱いません。

05:46:15 UTCの回収記録で、試験アラームを削除して不在を確認し、本番5アラームの通知有効を維持しました。メトリクスの履歴は削除しておらず、試験値の再送もしていません。本番の説明失敗メトリクスには人工的な失敗を混ぜていません。

途中の補助readerでは、ALBのdatetimeのJSON変換と、変数名`all`によるTypeErrorを、結果を取得する前に修正しました。また、回収の初回はprobeが既にOKに戻っていたため、ALARM必須の事前条件で停止し、削除は行いませんでした。保存済みの実ALARM・メール到達、現在の設定の完全一致、所有タグを確認した後に回収しました。これらの手順上の失敗を、本番の追加障害や別のユーザー要求として数えません。

## 品質台帳への記録方法と限界

[品質台帳](quality-ledger/README.md)へ、直接SNS到達、読み取り事前確認、通知無効での追加配置、監視配置、実メトリクス受信、通知有効化、専用probeと回収の7試行を記録しました。各行のn=1はその技術試行1回を表し、ユーザー要求数、作成リソース数、受信点数を分母にしません。単体47件とTerraformのmock-plan 5件は局所検証として本書だけに記録し、本番試行へ加算しません。費用とlatencyは未測定のため空欄にします。

本番のアプリ停止や説明生成失敗を人工的に起こす試験は実施していません。一般のLean失敗や個別ジョブの停滞を網羅しておらず、電話端末の通知音・バナーも未確認です。PQO全体の完了とは扱いません。ログの閉じた形式を観測する監視であり、すべての品質低下を検出するものではありません。今後の実障害では、失敗ログの観測、アラーム遷移、メール到達を照合します。通知の確認と、説明生成の修正配備・同一質問での回答成功・Recipeの正規公開は別の完了条件です。
