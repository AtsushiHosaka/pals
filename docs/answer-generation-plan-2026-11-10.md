# 回答生成の精度・時間・費用と同時10人: 現状と方針（2026-11-10）

## 目的

回答生成の精度を上げ、回答までの時間を短くし、費用を下げる。あわせて、10人が同時に回答を生成できるようにする。この Issue には、2026-11-10 時点の調査結果と、作業の分担案をまとめる。

調査の対象は、親リポジトリが pin している `pals-agent` e1b26c5 と `pals-api` 430aa19 のコード、改善ジャーナル、品質台帳、未マージの PR、関連 Issue である。本番に実際に配備されているリビジョンと、本番環境の環境変数の実値は確認していない。以下で「本番が指すコミット」と書くのは、この pin のことである。

## 分かったこと

### 1. 説明は学習者向けの構成になっていない

- 説明を書くモデルに渡るのは、命題と Lean コードだけである（`pals_agent/explanations.py:1499`）。Draft には自然言語の証明と導いた答えがあるが、渡していない。そのため説明は tactic の列から書き起こされる。
- プロンプトが、要約や方針を先に書くことを禁じている（`explanations.py:1548-1580`）。QA にも、結論を先に示す説明を拒否する指示がある（`explanations.py:1826`）。
- 計算問題の答えは、節か結論にしか現れない（#233 と同じ原因）。
- 学習者の水準を受け取る入力がない。
- QA は Luna の出力を Luna が1回だけ判定する。2回拒否されると、検証済みの証明があっても説明が出ない（#223、#252、#319）。

### 2. Lean の修復が当たりにくい

- 修復するモデルに渡る診断は、種別・識別子・行・列だけである。verifier が閉じた語彙へ変換し（`pals_agent/lean_verifier/http_server.py:820-869`）、API が固定文に置き換える（`pals-api/app/domain/models/compiler_feedback.py:10-23`）。モデルは未解決のゴール、期待された型、Lean のメッセージ本文を見ずに修復する。
- この設計は、verifier の任意の文字列をプロンプトへ入れないための防御である。緩めるには判断が要る（下の「判断が必要なこと」）。
- 修復は最大6回で、1回あたり約67秒、約0.039ドルかかる（回帰直線の傾きによる推定。費用は Terra のトークン単価を仮定している）。36題のうち3題が6回を使い切り、時間の22%、費用の29%を使った（`docs/improvement-journal/entries/2026-11-10-offline-savings-analysis.md`）。
- 同じ失敗が続いても止めない。警告をプロンプトに足すだけである（`pals_agent/pipeline.py:1601`）。
- Lean が通らなかったとき、利用者には何も返らない。Draft にある自然言語の証明も出さない。

### 3. 1件の処理がほぼ直列である

- 並行して動くのは、x² の QA 2本と、既定で無効の説明先行生成だけである。
- 説明先行生成は意味審査の間に始まる（`pals_agent/worker.py:873`）。コンパイルの間には始まらない。
- コンパイルの待ちは最大300秒で、worker は1秒ごとに結果を確認する（`worker.py:159`）。

### 4. 同時に処理できる新規証明は2件である

- 上限を決めているのは証明 worker のプロセス数で、本番は2である。infra の許可値は `{1,2}`（`pals-infra/host/private-runtime/compute_runtime.py:247`）、agent 側の上限は8（`pals_agent/worker_processes.py:26`）。
- 10人の負荷試験（#239、2026-11-06）では、簡単な新規証明で p50 が651秒、p90 が871秒だった。29件のうち5件が900秒で打ち切られた。失敗と HTTP エラーはなかった。
- そのとき compute の CPU は最大27.9%で、Aurora は 2 ACU、CPU 100% に達した。次に詰まるのは Aurora である。
- 11件目以降は拒否されず、SQS で待つ。

### 5. 費用

- モデル費用は1題あたり平均0.070ドル。成功は中央値0.050ドル、失敗は0.200ドルである（ローカル測定、36題。Terra のトークン単価を仮定した推定で、実際の単価は未確認）。
- プロンプトキャッシュが効いていない。測定では `cached_input_tokens` が全回0だった。可変の内容がプロンプトの途中にあり、先頭が固定になっていない。
- 検索で得た Draft（最大8件、各2万字まで）を、Draft・Sketch・Prove の3つのプロンプトに毎回入れている（`pals_agent/generator.py:628,720,766`）。
- 説明のプロンプトには Lean コードが2回入る（`explanations.py:1626-1630`）。
- AWS の固定費は30日換算で約370ドル。compute 139、Aurora 約116、NAT 45、制御ホスト31 が大きい（`docs/aws-cost-review-2026-11-04.md`）。

### 6. 改善が本番に届いていない

- `pals-agent` の main は、本番が指すコミットより80コミット進み、83コミット遅れている。機械的な Sketch 修復、文の固定テンプレート、繰り返し失敗での早期停止、import の最小化、段階別の時間計測は main にしかない。
- worker のリリースは、release-cycle v2 の実行 adapter がリポジトリにないため止まっている（#318）。
- 時間・成功率・費用の基準値は、ローカルで1題1回の測定である。本番の段階別の時間と p90、説明 QA の通過率は記録がない。本番で分かっているのは、回答が返った依頼の p50 301秒、p90 877秒（#223）である。

## 方針

効果の大きい順に並べる。

1. **本番系統と main を1本にし、リリースを再開する。** これが済むまで、以下のどれも利用者に届かない。
2. **失敗で時間と費用を使い切らない。** 修復の上限と早期停止を、本番の修復1回ごとの記録にもとづいて決める。先に記録を取る。
3. **修復に渡す診断を増やす。** ゴールと型の情報を、無害化したうえで渡す。精度への効果がいちばん大きいと見ているが、未測定である。
4. **説明の構成を変える。** 答えと方針を先に書き、Draft を説明の入力に加える。QA の基準もそれに合わせる。
5. **証明 worker を 2 から 8 に増やす。** インスタンスは r8a.large のままにし、Aurora の上限を 4 ACU に上げる。8プロセスでのメモリと CPU は未測定なので、負荷試験で確かめる。
6. **プロンプトを固定部分から並べ直す。** キャッシュが効けば、入力の費用と時間が下がる。
7. **コンパイルの間に説明を作り始める。** 初回で通る依頼は、説明の時間（x² で18〜21秒）だけ短くなる見込みである。

1題の時間は、枠を増やしても縮まらない。新規証明は単独でも138〜148秒かかる。縮めるには 2・3・6・7 と Recipe の再利用（約21秒）が要る。
