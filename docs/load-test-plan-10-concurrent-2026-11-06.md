# 10人同時利用の負荷試験計画（2026年11月6日）

固定費の削減（[AWS費用の調査](aws-cost-review-2026-11-04.md)、[容量の読み取り](aws-cost-capacity-2026-11-05.md)）を決める前に、10人が同時に証明を依頼したときの待ち時間と限界を測る計画です。実行はまだしていません。進行は[#239](https://github.com/AtsushiHosaka/pals/issues/239)です。

## なぜ先に測るのか

2026年10月30日〜11月6日のEC2は、計算側の平均CPUが1.1%でした。ただしこれは未リリースの低負荷で、本番の需要を表しません。この数字で縮小を決めると、リリース後に詰まるおそれがあります。

- 計算側の16GiBは、Mathlibのファイルキャッシュ（約7GiB）のためです。8GiBの上限では`import Mathlib`が5.8〜8.1秒から21〜129秒に悪化した実測があります（[品質台帳](quality-ledger/ledger.csv)のpr31）。
- 10人並列の律速は、機種よりレーンごとの並列上限だと見ています。コンテナの上限（assessment 3GiB、proof 1.5GiB、verifier 8GiB）から、本番は並列プロファイルで動いていると読めます。レビュー済みの最大値は、proofが2プロセス、assessmentが4プロセス、Leanのコンパイルが2並列です。
- 並列数の設定値は、2026年11月6日15時台JSTに読み取りで確認しました（下の表）。

### 確認済みの本番設定（2026年11月6日、計算側ホストの読み取り）

| 項目 | 値 | 出所 |
|---|---|---|
| proof worker | 2プロセス（`PALS_WORKER_PROCESSES=2`） | コンテナ環境変数（名前を絞って取得） |
| assessment worker | 4プロセス | 同上 |
| Leanのコンパイル | 最大2並列、タイムアウト300秒（`PALS_LEAN_MAX_CONCURRENT_COMPILES=2`） | verifierの環境変数 |
| 1プロセスの同時処理 | SQSから1件ずつ受け取り、同期的に処理（`MaxNumberOfMessages=1`） | `pals_agent/worker.py`のコード |
| SQSの可視性タイムアウト | 300秒、20秒のロングポーリング、5回受信でDLQへ | キューの属性 |
| ホストのvCPU | 2 | `nproc` |

つまり、本番が同時に進められるのは、証明の生成が2件、評価が4件、コンパイルが2件です。H1の前提（1プロセス1件）は、コードで裏づけられました。

## 目標（オーナーの回答、2026年11月6日）

- **想定する利用:** 10人が同時にこのシステムを使っている状態。10件を一斉に送る瞬間的な負荷ではなく、10人がそれぞれ依頼を出し、結果を読み、次の依頼を出す持続的な利用です。
- **待ち時間:** **最終回答まで**で、1分でできると理想的です。特に、`x^2`のような簡単な問題は、1分で出してほしい（オーナーの回答）。

実測との差を、先に書いておきます。

| 経路 | 単独で1件を処理したときの実測 | 出所 |
|---|---|---|
| Recipeの再利用（回答とLean再検証つき） | 19.9〜23.1秒（中央値21.5秒） | [60入力の実測](aws-broad-benchmark-2026-11-02.md) |
| 新規の証明の生成 | 138〜148秒 | ゲスト回答1件、新規証明12問の平均（[exact-precheck](exact-precheck-2026-11-03.md)） |

- Recipeの再利用は、単独なら1分以内です。10人が同時でも、1分以内に収まるかを測ります。
- 新規の証明は、**1人だけでも1分を超えています**。この時間の大半はモデルの生成と修復の往復で、機種やレーンの数を増やしても、1件の所要時間は縮みません。10人が同時だと、proofレーンの待ちが上乗せされます。
- したがって「1分」は、問題の区分ごとに評価します。簡単な新規（区分A）と再利用（区分B）には1分を目標に置きます。中程度の新規（区分C）は、合否にせず記録します。区分Aが単独で1分に収まるかは、まだ測っていません。収まらなければ、生成の高速化（修復回数、モデルの選択、簡単な問題を事前検査で閉じる）が別に要ります。
- 測るのは最終回答までです。最初の進捗表示までの時間も、参考として記録します。

## 立てる仮説

| 番号 | 仮説 | 外れたときの意味 |
|---|---|---|
| H1 | 10人が同時に始めると、proofレーン（最大2プロセス）が律速になり、最後の人は約4ラウンド待つ。1ラウンドを約140秒とすると、完了まで約9〜12分かかる | 律速が別（assessment、verifier、API）。待ちの場所を特定する |
| H2 | 2 vCPUの計算側は、コンパイル2並列でCPUがほぼ使い切られる | CPUに余裕があれば、vCPUを増やす理由が薄れる |
| H3 | メモリは16GiBで足り、OOMとページキャッシュの追い出しは起きない | 起きれば、ハーネス（段階1）でメモリを切り分ける |
| H4 | Aurora、NAT、ALBは10人でも余裕がある | 余裕がなければ、固定費の削減ではなく増強を検討する |
| H5 | Recipe再利用の経路は、10人が同時でも各リクエストが1分以内に完了する。新規の証明は、1人でも1分を超える | 再利用でも超えるなら、レーンかLean再検証が律速。新規が1分以内なら、想定より速い |

H1の数字は、ゲスト回答1件の実測138秒と、新規証明の平均148秒（[exact-precheck](exact-precheck-2026-11-03.md)）から置いた見積もりで、未測定です。1プロセスが1件ずつ処理することは、コードで確認済みです。

4. 実行前の確認事項:

   - 同時に走る他のリクエストがないこと。

   - DLQは空ではありません。proof-jobsのDLQに23件、proof-requestsのDLQに1件が残っています。試験では、実行前の件数を基準にして、増分で判定します。

### 段階2 実環境の10人

**負荷のかけ方:** 10人が同時に使う状態を作ります。各ユーザーは、依頼を1件ずつ出し、最終回答を受け取ってから20〜60秒の間をおいて次の依頼を出します。1人3件、全体で30件です。最初の1件は、10人のサインインとチャットの作成を終えてから、一斉に出します（最悪ケースの山）。

**費用の見込み:** 通常は約0.95ドル、上限は約2.2ドルです（区分Aが1件0.03〜0.10ドル、Bが0.003〜0.02ドル、Cが0.062〜0.10ドル）。1ドルに近いため、実行前に確認します。実行には、承認額（通常の見込みの1.25倍以上、約1.19ドル）を指定します。

**測るもの:**

| 区分 | 項目 | 取得元 |
|---|---|---|
| 利用者視点 | 依頼から終端までの時間（p50、p90、最大）、失敗の分類 | API、品質台帳の分類コード |
| レーン | proof・assessmentそれぞれの待ち時間、同時処理数 | SQSのApproximateAgeOfOldestMessageと滞留数、ログ |
| 計算側 | CPUの1分最大値、メモリ、コンテナごとのピーク | CloudWatch、`docker stats`、cgroupの`memory.peak` |
| Lean | コンパイルの待ちと所要時間 | verifierのログ |
| DB | Auroraの最大ACU、CPU、接続数 | CloudWatch |
| 通信 | NATの転送量、ALBの5xxとレイテンシ | CloudWatch |

CloudWatchの標準メトリクスは5分粒度です。1分粒度のCPUが必要なら、詳細モニタリングをインスタンスあたり月約2ドルで試験の間だけ有効にします（有効にするときは確認します）。

**判定基準（案）:** 数値はオーナーの判断が要ります。

| 項目 | 合格の目安（案） |

### 再利用が0件だった原因と、DLQの関係（仮説。コードと観測から、未確認）

**仮説:** Recipeの審査サービス（`pals-private-recipe-reviewer`）が本番に配備されておらず、再利用の試行が、毎回、最後まで進めない。

**根拠:**

1. 本番の計算側ホストで動くコンテナは3つだけです（assessment、proof、verifier）。審査サービスのコンテナはありません（2026年11月6日の読み取り）。インフラの実行コードでは、審査サービスは`reviewer_enabled`が真のときだけ作られ、偽なら、期待されるロールは3つだけです（`compute_runtime.py`、デプロイ済み`6ddafd5`）。
2. proofワーカーのコード（デプロイ済み`210ece8`）では、再利用の試行（`attempt_source == "recipe"`）の意味審査で、審査サービスのURLか秘密が未設定だと、`return False`を返します。メッセージは、削除されずに残ります。
3. 削除されないメッセージは、可視性タイムアウト（300秒）のあとに再配信され、5回受信されるとDLQに入ります。同じメッセージが、毎回同じ理由で失敗するので、再試行は、決して成功しません。
4. 観測は、これと整合します。(a) proof-jobsの59件のうち23件が、5回受信されて一度も削除されず、再試行で救われたメッセージは0件（決定的な失敗）。(b) 試験で、再利用の10問に、カタログの回答（`lean_catalog`）が0件。(c) 再利用の区分は、回答が304〜898秒と遅く、2件が900秒でタイムアウト。

**予測（検証できる）:** 試験の後に、proof-jobsのDLQが、試験前の23件から、再利用の試行ぶん（最大10件）増えているはずです。試験の時間窓の受信数は、「削除数＋5×DLQの増分」に近くなります。増えていなければ、この仮説は外れです。

**仮説が当たっていた場合の影響:**

- 再利用の経路は、機能していない。回答は、再利用の試行が詰まったあとに、新規の生成へ戻ります。そのため、再利用の質問も、新規の質問より遅くなります。
- DLQの23件（約39%）の、少なくとも一部は、これが原因です。#291の分類の入口になります。

**直し方の選択肢（どれも本番の変更で、署名付きリリースが要ります。オーナーの判断が要ります）:**

1. 審査サービスを配備する（`reviewer_enabled`を真にする）。再利用が機能し、1分の目標にとって最も効果が大きい。ただし、コンテナ1つ（メモリ上限1GiB）が増え、秘密の設定も増える。
2. 審査サービスがない間は、再利用の試行を、すぐ失敗にして新規の生成へ戻す。詰まりによる待ち（最大25分）と、DLQの増加が止まる。コードの変更が要る。
3. 審査サービスがない間は、再利用の選択自体を止める。同じ効果を、より小さい変更で得られる可能性がある。

### 次に分かりたいこと

1. 再利用の経路が、いま本番で機能しているか（カタログの選択可能な件数、言い換えの当たり外れ）。
2. 簡単な問題を単独で60秒以内にできるか（生成の高速化の余地。修復回数、モデルの選択、事前検査で閉じる）。
3. proofレーンを増やしたとき、Auroraが次の律速になるか。

- **モデル:** 新規証明は、1件あたり平均0.044ドル（Terra、12問、修復上限12回）〜0.062ドルです（[exact-precheck](exact-precheck-2026-11-03.md)）。1人3件（新規2件＋再利用1件）なら、全体で約0.9〜1.2ドルで、失敗や修復の増加で超える可能性があります。1回のテストが1ドル以下の見込みなら、確認なしで実行します。超えそうなので、実行前に回数と費用を示して確認します。

## 無償Proの付与

[pals-scripts/loadtest-pro-grant.py](../pals-scripts/loadtest-pro-grant.py)を、オーナーが実行します。

**事前準備（1回だけ）:**

1. SSMのプラグイン: `brew install --cask session-manager-plugin`
2. Pythonは、`psycopg`が入った`pals-api/.venv`のものを使います。

**手順:**

| 順番 | コマンド（`<repo>/pals-api/.venv/bin/python pals-scripts/loadtest-pro-grant.py` に続ける） | 内容 |
|---|---|---|
| 1 | `grant` | dry-run。AWSのメタデータだけを読み、10個のCognitoユーザーが有効であることを確認 |
| 2 | `check --execute --confirm-pool pals-mini-prod` | SSMのトンネル、TLS、マスターのログイン、事前検査（読み取りだけ）を確認。何も作らない |
| 3 | `grant --execute --confirm-pool pals-mini-prod` | 一時ログイン（10分で失効）を作り、10個に72時間の無償Proを付与し、読み戻して確認し、ログインを削除 |
| 試験後 | `revoke --execute --confirm-pool pals-mini-prod` | 付与を取り消す |

**仕組みと安全策:**

- あなたのSSOで、SSMのポート転送を開き、RDSのマスターのシークレットをメモリ内だけで読みます。マスターのパスワードも、一時ログインのパスワードも、画面やコマンドラインには出ません。
- 接続は`verify-ca`で、AWSの公開CAバンドル（初回に`truststore.pki.rds.amazonaws.com`から取得）を使って、証明書の連鎖を検証します。ホスト名は、トンネルの都合で`127.0.0.1`のため、検証しません。
- 付与の記録（`sub`と付与ID）は、`~/.pals-loadtest/grants.json`（権限0600）にだけ残ります。監査上の実行者は、一時ログイン名（`pals_op_lt_...`）です。
- 途中で失敗しても、一時ログインは必ず削除します。削除に失敗したときは、ログイン名を表示して、手動での削除を求めます。10分で失効し、パスワードは誰にも表示されていません。
- 事前検査で、ロールの属性、関数の存在、マスターのADMIN OPTION、前回の一時ログインの残りを確認します。1つでも外れれば、何も作らずに止まります。

**検証の範囲:** ローカルの使い捨てPostgreSQL 16で、本番の移行SQLの付与・取り消し関数を使い、一連の流れを通しました（`NOINHERIT`のログインは`SET ROLE`なしでは関数を呼べないことも確認）。本番では、`check`でSSMのトンネル、`verify-ca`のTLS、マスターのログイン、事前検査が通り、続く`grant`で10件を付与できました。初回の`check`で2つの不具合が見つかり、直しています。(1) マスターのADMIN OPTIONをカタログから推測して誤って拒否していたため、ロールバック付きの実際の付与の試行に変更。(2) `aws`だけを終了して`session-manager-plugin`が残りトンネルが開いたままになったため、プロセスグループごと止める形に変更。

## 実行側のスクリプト

[pals-scripts/loadtest-run.py](../pals-scripts/loadtest-run.py)です。本番の公開API（`https://api.palschat.site`、Cloudflare経由）を、Webアプリと同じ経路で呼びます。

1. Cognitoのアクセストークン（15分有効、自動更新）でサインインする。
2. 公開のチャットを1つ作る。
3. `POST /v1/chats/{chat}/proof-requests`で依頼を出し、`GET /v1/proof-requests/{id}`を2秒おきに読んで、`answered`・`failed`・`needs_input`のどれかになるまで待つ。
4. 依頼から最初の進捗表示（`queued`でなくなる）までと、最終回答までの時間を記録する。`answer.evidence_kind`で、実際に通った経路（`lean_catalog`、`lean_verified`、`llm_assessed`、`reviewed_explanation`）を区別する。

- **記録:** `~/.pals-loadtest/runs/<日時>/`の`results.jsonl`、`summary.json`、`summary.md`。問題文、トークン、パスワード、回答の本文は書きません。
- **安全策:** 既定は表示だけで、依頼は出しません（`/health`の確認のみ）。実行には`--execute`と、費用の承認額が要ります。問題の一覧が`draft`のままなら拒否します。失敗が4件に達したら、新しい依頼を出すのをやめます。
- **WAF:** ALBのWAFは、Cloudflareの送信元IPだけを許可し、IP単位のレート制限はありません。Cloudflare側の制限は、試験で初めて分かります。
- **測定の相補:** 試験の開始・終了時刻（UTC）を記録するので、同じ時間窓のCloudWatch（CPU、メモリ、SQS、Aurora、NAT、ALB）を、私が読み取りで集めます。

**手順（`<repo>/pals-api/.venv/bin/python`は不要で、標準のPython 3.12で動きます）:**

| 順番 | コマンド | 内容 |
|---|---|---|
| 1 | `python3 pals-scripts/loadtest-run.py` | 計画の表示と`/health`の確認。何も出さない |
| 2 | 問題の一覧の`status`を、承認の文言に書き換える | オーナーの承認 |
| 3 | `python3 pals-scripts/loadtest-run.py --execute --approve-max-usd 1.5` | 実行（約15〜20分） |
