# 10人同時利用の負荷試験計画（2026年11月6日）

固定費の削減（[AWS費用の調査](aws-cost-review-2026-11-04.md)、[容量の読み取り](aws-cost-capacity-2026-11-05.md)）を決める前に、10人が同時に証明を依頼したときの待ち時間と限界を測る計画です。実行はまだしていません。進行は[#239](https://github.com/AtsushiHosaka/pals/issues/239)です。

## なぜ先に測るのか

2026年10月30日〜11月6日のEC2は、計算側の平均CPUが1.1%でした。ただしこれは未リリースの低負荷で、本番の需要を表しません。この数字で縮小を決めると、リリース後に詰まるおそれがあります。

- 計算側の16GiBは、Mathlibのファイルキャッシュ（約7GiB）のためです。8GiBの上限では`import Mathlib`が5.8〜8.1秒から21〜129秒に悪化した実測があります（[品質台帳](quality-ledger/ledger.csv)のpr31）。
- 10人並列の律速は、機種よりレーンごとの並列上限だと見ています。コンテナの上限（assessment 3GiB、proof 1.5GiB、verifier 8GiB）から、本番は並列プロファイルで動いていると読めます。レビュー済みの最大値は、proofが2プロセス、assessmentが4プロセス、Leanのコンパイルが2並列です。
- 並列数の設定値そのものは、保護された設定にあり、未確認です。

## 立てる仮説

| 番号 | 仮説 | 外れたときの意味 |
|---|---|---|
| H1 | 10人が同時に始めると、proofレーン（最大2プロセス）が律速になり、最後の人は約4ラウンド待つ。1ラウンドを約140秒とすると、完了まで約9〜12分かかる | 律速が別（assessment、verifier、API）。待ちの場所を特定する |
| H2 | 2 vCPUの計算側は、コンパイル2並列でCPUがほぼ使い切られる | CPUに余裕があれば、vCPUを増やす理由が薄れる |
| H3 | メモリは16GiBで足り、OOMとページキャッシュの追い出しは起きない | 起きれば、ハーネス（段階1）でメモリを切り分ける |
| H4 | Aurora、NAT、ALBは10人でも余裕がある | 余裕がなければ、固定費の削減ではなく増強を検討する |

H1の数字は、ゲスト回答1件の実測138秒と、新規証明の平均148秒（[exact-precheck](exact-precheck-2026-11-03.md)）から置いた見積もりで、未測定です。proofレーンが1プロセスあたり1件ずつ処理することを前提にしています。

## 段階

実行する順番は、本番を止めない段階2を先にします。

| 段階 | 内容 | 本番への影響 | モデル費用 |
|---|---|---|---|
| 0 準備 | 並列数の実設定を確認。テスト用アカウントと問題を用意 | 読み取りのみ | なし |
| 2 実環境の10人 | 本番と同じ経路で、10件を同時に依頼し、待ちと資源を測る | actorを止めない。通常のリクエストとして処理 | 約0.5〜1ドル |
| 1 インフラのゲート | 既存の[負荷試験ハーネス](https://github.com/AtsushiHosaka/pals-infra/tree/codex/aws-private-runtime/host/lean-parallel-loadtest)でメモリ・OOM・コンパイルの重なりを判定 | 本番のactorを止める（quiesce） | なし（fakeを使用） |

段階1は、段階2で「並列上限を上げる」「機種を上げる」判断が出たときだけ行います。段階1のハーネスは、本番のhostではまだ一度も実行していません。

### 段階0 準備

1. 本番の並列数を確認します。読み取り専用で、秘密を含む環境変数ファイルは開きません。次のどちらかで足ります。
   - `docker top`でproof・assessmentのプロセス数を数える。
   - verifierのコンパイル並列数は、実行済みのログか設定の差分で確認する。
2. テスト用アカウントを10個用意します。アカウントの作成は私が行えない範囲なので、オーナーかテスト用の既存アカウントを使います。
3. 問題を10問選びます。
   - 互いに異なる、仮定を明示した中程度以上の証明問題にします。
   - 平方展開`(x+y)^2`の問題は使いません（AGENTSの方針）。
   - Recipeの再利用に当たらない問題にします（再利用だとproofレーンを通らず、測定にならない）。
   - 開発中に解けると確認済みの問題にします（失敗の切り分けを容易にするため）。
4. 実行前の確認事項:
   - 利用枠・課金の状態（テスト用の権利で課金が走らないこと）。
   - 同時に走る他のリクエストがないこと。
   - SQSの滞留とDLQが空であること。

### 段階2 実環境の10人

**投入:** 10件を5秒以内に送ります（最悪ケース）。必要なら、60秒かけて10件を送る場合も1回測ります。ただしモデル費用が倍になるため、オーナーの確認後です。

**測るもの:**

| 区分 | 項目 | 取得元 |
|---|---|---|
| 利用者視点 | 依頼から終端までの時間（p50、p90、最大）、失敗の分類 | API、品質台帳の分類コード |
| レーン | proof・assessmentそれぞれの待ち時間、同時処理数 | SQSのApproximateAgeOfOldestMessageと滞留数、ログ |
| 計算側 | CPUの1分最大値、メモリ、コンテナごとのピーク | CloudWatch、`docker stats`、cgroupの`memory.peak` |
| Lean | コンパイルの待ちと所要時間 | verifierのログ |
| DB | Auroraの最大ACU、CPU、接続数 | CloudWatch |
| 通信 | NATの転送量、ALBの5xxとレイテンシ | CloudWatch |

CloudWatchの標準メトリクスは5分粒度です。1分粒度のCPUが必要なら、詳細モニタリングをインスタンスあたり月約2ドルで試験の間だけ有効にします（有効にするときは確認します）。

**判定基準（案）:** 数値はオーナーの判断が要ります。

| 項目 | 合格の目安（案） |
|---|---|
| 終端への到達 | 10件すべて。インフラ起因（`infra.*`）の失敗は0 |
| 完了時間 | p50が3分以内、p90が10分以内 |
| メモリ | OOM kill 0、`MemAvailable`の最小値が1GiB以上 |
| Aurora | 最大ACUが上限（2）に張り付かない |
| DLQ | 0件 |

**中止条件:** 累計のモデル費用が1.5ドルを超えそうなとき。失敗が3件以上連続し、原因が環境側にあるとき。

### 結果の読み方

| 結果 | 次の判断 |
|---|---|
| H1が当たり、他に余裕がある | 機種ではなくレーンの並列上限の引き上げ（コードとレビュー）を検討 |
| CPUが飽和（H2） | 並列上限とvCPU（xlarge）をセットで検討。段階1で確認 |
| メモリが逼迫（H3が外れる） | 段階1でメモリの切り分け。縮小は行わない |
| すべて余裕がある | 10人はこの構成で足りる。固定費削減（EC2・NAT）は、リリース後の実測と合わせて検討 |

## 費用

- **モデル:** 新規証明は、1件あたり平均0.044ドル（Terra、12問、修復上限12回）〜0.062ドルです（[exact-precheck](exact-precheck-2026-11-03.md)）。10件で約0.5〜1ドルで、失敗や修復の増加で超える可能性があります。1回のテストが1ドル以下の見込みなら、確認なしで実行します。超えそうなら、回数と費用を示して確認します。
- **AWS:** 追加のインスタンスは立てません。詳細モニタリングを使う場合だけ、数セントです。
- **反復:** 同じ問題の反復はしません。結論に必要な最小回数（1回）にします。

## 実行前にオーナーが決めること

1. 目標の定義: 「10人が同時に依頼」か、「10人がそれぞれ別の時刻に使っている」か。
2. 許容する待ち時間（上の案でよいか）。
3. 実行の時期（段階2は本番を止めない。段階1は本番のquiesceを伴うため、都度確認）。
4. テスト用アカウントの用意。
5. 段階1に進む場合、署名済みmanifestの有効期限の確認（失効後にactorを止めると戻れない）。
