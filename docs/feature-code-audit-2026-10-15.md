## 結論と範囲

本番復旧時の主要な正常系は成功しているが、全分岐・障害時まで正常とは言えない。今回のレビューでは優先して直すべき5項目を確認した。実装や本番設定は変更していない。

対象は本番と同じ API `0abc2f5`、frontend `ee35e1f`、infra `7cb51d8`。認証HTTP処理、プロジェクト作成、証明要求・ゲストの状態管理、資料通信、検索・共有の入口、公開ルート、運用監視を読んだ。これは全コードの網羅的監査やセキュリティ認証ではない。CodeRabbitによる差分レビュー結果ではなく、ソース読解・公開経路の読み取り確認・ローカル障害注入による所見。

## 1. P2: 回答の種類によってLeanソース表示の公開ルートが欠ける

- ゲストの `llm_assessed` / `reviewed_explanation` は `GuestLeanSourcePanel.tsx:38` から `getGuestRequestSources` を呼ぶ。`lib/api/guestChat.ts` は `GET /v1/guest/proof-requests/{id}/sources` を要求するが、infra `host/macmini-edge/guest-chat.caddy:35` 以下には `/lean` と `/answers` しかなく、`/sources` がない。
- 本番で今回のQA要求IDへの匿名GETを比較すると `/sources` は入口の `404 text/plain: Not found`、`/lean` はAPIの `401 application/json: guest_session_required`。後者の401は認証情報を送らない確認として正常。前者はAPIの認証境界に到達していない。
- ログイン後にも、カタログ証明を使う `lib/api/proofRequests.ts:83` の `/v1/proof-requests/{id}/lean-source` に対する許可OriginのOPTIONSが404。他方 `/sources`、`/retry`、proof-job `/recovery`、数学設定、検索は同じOPTIONS条件で200。
- 影響: 新たにコンパイルした証明は表示できても、参照・カタログから返した回答のコード表示は失敗する。今回カタログ回答そのものは新規生成していないため、回答生成の可否とは区別する。
- 対策: GET/OPTIONSの厳密なパスを既存Host境界内に追加し、ソースの存在だけでなく公開入口経由の回帰テストを追加する。所有権・Cookie・Origin検証は維持する。

## 2. P2: 一時的な進捗取得失敗で自動更新が止まる

- `pals-webfront/hooks/useProofRequests.ts:65` は成功時だけ次回タイマーを設定し、catch (`:66`) はエラー状態を保存して終了する。`useGuestChat.ts` のpollにも同様の構造がある。
- ローカルVitestで検証中の要求を返し、次のGETだけ通信エラーにすると、その後120秒進めても取得回数が増えないことを再現。`working=true` は残る。手動refreshで再開することも確認した。
- `ProjectDetailScreen.tsx:968` と `LegacyChatArchive.tsx:523` はその状態で送信を無効化する。`ProofRequestThread.tsx:103` に手動再試行はあるため「復帰不能」とは言わないが、短い通信断だけで利用者の操作が必要になる。
- 対策: 一時的なネットワーク/5xxに限り上限付きの待ち時間を増やす再試行を入れる。認証・所有者変更・404等を同一視しない。検証中の表示と通信中断の表示を区別する。

## 3. P2: プロジェクト作成の応答消失後に重複作成できる

- `pals-api/app/application/services/projects.py:35` は呼び出すたびに新しいUUIDを生成する。APIと `pals-webfront/lib/api/projects.ts:55` に作成操作の冪等キーがない。
- `NewProjectDialog.tsx:91` は失敗表示の後に送信ロックを解除し、同じ入力の再送が可能。DBには名前の同一性を作成操作の識別子として扱う仕組みはない。
- 実サービスと偽repositoryを使い「保存した後にcommit_unknown例外→同じコマンドを再送」を実行し、異なるIDが2つ作られることを再現した。本番データは作成していない。
- 対策: クライアントが生成・保持する操作キーとサーバ側の永続的な重複排除を追加する。応答不明時にも同じキーで結果を再取得できるようにする。プロジェクト名による一律重複禁止は同名作成の用途を壊すため避ける。

## 4. P2: 認証済みAPIの一部にアプリ側の通信時間上限がない

- `pals-webfront/lib/api/client.ts:133` は渡されたsignalだけでfetchする。`useProjects.ts` の作成・一覧、`useProofRequests.ts` の取得・送信は、画面切り替え等のAbortControllerはあるがタイマーによる上限がない。
- 接続が成功/失敗のどちらにも確定せず残る条件では、処理中状態が続く。プロジェクト作成ダイアログは `NewProjectDialog.tsx:99` のpending中に閉じられず、キャンセルも無効になる。
- これはコードで確認した条件付きリスク。本番ネットワークを故意に停止しての再現は行っていない。ブラウザや上流のタイムアウトが先に働くことはあるが、アプリが復帰時間を保証していない。
- 対策: 操作別の時間上限と利用者による待機中断を設ける。書き込みのタイムアウトは未保存を意味しないため、項目3の重複排除と合わせて扱う。PDF処理など既存の長い上限が必要な操作を短い共通値に潰さない。

## 5. P2: 常時監視は機能障害をhealthyと判定し得る

- `pals-infra/host/macmini-recovery/auto_recovery.py:131` の継続監視は `/health`、`/signin`、コンテナ状態とreadyファイルを確認する。`:157` はそれらが成功するとhealthyにする。
- `pals-api/app/api/routes/health.py:10` は候補検証ランタイムの終了を検知するが、DBの業務処理・ゲストIP整合・ログイン成功・プロジェクト作成・外部モデルの応答は確認しない。
- 今回追加したゲストセッション検査は通常デプロイ完了時に実行される。常時監視や `pals_normal_update_authority.py` の既存復旧後ヘルス確認まで自動で拡張されたわけではない。
- 影響: 稼働後に特定APIや外部依存だけが壊れても、監視上は正常のままになり得る。今回の障害も通常ヘルスでは検知できなかった。
- 対策: 既存livenessと分離した機能監視を追加する。ゲストは毎回新しいセッションを発行して制限枠を消費する方式を避け、維持した検査セッションや読み取り検査、専用テストアカウントを用いる。破壊的な自動復旧の判定にすぐ結び付けず、まず機能別に検知・通知する。
