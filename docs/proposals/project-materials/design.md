# プロジェクト資料添付 — 設計案

WORKING / 機能の合意済み部分と料金の未確定部分を含む。要件は[requirements.md](requirements.md)。確認待ちの機能は条件付きの設計であり、既存構成に実装済みではない。

## 所有権と処理

- APIを資料・所有権・利用枠・状態の唯一の管理主体とする。既存Cognito subjectとProjectの所有権で検証する。
- DBトランザクションで5件の枠と必要なアカウント容量を予約する。upload leaseは短命とし、固定された隔離object key・サイズ条件を持つ署名アップロードを返す。
- 完了時に実objectのサイズ・形式・digestを確認する。版とhashを固定し、その後の同じ署名URLによる上書きが確定版へ影響しないよう、stagingと確定原本を分離する。
- 外部ファイルの解析は隔離した処理系に置く。埋込コードや外部リンクを実行しない。page/pixel/展開サイズ/CPU/メモリ/時間に上限を持ち、処理失敗でAPIや証明workerを停止させない。具体的な上限とlibraryは実資料評価後に固定する。
- 原本、ページ別抽出文、画像の読取り結果、検索chunkを別に保持する。抽出器版・原本hash・ページ/座標/行範囲を結合する。PDF内の印刷ページラベルと1始まりの実ページ番号は混同しない。
- 原本閲覧はアプリ認証と隔離し、PDF内JavaScript/埋込ファイル起動/自動通信を許可しない。初期対応外のHTML/Markdownは受理しない。原本ダウンロードは認証後の短命アクセスと安全なContent-Disposition/Content-Typeを用い、署名URLをログへ残さない。
- 自動検索採用時も、全文を毎回モデルへ送らない。owner/project/versionで絞った検索から必要箇所だけ渡す。モデル入力・外部サービス送信の上限は容量とは別に設ける。

## 状態と失敗

`uploading → processing → ready / failed`、任意の生存状態から`deleting → deleted`。

全ページのmanifestを作成し、文字層がないページもOCR/画像処理する。全ページ完了でreadyとする。一部失敗を成功として隠さずfailedとし、処理済みのページは再試行時に再利用してよいが新たな参照元にはしない。原本の閲覧は処理状態と分離する。lease失効・放棄・孤立objectは回収し、再試行は同じ版と処理IDへ結合する。削除済み版へ遅れて到着する処理結果を拒否する。機械的な運用再試行と利用者の新規処理を区別する。

| 状態 | 5件枠 | アカウント原本容量枠 |
|---|---|---|
| uploading | 1件予約 | 申告容量を予約。実byte上限を別途強制 |
| processing / ready / failed | 1件 | 確定原本の実byte数 |
| deleting / 失効後の残留object | 解放済み | 原本の実消去確認までは解放しない |
| deleted / object未作成の予約失効 | 0件 | 0。派生物/バックアップは別途運用予算で追跡 |

この表は提案。削除でファイル件数枠が空いても、容量回収待ちなら新規送信前にその理由を表示する。退避objectや派生物を含めた物理容量を別に計測し、削除/再送で取込の期間上限は復活させない。

既存SQS/S3とAPIの構成を生かすが、未信頼PDFの解析をLean verifierへ追加しない。実装検証で各版ごとに別アプリ/コンテナを乱立させず、必要な隔離処理サービスを一つの安定した役割として設計する。

## 証明・回答との結合

proof開始時に対象projectと利用可能な資料版集合を固定する。実採用chunkはjob固有のmaterial snapshotへ保存し、修復・説明・追加QAも対象snapshotを明示する。原本の後日差替えで過去の意味を変更しない。明示的な再送のみ新しいsnapshotを作る。

「問3を証明」等で資料から命題を補完する場合は、生成前に原本の該当範囲と命題全文を並べて提示する。元依頼・原本version/hash/location・確認された命題全文・確認したowner/時刻をimmutable request bindingとし、後から抽出文を差替えない。独立QAは原本の対象範囲と確定命題の対応を確認したうえで、確定命題とLeanの対象命題を照合する。同じOCR文だけを二回読ませることを原本との独立照合と数えない。確認待ちではproof枠を予約しないが、既に実行した資料解析量は別に計測する。

既存ProofCreate.contextには全文/画像を入れない。workerは既存のjob/claim認証に結合した内部APIから採用範囲の引用と対応する原ページ画像を上限付きで取得し、DB権限を追加しない。証明用Lean行参照と資料の文献参照は別型にする。内部取得権限はstage claimとowner/project/version/hash/rangeへ結合する。APIは出典を所有者・版・hash・範囲で検証し、独立QAも同じ資料snapshotを受ける。

資料の指示や『この定理は正しい』という記述は認証・料金・ツール権限・Lean検証を変更できない。抽出された問題の意味が不確かなら確認を要求する。資料閲覧・抽出文にLean検証済み表示を流用しない。画像だけの自動生成は追加せず、inline送信には何を証明・説明したいかを入力する。

## 削除・外部処理

新規参照の禁止を同期処理し、原本・抽出文・索引等の物理削除を追跡する。削除後の過去引用保持は、全文検索索引の保持を許すものではない。削除対象を参照中のjobでは以後の外部送信・公開を止め、利用tokenの仮押さえを解放する案とする。バックアップからの消去期限、provider保持期間は次の決定対象。削除APIに『即時完全消去』を偽って表示しない。

既存のS3はversioningが有効なため、delete markerだけでは消去済みにしない。削除対象objectの過去versionと未完了upload、派生objectも対象にする。既発行の閲覧URLは即時失効を保証できないため、原本objectの消去と短いURL有効期限を組み合わせ、最大残存時間を契約へ明記してから実装する。

## 判断の根拠

[OpenAI File inputs](https://developers.openai.com/api/docs/guides/file-inputs)（2026-09-30確認）は、PDF処理に本文とページ画像の入力があることを明示する。50MB保存上限をAI入力上限と同一視しない。

[S3署名URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)（同日確認）は、有効期限内の再利用や同じkeyの上書きを許す。署名URLを一回限りの確定原本として扱わない。

## ページ表示とinline画像

Projectホームの資料カードから右サイドパネルを開く。引用リンクは署名URLを本文へ埋め込まず、material version IDと1始まりの実ページ番号へ結合する。押下時に所有権と削除状態を再確認し、サーバー側で安全に描画したページ画像を表示する。ページ移動・拡大・ファイル名・ページ番号・閉じる操作を提供し、既存Leanパネルとの切替でもチャット入力を失わない。削除後は「資料が削除されました」を表示し、古いキャッシュ画像で代替しない。

inline画像はowner/upload purpose/対象chatに結合し、Project資料枠へ自動追加しない。選択・貼付・ドラッグで添付し、送信前にpreview/除去、送信後は履歴へ固定する。APIが確定した順序付き画像manifest（原本hash、派生画像hash、変換version、寸法）をidempotencyと意味QAへ含める。generatorと別セッションQAへ同じ実画像を渡し、画像欠損や読取不能でtext-onlyへ黙って戻らない。画像の条件を含む同値性に対応していないtext-only Recipe検索はno_matchとして通常の画像対応生成へ進める。

## 使用量と設定

設定は既存chatの入力を保持したまま開く二列dialogとし、狭い画面では縦配置にする。一般設定と使用量/プランを分離し、未実装の通知/連携等を並べない。アカウントメニューは本人名・実プラン・実残量を使う。旧APIの回数をtokenと呼ばず、旧/new policyを明示して移行する。

成功確定まで最大予算を予約し、成功時に実績を確定して余りを返す。失敗時は全予約を解放する。失敗後の説明再試行は、その時点の通常枠を再予約し、残量不足なら外部処理前に止める。最初の予約が期間をまたいで成功した場合は予約した元期間へ確定し、後の期間へ勝手に付け替えない。1proofの成功確定は最大1件。旧予約・旧失敗へ遡及適用しない。換算した利用tokenで全工程を合算する（D11/D12回答済み）。同じ依頼の失敗した過去cycleの費用を成功した説明再試行へ遡って課さず、成功cycleの事前上限内の費用を一度だけ確定する案とする。


## 事前上限と全工程計測

見積は課金policy/価格表version、owner、本文hash、順序付き画像manifest、Project資料snapshot、モデル、最大利用token、期限へ結合する。送信直前に同じ入力と資格をサーバーで再確認し、DBで最大tokenを予約できたときだけjob/outboxを作る。並行送信でも残量を超えない。編集・資料変更・見積失効時は再見積を表示し、利用者が見ていない大きな予算へ置換しない。

各外部呼出し前に、stageの既存claim/元資料hashに結合した永続call permitで入力上限と最大出力を予約する。未確定callと確定実績の和が依頼上限を超える次の呼出しを許可しない。上限不足なら、それまでの不完全な出力を成功扱いせず失敗として依頼のtoken予約を解放する。上限超過分を後請求しない。

全工程とは生成、修復、経路選択、検索embedding/reranking、独立semantic QA、説明生成・修正・QAを含む。資料の初回全ページ取込は別operationであり、各質問で全ページOCRを再計上しない。追加質問は独立operationで事前上限・回答QA・成功確定を持つ。

利用量はproviderの実usageを取得し、cached inputはinputの内数、reasoning outputはoutputの内数として二重加算しない。画像入力のprovider tokenがinputに含まれる場合は枚数料金を重ねない。モデル名・価格version・call ID・実token・状態のみを永続化し、本文/画像/署名URLを会計台帳に保存しない。

現在のgeneration-only、best-effort計測はこの精算要件を満たさない。新しいoperation/permit/receipt契約を追加し、既存generation endpointのclaim認証を緩めない。通信断やusage欠損を0と扱わず、未解決callがある間は成功会計を確定しない。有限の復旧期限後も不明なら利用者の消費0で終了し、実原価の不明状態は運用記録へ残す案とする。

旧回数と新tokenを足さない。旧jobの予約・履歴は保持し、新token制度はpolicyと適用日で分離する。新UIは単位をAPIから確認し、旧回数をtokenと呼び換えない。具体的な価格・枠と全工程計測の検証が揃うまで新請求制度を有効にしない。


## 資料読取り枠の精算案

取込operationは全ページreadyで初めて全ページ分を確定し、失敗/取消は読取り枠を全解放する。999ページ処理後の失敗も部分消費しない。同じ原本版の再試行では処理済みページを再利用できるが、readyになった一度だけ当該ファイルの全ページ数を確定する。既に成功精算済みの版の運用再配送・再索引は利用者へ二重計上しない。再アップロードは別版・別処理として事前に示す。処理済みページのprovider実原価と試行制限は別計測し、失敗無料を原価0と扱わない。これは資料取込への失敗無消費の拡張案であり、証明への合意と区別して価格決定時に確認する。
