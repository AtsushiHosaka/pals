# 回答経路の段階別レイテンシ計測

質問の送信から回答の表示までを段階別に計測できるようにし、ローカルの実経路で測定しました。誰も内訳を説明できていなかった「1回あたり約5秒の非モデル時間」は、大半がHTTP呼び出しごとの新規プロセス起動と通信の待ち時間でした。API自身の処理は約0.2秒で、Pythonのローカル処理は数ミリ秒です。

測定は2026年11月2日に、ローカルのDocker構成で実施しました。AWS本番の値ではありません。サンプル数も少ないので、下の表の数値は今回の実行の記述値であり、性能の保証ではありません。p95は順位(n−1)×0.95の線形補間です。

## 約5秒の内訳

次の表は、意味的再利用（モデル呼び出し2回が並列で走る経路）の値です。有料アカウントでは本番と同じ11回のHTTP呼び出しを含みます。8件の中央値は、ワーカー内の合計が12.46秒、モデル呼び出しの区間が8.43秒、それ以外が3.39秒でした。

8件の内訳には注意が必要です。7件は有料で、呼び出しの構成は本番と同じですが、最後の出力検査で `proof_reuse_invalid_response` となりました（後述）。残りの1件は回答まで到達しましたが、無料プランなのでinput_tokensとpermitがありません。計測なしの本番ブランチでは、有料で回答まで到達した例が1件あり、画面側で12.1秒でした。

| 段階 | 実測の目安 | 内容 |
|---|---:|---|
| claim | 0.37秒 | API処理は約0.03秒 |
| batch_load | 0.42秒 | API処理は約0.05秒 |
| input_tokens（2並列、1回あたり） | 約1.2秒 | OpenAIの処理は0.1〜0.5秒 |
| permit（2並列、1回あたり） | 約0.7秒 | API処理は約0.04秒 |
| semantic_result（2並列、1回あたり） | 約0.6秒 | API処理は約0.02秒 |
| settle | 0.44秒 | API処理は約0.03秒 |
| 重なりを除いた合計 | 3.39秒 | API処理の合計は中央値0.23秒 |

ワーカーの外にも次の時間があります。

| 段階 | p50 | p95 | 内容 |
|---|---:|---:|---|
| 投入からSQS送信まで | 36ミリ秒 | 155ミリ秒 | outboxの待ち時間 |
| SQSの待ち時間 | 3ミリ秒 | 5ミリ秒 | ワーカーが空いている場合 |
| 回答確定から画面のポーリングで読むまで | 0.98秒 | 1.41秒 | 1.5秒間隔のポーリングによる待ち |

これらを足すと、サーバーとポーリングの非モデル時間は約4.4秒です。さらに、モデル呼び出し自体の区間にも1回あたり約1.2秒の通信時間が含まれます。OpenAIが報告した処理時間との差で、並列の2呼び出しのうち長い方が全体を決めます。これをモデル側に数えるか非モデル側に数えるかで、約5秒という見積もりとの差は埋まります。

ワーカー内の時間は、どの区間にも入らない残りが中央値6ミリ秒まで減りました。Pythonでのバッチ検証、順位付け、プロンプト作成、応答解析は合計で約1ミリ秒です。

## 新規プロセス起動の費用

ワーカーはHTTP呼び出しのたびにPythonの子プロセスを起動しています。`tools/latency/http_helper_overhead.py` を実際のワーカーコンテナ内で15回ずつ実行した中央値は次のとおりです。

| 測定 | APIへのGET | OpenAIへのGET |
|---|---:|---:|
| 現在のヘルパー | 301.5ミリ秒 | 523.3ミリ秒 |
| プロセス内で毎回新しい接続 | 1.1ミリ秒 | 202.0ミリ秒 |
| プロセス内で接続を再利用 | 0.2ミリ秒 | 183.0ミリ秒 |

子プロセスの起動だけで279.4ミリ秒かかり、`-X importtime` ではそのうち約230ミリ秒がモジュールのインポートでした。有料の意味的再利用では、モデル呼び出し以外に6段階があるので、起動だけで約1.7秒になります。

ただし、新規プロセスの起動は認証情報の隔離とハードデッドラインのために入れられた設計です。今回は計測だけを行い、変更していません。permitのように、起動費用を引いてもなお0.3秒ほど説明できない呼び出しが残ります。原因は未特定です。

## 新規証明の内訳

新規証明は3件を測りました。件数が少なく、修復回数の差が大きいので、中央値は参考程度です。

| 項目 | 件1 | 件2 | 件3 |
|---|---:|---:|---:|
| 証明ジョブの合計 | 139.1秒 | 155.8秒 | 448.8秒 |
| モデル呼び出しの区間 | 98.4秒 | 113.6秒 | 359.9秒 |
| Lean検証の合計（API記録） | 11.8秒 | 15.9秒 | 29.1秒 |
| Lean結果の待ち（1秒間隔のポーリングを含む） | 13.9秒 | 17.5秒 | 39.3秒 |
| 文脈の検索（内部のモデル呼び出しを含む） | 11.2秒 | 13.5秒 | 7.6秒 |
| API呼び出しの回数 | 49回 | 41回 | 135回 |
| API呼び出しの区間 | 19.8秒 | 15.8秒 | 52.7秒 |
| どの区間にも入らない残り | 1.5秒 | 1.3秒 | 4.2秒 |

新規証明でも最大の項目はモデル呼び出しです。今回の件3は修復が9回走りました。API呼び出しの区間のうち、API自身の処理は中央値で1.7秒でした。

Lean単体のコンパイルは、失敗した候補も含む15件で中央値2.0秒、p95は12.4秒です。

## 計測できなかったもの

- AWS本番の値。ローカルのワーカーはOrbStack上で動き、APIとの通信はTLSなしのHTTPです。本番は通信にTLSが入るので、1呼び出しの費用は変わるはずですが、増減は未確認です。
- ブラウザーの描画時間。計測はサーバー側と、Web画面と同じ1.5秒間隔でポーリングするドライバーまでです。
- Lean監査の段階。本番ブランチの `pals-agent` にはまだ `lean_audit.py` がありません。別のセッションの変更が入ったら、`VerificationTiming` の段階を追加する必要があります。
- 完全一致の再利用（公開時に約4.7秒と計測された経路）。今回の質問はこの経路に入りませんでした。
- カタログの規模の影響。ローカルに投入できた検証済みのRecipeは1件だけです。本番の20候補のバッチより `batch_load` と検証、入力トークンは小さくなります。
- 同時実行時の影響。測定は1件ずつ、ワーカーが空いている状態で行いました。ワーカー並列度の判断には、負荷をかけた測定が別に必要です。
- 新規証明の区間外の1.3〜4.2秒。アーティファクト保存などが候補ですが、段階を分けていないので断定できません。

## 計測の範囲

`pals-agent` の `runtime_latency.py` を拡張しました。従来はproof requestの有料呼び出しだけが対象で、新規証明は計測していませんでした。新しい追跡基盤は入れていません。

- ワーカーの段階: SQSの待ち時間、API呼び出しとモデル呼び出しごとの時間、役割（draft、sketch、prove、route、repair、semantic review、explain、explanation review）、ローカル処理、Lean結果の待ち。
- APIの段階: 投入、ポーリング、ワーカー向けルート、outbox送信、Leanジョブの反映、候補検証。
- 区間の時間は `Server-Timing` と `openai-processing-ms` を使ってサーバーの処理時間と通信時間に分けます。`Server-Timing` を返すのはワーカー認証の内部ルートだけです。
- 記録するのは固定のラベル、数値、UUIDのSHA-256だけです。証明、命題、回答、URL、ヘッダー、例外の本文は記録しません。

計測の失敗はリクエストに影響しません。計測ありの場合となしの場合で決済の内容が一致することを、単体テストで確かめています。

`pals-observability` は評価履歴をLangfuseへ送るもので、この用途には使っていません。

## 使い方

`pals_agent.latency_report` は、ログを読んで経路と段階ごとのp50とp95を出します。

```bash
python -m pals_agent.latency_report worker.log api.log verifier.log
```

```bash
docker compose logs --no-log-prefix worker assessment-worker api verifier reconciler | python -m pals_agent.latency_report -
```

CloudWatchのログは次のように渡せます。ロググループ名は環境に合わせます。本番では未実行です。

```bash
aws logs filter-log-events --log-group-name "$LOG_GROUP" --filter-pattern '"event"' --query 'events[].message' --output json | jq -r '.[]' | python -m pals_agent.latency_report -
```

ログがない過去の依頼は、DBの時刻から読み取り専用のクエリで集計できます。`updated_at` は後の書き込みでも動くので、確定時刻は上限値です。

```bash
psql "$URL" -v days=7 -f pals-api/scripts/answer_path_latency.sql
```

実経路の測定は `pals-scripts/run-answer-latency-probe.py` で行えます。質問の本文も回答も出力しません。

## 測定の条件

`pals-local` のDBを別のボリュームへ複製し、その複製だけを変更しました。元のボリュームは変更していません。測定後、スタックと複製は削除しました。複製には次の手当てをしています。

- ローカルの移行処理で不足する権限を3件付与しました。proof_verification_candidatesのUPDATE、proof_explanationsのSELECTとUPDATE、関連テーブルのSELECTです。
- `tests/fixtures/recipe_exact_input_power` の検証済みRecipeを1件投入し、対応するツールチェーンを有効にしました。
- テストアカウントに検証用のProプランを付与し、1時間あたりの依頼数の制限を、作成時刻をずらして回避しました。

モデルは実際のOpenAI APIを使いました。生成モデルの選択は gpt-6.1-terra と medium です。意味的再利用の審査は、コードに固定されたモデルで動きます。

## 別途の確認が必要な点

ローカルでは、質問文に `0^0=1` を明記すると `proof_reuse_invalid_response` で失敗する例が多く出ました。計測ありで8件中7件、計測なしの本番ブランチでも4件中2件です。同じ質問の結果がばらつくうえ件数も少ないので、この数だけでは計測の有無による差を判別できません。そこで、計測の有無で決済の内容が一致することを、固定の応答を使う単体テストで確かめています。出力検査が何を拒否したのかは記録に残らず、原因は未特定です。

`0^0` を明記しない質問では、2つの審査が `needs_input` や `miss` を返し、チャットの判定と通常の審査へ進む例が多く出ました。この場合のワーカー内の時間は25〜40秒です。ローカルのRecipeが1件で、数学規約の設定も本番と異なるので、本番での発生頻度は分かりません。

`local_legacy_database_release` は、現在の本番ブランチのコードに必要な上記の権限を付与していません。ローカルでは、新規証明の検証結果の確定と回答への反映で止まります。
