# GPTの3モデルを選び、実績原価を利用トークンへ換算する

2026-10-07 JST。ユーザーはGPT-6 Luna、GPT-6.1 Solに加えてTerraを選択肢に含め、各モデルの実績原価を共通の利用トークンへ換算する方針を承認した。選択モデルを使うのは回答・Leanコードを作る工程で、Draft適合判定などの判断処理は固定する。本資料は仕様変更と実装前調査の記録であり、機能の実装・公開は未完了。

## 選択肢と公式料金

当面はGPT系の3モデルを対象にする。TerraのIDは既存構成と公式資料にある`gpt-5.6-terra`。既存のLuna既定値を維持し、送信前に選択できるようにする。選択結果は依頼に保存し、見積りと再送の同一性判定に含める。

OpenAI Docsで2026-10-07に確認したStandard・短いコンテキストの料金は次のとおり。単位は100万トークンあたりのUSD。

| モデル | API ID | 通常入力 | キャッシュ入力 | キャッシュ書込み | 出力 |
|---|---|---:|---:|---:|---:|
| GPT-6 Luna | `gpt-6-luna` | 0.10 | 0.01 | 0.125 | 0.50 |
| GPT-6.1 Sol | `gpt-6.1-sol` | 2.00 | 0.10 | 2.50 | 10.00 |
| GPT-5.6 Terra | `gpt-5.6-terra` | 2.00 | 0.20 | 2.50 | 12.00 |

出典：[公式料金表](https://developers.openai.com/api/docs/pricing)、[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)。1回のprovider呼出しで入力が272,000トークンを超えると、その呼出し全体の入力・キャッシュ単価は2倍、出力は1.5倍になる。複数呼出しの入力を合算して判定しない。処理方式やリージョンに追加料金が適用される場合は、その条件も価格記録に含める。

## 実績の精算と事前予約を分ける

送信前には最大消費量を表示し、その量を予約する。成功時には各呼出しの実績トークンと該当単価で原価を算出し、全工程の原価を合計してから利用トークンへ換算する。生成、修復、独立QA、説明で異なるモデルを使った場合も、それぞれの単価を使う。失敗時は既存方針どおり利用枠を消費せず、判明しているprovider原価は記録に残す。

現行の換算基準は100万利用トークンあたりUSD 0.75相当。変更時は新規依頼から適用し、受付済み依頼の基準は固定する。トークン数と単価の計算に整数を用い、利用トークンへの切上げは依頼全体で1回だけ行う。

通常入力・キャッシュ入力・書込みを重複しない区分としてproviderから確定できる場合、原価は次式で計算する。

```text
原価USD = ((入力総数 - キャッシュ入力 - 書込み) × 通常入力単価
         + キャッシュ入力 × キャッシュ単価
         + 書込み × 書込み単価
         + 出力総数 × 出力単価) / 1,000,000
利用トークン = ceil(全工程の原価USD / 0.00000075)
```

推論トークンが出力総数に含まれる場合は追加加算しない。欠けた内訳をゼロと推測しない。APIが内訳を返さない場合は、providerの計測契約を確認するまで精算不能として扱う。事前予約の上限見積りは、実績原価として精算しない。

料金条件がStandard・短いコンテキストで、確定した通常入力1,000・出力1,000、キャッシュ入力と書込みがともに0の1呼出しだけなら、LunaはUSD 0.0006で800利用トークン、SolはUSD 0.012で16,000、TerraはUSD 0.014で18,667となる。これは計算例であり、実際の1依頼の料金見積りではない。

## 現行実装では全工程の原価が揃っていない

親リポジトリが参照するAPI `aa8b12c`、agent `7a6c343`、webfront `d436271`のソースを読み取りで確認した。既存チェックアウトは別のrevisionと他作業の変更を含むため、最終判断には参照commitを用いた。モデル呼出しの一覧と根拠は[利用箇所の調査](model-callsite-inventory-2026-10-07.md)に記録した。実provider試験や稼働環境の設定確認は実行していない。

| 確認箇所 | 現状 | 今回必要な変更 |
|---|---|---|
| `pals-api/app/domain/billing_prices.py` | Luna/Terraは全入力をキャッシュ書込み単価で見積る | 新しい価格記録を追加し、実績の内訳を反映する。旧価格は保持 |
| `pals-api/app/infrastructure/repositories/token_accounting.py` | 換算の分母は`750_000`。実績計算でキャッシュ割引を使わない | 新ポリシーで内訳ごとの原価を計算し、全呼出しの合計を最後に切り上げる |
| provider usageとreceipt | キャッシュ書込み数を保持しない | 計測契約・新receipt・追加保存項目を揃える |

既存の`utilization-v1-2026-09-30`や`standard-upper-bound-2026-09-30`を新計算で読み替えない。新規依頼用のポリシーと価格記録を追加する。全工程の集計・実PostgreSQLでの再送/失敗/期間またぎ・各モデルの実provider試験が揃うまでは、今回の仕様を実装済みと扱わない。

## 生成を切り替え、判断とQAは固定する

ユーザーは回答・Leanコードの生成だけを切り替え、Draft適合判定などは固定するよう指示した。説明・追加質問の回答は生成側、独立QA・検索・修復先の判定は固定側に置く。既存の限定的なTerra昇格も固定のassessment方針に残し、選択された回答生成モデルを勝手に置き換えない。

現行コードではassessmentが回答文も生成し、説明とQAも同じモデル設定を参照する。これらを分けてから選択モデルを渡す。ユーザーの指示どおり、先に全モデル利用箇所を調査した。選択モデルと固定モデルの両方の実績原価を利用量へ反映する。

仕様は[PFR-001](../specs/proof-request-reuse/requirements.md)と[BILL-016](../specs/individual-billing/requirements.md)に反映し、実装・検証タスクをそれぞれの`tasks.md`に未完了として記録した。
