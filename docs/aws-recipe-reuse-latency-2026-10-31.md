# AWSでのRecipe再利用と応答時間の実測

2026年10月31日の公開UI検証では、自然数べきの連続性問題に25.003430秒で回答しました。事前にLeanで検証したRecipeを再利用し、この要求用のLeanジョブは作成していません。完全な回答を1秒で返す目標は未達です。

測定対象は、AWS側の要求作成から回答保存までの時間です。ブラウザーから要求作成までの通信時間、回答保存後の受信・描画時間、負荷試験のp50・p95は今回の数値に含めていません。この記録は単発の実行結果と、次の実装候補をまとめたものです。新しい高速経路は実装していません。

最大の区間は、候補のスコープ照合にかかった6.565694秒です。入力には8候補の証明・回答などが含まれ、入力トークン数も7,014と最大でした。ただし、DB検索とモデル処理を別々に計測した値はありません。単一のAPI呼び出しが6.565694秒かかったとは断定しません。

今回の主な待ち時間は、依存順に実行する5回のモデル処理です。新規Leanコンパイルがない経路のため、Lean用インスタンスの増強だけで、この25秒を短縮する設計にはなりません。受付からclaimまでにも1.019604秒かかっており、1秒を目指す場合は、モデル呼び出しと要求の受け渡しを含む経路全体を見直す対象です。

同じ質問の先行要求`8bf7b7ed-b672-4cac-a48d-6f29e2039746`は、AWS上の別リリースで154.333291秒かかりました。先行要求には修正2回とLean検証3回があり、検証の合計は6.768秒でした。今回との比較は、2件の経路と保存結果の違いを示すものです。一般的な高速化率や30同時要求時の性能は、まだ測っていません。

## 1秒を目指す次の候補

対象を、全文と適用範囲を事前に確認した定型問題に限定する案です。まず登録済み問題を新しい会話で選ぶ場合を対象とし、自由な言い換えや追加条件は既存のモデル照合経路で扱います。通常の質問、画像、資料、追加の会話を使う機能は残します。

定型問題の同一性は、版を固定した正規JSONとそのハッシュで管理する案です。初期版では、問題文のUTF-8バイト列をそのまま比較します。Unicode正規化、空白除去、変数名の一括置換、検索上の類似度で一致範囲を広げません。別の言い方を登録する場合は、それぞれの全文と数学的な範囲を別途確認します。

問題文だけのハッシュでは適用条件を表せません。候補の契約には、対象と型、定義域、仮定、量化の順序と依存関係、結論、指定された証明方法、出力言語を含めます。会話・資料・画像・数学上の規約も、要求の状態として識別します。最初の対象では、追加の文脈がある要求をこの経路に適用しません。

この登録は、過去の要求に対するモデルの`approved=true`を保存する仕組みとは分けて定義します。登録時には、定型問題の全文が、公開するentryと実際のLean定理のどの範囲に対応するかを確認します。登録後も、各要求の認証・所有範囲・利用上限・現在の文脈を確認し、その要求と登録済み問題が同一であることを検証する契約が必要です。

### 新しく定義する信頼の契約

| 対象 | 提案する確認内容 |
|---|---|
| 定型問題の登録 | 全文と数学的な範囲を確認した記録、形式の版、公開するentryへの対応を固定する |
| entryと証明 | entry全体のハッシュ、entryを承認したreview署名、実コンパイルreceipt、Leanソース、target、toolchainを照合する |
| 各要求 | 問題の全文・言語・方法・文脈を照合し、認証・所有範囲・利用上限を適用する |
| 現在の状態 | Recipeの公開状態・revisionと、稼働リリースが許可するtoolchain・登録情報を確認する |
| 保存する結果 | 要求ID・claim・revision・要求の状態・entryに結び付けた、専用の同一性確認結果を記録する |
| 停止・失効 | 登録の停止、署名鍵の更新・失効、toolchain変更、検索から回答確定までの途中の公開停止を定義する |

現行の`RecipeCorrespondence`は、異なる2つのセッションIDと、要求に結び付けた対応確認を受理する契約です。新方式では、定型問題の同一性を確認する専用の証拠と受理条件を別途設計します。LLMの承認記録やセッションIDを生成したことにする実装は、この案に含めません。

正しい一致を確認できた要求は、追加のSQS受信、モデル呼び出し、新規Lean実行を待たずに、検証済みの回答を返す専用経路の候補になります。既存の内部worker認可や課金処理をそのまま省略する手順は未定義です。認可・保存・利用上限の状態遷移まで設計し、別の実装レビューを行う必要があります。

### 実装前後に必要な検証

| 検証 | 確認する結果 |
|---|---|
| 登録時の実証拠 | 実コンパイルと独立した登録内容の確認、正規JSON・署名・各ハッシュの対応が実データで成立する |
| 数学的な差 | 定義域、自然数0の扱い、仮定、量化順序、右極限と両側極限、指定方法が変わると同一扱いしない |
| 文脈の差 | 会話、画像、資料、規約、出力言語の追加・変更で、別の要求への確認結果を使わない |
| 失効と競合 | 公開停止、revision・toolchain・鍵の変更や、照合中の状態変更に対応する |
| 要求と権限 | 別ユーザー・別要求の結果を再利用して認可を省略せず、再送による二重処理や利用上限の抜けがない |
| 未対応の入力 | 既存の照合経路へ戻り、汎用質問や既存機能を失わない |
| 実際の応答時間 | 公開UIの送信から回答表示までを、初回・反復・30同時要求で測り、p50・p95と失敗率を残す |

ハッシュ検索だけの時間では、公開UIの回答時間を判断できません。1秒の達成可否は、新しい経路の実装後に、通信・認可・DB処理・回答表示まで含めて測定します。今回の記録では、この経路の安全性や実行時間を実証したとはしていません。
