# Recipe検索を1,000件規模にする変更の測定記録

意味的なRecipe再利用は、1言語・1ツールチェーンあたり32件を超えると使えなくなっていました。この上限を外し、APIが選んだ5件だけを2つの審査モデルに渡す方式へ変更しました。1,082件で正しいカードが5件に入った割合は99.2%です。審査の入力トークンと分類時間は、カタログの件数を増やしてもほぼ変わりません。

ただし、回答を修正したカードでの再測定で誤った再利用が1件見つかりました（[修正後カードの再測定](#修正後カードの再測定)）。候補の絞り込みの問題ではなく、カタログに近いカードが増えると表に出る審査の問題です。解消するまで、公開カタログを増やさないよう勧めます。

この記録はローカル環境での測定です。本番には配備しておらず、本番データも変更していません。

## 本番の現状

意味的な再利用は止まっていないと判断しました。件数の上限が数えるのは検索公開済みの`selectable_entries`で、記録上は20件です。admittedの102件はこの上限の対象ではありません。2026年11月2日の公開3例も`lean_catalog`で回答しています。

根拠は[seq15配備後の読取記録](aws-recipe-semantic-benchmark-2026-11-02.md)とコードです。今回あらためて本番DBを読もうとしましたが、読取専用のコマンドが権限判定で拒否されたため、最新の件数は確認していません。

## 変更内容

- APIに`recipe-window`を追加しました。凍結済みの質問文でカタログを順位付けし、上位5件だけを検証して返します。ワーカーは検索語も件数も指定できません。
- 順位付けの第一候補は`text-embedding-3-large`の1024次元ベクトルです。全件にベクトルがない場合、ベクトルの取得に失敗した場合、保存先がない場合は、文字n-gramのBM25に切り替えます。この切り替えで変わるのは候補の質だけで、審査の条件は変わりません。
- 審査対象の5件を受領記録に残し、精算時に5件以外のRecipeを拒否します。以前は全件の一覧だけを記録していたため、モデルに見せていないRecipeを区別できませんでした。
- 審査プロンプトは、入力の性質を述べる1文だけを変更しました。入力がカタログ全件ではなくなったためです。審査の条件と合議の規則は変更していません。
- ベクトル用の`pals_recipe_retrieval`スキーマは、本番マイグレーションの台帳に登録していません。ベクトルに再利用を認める権限はなく、未導入でもBM25で動くためです。
- 全件を返す旧経路と32件の上限は、旧ワーカーのために残しました。過去の受領記録も従来どおり検証します。

## 再現率

各問いについて、正解のカードと、シードを固定して選んだ他のカードで指定件数のカタログを作りました。陽性は237問です。そのうち131問は教科書カード、40問は本番の20件、66問はくだけた表現や定理名だけなどの難問です。作成者には英語の命題とLeanの命題だけを渡し、順位付けの方式は伝えていません。

正解が上位5件に入った割合は次のとおりです。

| 方式 | 32件 | 100件 | 1,082件 | 1,082件の内訳（教科書・本番20件・難問） |
|---|---:|---:|---:|---|
| 採用: 3-large 1024次元 | 100% | 100% | 99.2% | 100%・100%・97.0% |
| 代替: BM25 | 未測定 | 未測定 | 84.8% | 99.2%・75.0%・62.1% |

別の予備比較では、難問66問と1,045件で次の結果でした。

| 方式 | 上位5件に入った割合 |
|---|---:|
| 以前のエージェント内の順位付け（文字n-gramのcosine） | 51.5% |
| BM25 | 62.1% |
| `text-embedding-3-small` 384次元 | 66.7% |
| `text-embedding-3-large` 1024次元 | 97.0% |

Draft検索と同じ`text-embedding-3-small`では不足するため、`text-embedding-3-large`を採用しました。文字n-gramの改良は開発用の問いでは効果が見えましたが、保留した検証用の問いでは上回らなかったため、方式の選択には使っていません。

## 誤った再利用

本番と同じ`attempt()`の経路で、GPT-6 Lunaのlow設定による実審査を行いました。問いごとに2回の独立した呼び出しです。近似陰性は151問で、定数の変更44問、仮定の削除38問、逆18問、定義域の変更16問、片側と両側の違い9問などです。

| 条件 | 32件 | 100件 | 1,082件 |
|---|---:|---:|---:|
| 近似陰性151問の誤再利用 | 0 | 0 | 0 |
| 同上で片方の審査が承認した回数 | 1/302 | 4/300 | 2/302 |
| 正解カードを除いた陽性237問の誤再利用 | 0 | 0 | 0 |
| 同上で片方の審査が承認した窓の数 | 0 | 0 | 1 |
| 陽性237問で別のカードを選んだ数 | 0 | 0 | 0 |

32件での以前の順位付けでも、近似陰性の誤再利用は0件でした。1,082件をBM25で絞った場合も、誤再利用と別カードの選択は0件でした。

この表の範囲では誤再利用は0件でした。ただし、この0件は規模の影響がないことを示すものではありません。次の節のとおり、同じ質問と同じ近いカードで実際に誤再利用が再現しています。

## 修正後カードの再測定

Draft/Recipeセッションが全カードの回答を書き直した`pals-agent#27`の`fbbc001`で、1,082件を再測定しました。`search-candidates.json`のSHA-256は`8ebd3f199ba3f71e`で始まります。

| 指標 | 修正前 | 修正後 |
|---|---:|---:|
| 陽性237問の再利用率 | 59.5% | 65.4% |
| 教科書カードの再利用率 | 59.5% | 65.6% |
| 本番の20件の再利用率 | 82.5% | 82.5% |
| 難問の再利用率 | 45.5% | 54.5% |
| 正解が5件に入った割合 | 99.2% | 98.7% |
| 近似陰性151問の誤再利用 | 0 | 0 |
| 同上で片方の審査が承認した回数 | 2/302 | 3/300 |
| 正解カードを除いた237問の誤再利用 | 0 | **1** |
| 陽性237問で別のカードを選んだ数 | 0 | **1** |
| 全問の分類時間の中央値 | 6.24秒 | 6.66秒 |
| 1呼び出しの入力トークンの中央値 | 5,491 | 6,700 |

回答が完全な証明になった分、再利用率は上がり、入力トークンは約22%増えました。

誤再利用の2件は同じ質問です。「実数を並べた二つの組で、対応する数どうしを掛けて全部足した値の二乗が、それぞれの二乗和を掛けたもの以下になるのはなぜ？」という一般の有限和の質問に、2次元版の`cauchy_schwarz_two_dimensional`を再利用しました。2つの審査はどちらも、この質問を「2組の実数」についての質問と読んでいます。1件では正解カードが6位で候補から漏れ、もう1件では正解カードをカタログから除いていました。

同じ5件の候補で、この質問を各10回審査して原因を切り分けました。

| 条件 | 2次元版の再利用 | 有限和の再利用 | 不成立 |
|---|---:|---:|---:|
| 修正後カード・2次元版あり・有限和なし | 10 | 0 | 0 |
| 修正前カード・同じ候補 | 7 | 0 | 3 |
| 修正後カード・有限和も候補に追加 | 1 | 6 | 3 |
| 修正後カード・質問を明示的な一般形に変更 | 0 | 0 | 10 |

ここから次のことが分かります。

- 回答の書き直しが原因ではありません。修正前のカードでも10回中7回起きました。先の測定で0件だったのは、偶然に近い結果です。修正前の同じ条件では、片方の審査が承認し、もう片方が止めていました。
- 質問が曖昧なときに、候補に有利な読み方で確定しています。明示的な一般形なら正しく拒否します。本来は`needs_input`にすべき場面です。
- カタログの増加で危険が増えます。32件や100件の候補にはこの2次元版が入っていなかったため、審査の問題が表に出ませんでした。つまり、審査の弱点は規模によって悪化します。
- 正解カードが候補に入っていれば、多くの場合は正しい方を選びます。ただし10回中1回は2次元版を選びました。候補の絞り込みを改善するだけでは解消しません。

審査が回答の誤りとして挙げた3件も確認しました。`splitting_field_is_normal`の零多項式の記述は指摘どおりの誤りでした。`countable_union_of_countable`は審査の読み違いで、回答は正しく書かれています。`dirichlet_primes_in_progression`は、審査の指摘に根拠が示されていませんでしたが、Draft/Recipeセッションの通読で非実指標の段に誤りが1か所見つかりました。この2件はDraft/Recipeセッションが`pals-agent#27`の`f71a674`で修正済みです。今回の再測定は修正前の`fbbc001`によるもので、再実行していません。

## 速度とメモリ

審査の時間と入力トークンは、件数を増やしてもほぼ一定でした。

| 指標 | 32件 | 100件 | 1,082件 |
|---|---:|---:|---:|
| 全問の分類時間の中央値 | 6.28秒 | 6.39秒 | 6.24秒 |
| 全問の分類時間のp95 | 9.72秒 | 10.21秒 | 10.03秒 |
| 再利用した問いの分類時間の中央値 | 6.12秒 | 6.42秒 | 6.00秒 |
| 1呼び出しの入力トークンの中央値 | 5,394 | 5,664 | 5,491 |

APIの読み出しは、実PostgreSQL 16で15回測定した中央値です。読み出し時間にはDB接続、スキーマの検証、Recipeの検証が含まれます。接続先はローカルのDockerで、Auroraではありません。

| カタログ | 経路 | 読み出し時間 | Pythonのピーク | 候補の本体 |
|---:|---|---:|---:|---:|
| 21件 | 旧経路 | 76ms | 0.43MB | 39KB |
| 21件 | 新経路・ベクトル | 109ms | 0.25MB | 10KB |
| 32件 | 旧経路 | 98ms | 0.55MB | 61KB |
| 32件 | 新経路・ベクトル | 102ms | 0.25MB | 10KB |
| 100件 | 新経路・ベクトル | 106ms | 0.23MB | 7KB |
| 1,063件 | 新経路・ベクトル | 144ms | 0.22MB | 8KB |
| 1,063件 | 新経路・BM25 | 150ms | 2.87MB | 8KB |

回答までの時間は少し長くなります。問い合わせのベクトル取得が加わるためで、このMacからの実測は中央値約150msでした。現在の20件と比べると、ゲスト経路で約0.2秒の増加を見込みます。有料経路では、許可と記録の通信も加わります。公開記録の1通信0.28〜0.38秒を当てはめると、合計で約1秒の増加です。この有料経路の数字は未測定の推定です。

## 再利用率を決めているもの

検索の次の制約は審査です。正解のカードが見えていても、再利用に至る割合は次のとおりでした。

| 陽性の種類 | 32件 | 100件 | 1,082件 |
|---|---:|---:|---:|
| 全体 | 57.4% | 58.2% | 59.5% |
| 教科書カード | 59.5% | 58.0% | 59.5% |
| 本番の20件 | 85.0% | 80.0% | 82.5% |
| 難問 | 36.4% | 45.5% | 45.5% |

1,082件をBM25で絞った場合の全体は50.6%です。審査理由を読むと、教科書カードで多いのは次の拒否でした。

- 保存回答が「概略」で、完全な証明ではないと判断された。
- 保存回答の変数名と質問の変数名の対応が明示されていない。
- Leanの命題が質問より狭い、または広いと判断された。

両方の審査が再利用と答えたのに合議で不成立になった窓も、14・23・17件ありました。依頼の分類や数学規約の判断が一致しなかったものです。カードの回答については、Draft/Recipeの担当セッションへ共有しました。

## 残るリスク

スケールによって、審査の既知の弱点が表に出る機会は増えます。2つの審査は同じモデルでプロンプトもほぼ同じで、`request_scope`と規約の選択は合議で比較していません。今回の実測でも、完備性を除いたバナッハの不動点定理や、`order_dvd_totient`の逆のような命題を片方の審査が承認し、もう片方が止めました。片方の承認率は904回中7回です。件数との相関は見えませんでしたが、最終的な安全性は2つ目の審査に依存しています。

実際に、曖昧な質問と近いカードの組み合わせで誤再利用が再現しました。今回の変更では審査を変えていません。カタログを公開で増やす前に、曖昧な質問を`needs_input`にすることと、別モデルの審査や範囲の比較を検討する必要があります。

候補の絞り込みの変更そのものは、現在の20件なら配備して問題ないと判断します。20件には今回の例のような近いカードの組が測定上なく、32件までの測定で誤再利用は0件でした。ただし、本番の20件だけで構成したカタログは測っていません。

## 測定の範囲と限界

- 再現性の確認を除き、測定は各条件1回です。処理できず不採用となった問いは失敗のまま分母に残しました（1,082件の陽性で2問、32件で9問、修正後カードで5問）。
- カードは審査の入力に実データを使いましたが、コンパイル証跡と署名は速度測定用の合成データです。Leanの再検証は行っていません。
- 問いとカードの両方をClaudeが書いたため、実際の学習者の入力より再現率が高く出ている可能性があります。難問の組はこの差を見るために追加しました。
- カタログは作業中のものです。測定には`search-candidates.json`のSHA-256が`413ddc9567043288aa3e27d23fe9a6eda83ea17695ad5407925f8c918d3ac33f`であるスナップショットを使い、これに20件を加えました。
- 陰性のラベルは作成者の意図です。誤再利用の1例は手作業で確認し、誤再利用として数えました。この質問は長さを明示していませんが、2次元の証明では「全部足した」一般の場合に答えられないためです。
- モデル呼び出しは4,838回、入力27,315,193トークン、出力2,351,227トークンでした。版付き単価による費用推計は約3.91 USDで、provider請求書の実額ではありません。修正後カードの再測定は1,249回で約1.16 USD、反復審査は80回です。キーは親リポジトリの`.env.local`のものを使いました。

## 配備の順序

1. 公開カタログは、誤再利用の解消まで増やしません。
2. APIを先に配備します。新しいワーカーが古いAPIに当たると、404で失敗するためです。
3. ワーカーを配備します。この時点ではベクトルがないのでBM25で動きます。
4. 所有者の承認後に、`lean-recipe-retrieval-admit --apply-storage`で保存先を作り、`--vectors`でベクトルを取り込みます。
5. 旧ワーカーがなくなった後に、旧経路と`MAX_RECIPES`を削除します。

コーパスと実行方法は`pals-agent/testdata/recipe-retrieval-eval-v1/`にあります。
