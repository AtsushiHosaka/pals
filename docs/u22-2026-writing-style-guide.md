# U-22・ProtoPedia提出文の書き方

- 調査日: 2026-08-31
- 目的: 今後追加される応募項目も同じ文体と構成で書くための基準

## 調査結果

U-22の公式資料と過去受賞作を確認した。審査で必要なのは、特徴のある文体ではなく、制作した理由、処理の内容、実装上の工夫、動作結果を審査員が短時間で確認できる文章である。

2026年の審査は、プロダクト、テクノロジー、アイデアの観点で行われる。ProtoPediaには、制作背景、作品概要、システム構成、実装内容、既存作品との差、最も工夫した点、開発で苦労した点、今後の予定を記載するよう指定されている。AI活用については、使用した場所、用途、採用理由、得られた効果の説明が必要である。

2024年と2025年の審査員講評では、本人が経験した具体的な課題、課題から必要機能を決めた過程、AIの限界を理解した設計、実装後の検証が評価されている。2023年の受賞者コメントには、一般的でない技術を分かりやすく説明できなかったことへの反省もある。

過去受賞作の概要は、主に次の順序で書かれている。

1. 誰が、どの場面で困っているか
2. 作品に何を入力するか
3. 作品が何を処理するか
4. 利用者に何を表示するか
5. 既存の方法と異なる処理は何か

## PALSで使う文章の形式

### 概要

一文で、入力、主要な処理、出力を書く。技術名は作品を理解するために必要なものだけを含める。

> PALSは、自然言語で入力された数学の命題からLean 4の証明を生成・検証し、検証済みコードを基に学習者向けの証明文を作るWebアプリケーションです。

### U-22の各応募項目

各項目は、最初の一文で結論を書き、その後に仕組みを説明する。

1. 結論を一文で示す
2. 実際の処理を三文から五文で説明する
3. 必要な場合だけ具体例を一つ入れる
4. 実装結果または現在の制約を最後に書く

AI活用の説明は、使用場所、用途、採用理由、確認方法の順にする。使用したサービス名だけを並べない。

### ProtoPediaのシステム構成

利用者の入力から画面表示までの順に書く。見出しには機能名を使う。

```markdown
### 全体構成
### Draft・Sketch・Proveによる証明生成
### Leanによる証明コードの検証
### 入力された命題とLeanの証明対象の照合
### 検証済みLeanから自然言語の証明を生成
### OpenMathとpgvectorによるDraft検索
### 使用技術
```

### ProtoPediaのストーリー

制作動機は、数学科のゼミで経験した問題を二段落以内で説明する。その後は実装の説明を中心にする。

```markdown
## 制作背景
## 解決したい課題
## 作品の概要
## 既存の方法との違い
## 最も工夫した点
## 開発で苦労した点
## 今後の予定
## 開発者からのメッセージ
```

## 文体の基準

- 一段落では一つの内容だけを説明する。
- 技術名を出す文では、その技術を何に使うかも書く。
- 形容詞より、実行する処理を書く。
- 抽象的な動詞を、再生成する、コンパイルする、照合する、保存する、表示するなどの処理名へ置き換える。
- かぎ括弧、太字、対句、キャッチコピーを強調目的で使わない。
- 同じ特徴を複数の項目で繰り返さない。
- Draft検索など開発途中の機能は、実装済みの範囲と残作業を分けて書く。
- Leanによる自然言語説明の完全保証や、ハルシネーションの完全な排除は主張しない。

PALSでは、Draft、Sketch、Prove、Leanコンパイル、命題の照合、説明生成、x²の連続性という具体的な処理を示せばよい。追加の宣伝表現は使わない。
