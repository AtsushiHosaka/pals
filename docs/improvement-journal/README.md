# 改善ジャーナル（時間・成功率・費用）

証明1件あたりの **時間を減らし、成功率を上げ、費用を下げる** ための取り組みを、日付順に欠かさず残す場所です。2〜3週間積み上げた経緯そのものが資産になるため、うまくいかなかった試みも、測定の条件と数字つきで残します。

数字の正本は[品質台帳](../quality-ledger/README.md)（`ledger.csv`）です。ジャーナルは、台帳の行を結ぶ「なぜそれを試し、何が分かり、どう決めたか」の記録です。

| ファイル | 内容 |
|---|---|
| [kpi-timeline.md](kpi-timeline.md) | 3つの指標（時間・成功率・費用）の推移の一覧。1行が1つの測定 |
| [entries/](entries/) | 1回の試み（仮説・変更・測定・結果・判断）につき1ファイル。ファイル名は `YYYY-MM-DD-<slug>.md` |

## 記録の規則

1. **追記のみ。** 過去のエントリは書き換えない。誤りが分かったら、新しいエントリで訂正し、元のエントリに訂正への参照を足す。
2. **1つの試みにつき1ファイル。** ファイルを分けるのは、複数のセッションが同時に追記しても衝突しないためです。
3. **結果が悪くても、効果がなくても書く。** 「効果は確認できない」は有効な結果です。偶然を排除できない差を、改善と書かない。
4. **数字には条件を付ける。** モデル、推論の量、修復上限、カード数（n）、実行回数、実行日、費用、信頼区間（あれば）。条件が違う数字を並べて改善率を作らない。
5. **根拠をたどれる。** PR、コミット、docs、台帳の行ID、生データの場所を書く。たどれない値は書かず、「未確認」と書く。
6. **質問本文・Lean本文・利用者情報・秘密は書かない。** 診断コードと分類だけを書く。
7. **測定や変更をしたら、そのセッションの終わりまでにエントリを足す。** 台帳への1行追加（[AGENTS.md](../../AGENTS.md)）とは別に行う。

## エントリの形式

```markdown
# <題> （YYYY-MM-DD）

- 指標: 時間 / 成功率 / 費用 のどれを狙ったか
- 仮説:
- 変更（PR・コミット・フラグ、既定のオン/オフ）:
- 測定の条件: モデル、推論の量、修復上限、カード、n、回数、実行日
- 結果: 数字の表（ベースと比較。条件が違えば並べない）
- 判断: 採用 / 見送り / 追加測定。理由
- 費用:
- 限界・未確認:
- 次にやること:
- 出典: PR、docs、台帳の行ID、生データ
```
