# スキーム論 第3回: 同値の質問、検証環境の振り分け、Stacks 環境（2026-11-14）

- 指標: 同値の 4 題（v3）での依頼どおりの通過、30 秒以内の題数、Stacks 環境の起動・import・検証の時間。
- 仮説: 連結性が通らないのは、スキームの性質と環の性質の同値を 1 つの定理で両方向に述べないため。層のコホモロジーが通らないのは、worker に検証環境を選ぶ処理が無いため。
- 変更（pals-agent#136、pals-api#107）: 同値の質問に A ↔ B を両方向で述べる案内を足す。質問から検証環境を選ぶ関数（ローカル検証のみ、既定 off）。信頼水準を API の status に足す（既定 off、スキーマ変更なし）。
- 結果（v3、各 n=1）: 依頼どおり 1/4 → 4/4。連結性は部分命題の失敗から、同値の 1 つの定理になった（ただし修復 5 回、708 秒）。Stacks 用の検証環境は手元でビルドできた（StacksCore 116 秒）。定常の検証は既定より約 20% 遅く（9.9 秒 対 8.3 秒）、初回は 24 秒。import を絞ると約 40% 縮む。
- 判断: 採用（#136、#107 はマージ済み、配備なし）。
- うまくいかなかったこと: 最初のビルドで、Lake が Stacks をクローンする最中に失敗し、Mathlib をソースからコンパイルし始めた（止めて、手作業のクローンでやり直した）。広い範囲を止めようとしたコマンドは拒否された（自分のプロセスの PID だけを指定して止め直した）。独立レビューが、振り分けのバグ（選んだあとに再び選び直して必ず失敗）を見つけた。
- 限界・未確認: Frontier を含む環境はビルドしていない。v3 の修正後の時間は StacksCore のビルドと同時で、負荷の影響を受ける。意味レビューはモデルによる判定。
- 次にやること: API の検証器が環境を受け取る契約（配備を伴う案）、Frontier の閉包の検査の判断、T2 経路の有効化、Tag を名指ししない質問への補題の引き。
