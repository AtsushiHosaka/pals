# T2: Draft を外す・単独寄与の切り分け（2026-11-11）

- 指標: 時間（主）、初回コンパイル成功率、費用
- 仮説: Draft→証明の直列が時間の壁。Draft を飛ばす（易しい題）か、Draft を証明と並行に走らせて修復の種にだけ使えば、初回成功を落とさず時間が縮む。2候補の競争と併せて初回成功も上がる。
- 変更: pals-agent PR #107 の追加コミット。`PALS_T2_NO_DRAFT_ENABLED`（`ProofRequest.routine` が真なら Draft なし、偽なら Draft を並行実行して修復用に保持）、`PALS_T2_NAME_SAFETY_ENABLED`（未知識別子の対策の指示）。すべて既定 off。前回エントリ [t2-lane-first-measurement](2026-11-11-t2-lane-first-measurement.md) の続き。
- Issue: AtsushiHosaka/pals#327、#137

## 測定の条件

- 腕（同じ14題、題ごとに4腕を連続・順序は交互、1題1腕1回）: `base`（既定）、`nd_k2`（No-Draft＋2候補。No-Sketch は No-Draft に含まれる）、`t2`（前回の全部入り: No-Sketch＋2候補＋パッチ修復＋並列説明）、`nd_k2_names`（`nd_k2`＋名前の指示）。
- 題: `generation-eval-v1` tuning 分割から層別の14題（easy 3、medium 5、hard 6）。**routine は easy の3題だけ**（評価では manifest の `tier == easy` を査定の代わりにした）。他の11題は Draft を並行実行。
- モデル・Lean・修復上限6・費用の計算・時間の定義は前回と同じ。腕ごとの費用上限US$0.93（ランナーが判定）。
- 負荷（**この測定の最大の弱点**）: 実行前に1分負荷が8以下になるまで最大30分待つ規則にしたが、30分では下がらず（負荷16.4）、そのまま実行した。実行中の1分負荷は題の開始時で平均10.9（最大17.0）、終了時で平均10.8（最大17.2）。腕ごとの平均は 9.8〜10.9 で腕間の差は小さい。固定の小さな証明を実 `LeanVerifier` に通す探針（3回）は、開始時（負荷8.0）で 9.9〜10.6 s、終了時（負荷12.6）で 16.9〜17.4 s。
- **正規化は推計である**: 「Lean 1回を3 s」とみなす。3 s は本番の失敗コンパイル2.0 s と前回の記録（検査2.8〜4.9 s）からの**仮定**で、この端末で無負荷の値を測ってはいない。各題の Lean 区間（重なる区間は1つにまとめる）を3 sに切り詰め、他は測定値のまま。モデル呼び出しは静かな端末でも同じ時間とみなしている。以下 `norm` と書いたものが推計、他は測定値。
- 統計: 題を単位にした対比較。`analyze_stages.py` は共有実装 `pals_agent/evals/analysis.py` を使うように直した（符号反転検定は16題以下で厳密列挙、McNemar は対応のある二値セルのみ）。

### 30秒に届いたか

- **nd_k2 は、測定した p50 で検証まで29.1 s、回答完成まで40.1 s。** 検証までは p50 ≤ 30 s の線にぎりぎりで入った（負荷10前後の端末で）。回答完成（レビューと説明込み）は40.1 s で、まだ10 s 超過している。norm（Lean 3 s の仮定）では 14.5 s と 25.2 s。
- p90: 検証まで47.4 s、回答完成60.5 s（測定）。norm で 33.7 s と 47.7 s。30 s には届かない。n=14 の p90 は事実上13番目の値で、不安定。最悪の題（失敗した hard、修復6回で389 s）は p90 に出ない。
- 題の層ごとの検証までの時間（nd_k2、秒）: easy 10・33・41、medium 11・24・38・47・48、hard 16・23・25・27・31・389。easy（Draft 省略）の3題が速いとは言えない（41 s の題がある）。難度との明確な関係は見えない。
- 残りの壁: (1) 回答完成の後半: 意味レビュー約3 s＋説明の待ち約8 s（`nd_k2` は並列説明を使っていない。t2 では説明の待ちが4.2 s、レビュー3.8 s）。説明を並行化すると p50 で約3〜4 s短縮する見込み（`t2` 腕との差からの目安であり、`nd_k2＋並列説明` は測っていない）。(2) 直接証明の生成が p50 約20 s（出力トークンに比例、2候補の速いほうで決まる）。(3) 初回で通らない題（1/14）の修復が p90 を決める。

### 単独の寄与（切り分け）

- 腕は4つだけなので、**要素ごとの完全な切り分けではない**。分かること: (a) 前回の全部入り `t2` から「No-Draft」を足し、パッチ修復と並列説明を外した `nd_k2` が、時間・費用・初回成功のすべてで `t2` に勝った（時間は14題すべて短縮）。(b) したがって Draft を外す効果は大きい。(c) パッチ修復・並列説明を外したことの効果と、Draft を外した効果は、この比較では混ざっている（`nd_k2` と `t2` は Draft の有無と、パッチ・並列説明の有無の両方が違う）。No-Sketch 単独の腕、2候補単独の腕は測っていない。
- 名前の指示（`nd_k2_names`）は、初回成功を変えず（13/14 同士）、時間はむしろ延びる向き（+5.5 s、区間は0をまたぐ）。この標本では効果を確認できない。初回失敗の題がほぼ無く（nd 系は各1題）、効く余地がなかった。

## 初回失敗の分類（28 回の対比較分＋今回の再実行）

最初の対比較（前回の14題×2腕）で初回が通らなかった9件: `formal_harness_mismatch`（モデルが固定の命題を書き直した）3件（base 2、t2 1）、Sketch 段の失敗（`pals.generation_empty`: Sketch が検査に落ちた。base のみ）3件、Lean コンパイル失敗 3件（うち未知識別子 2）。2候補の競争が走る腕の初回コンパイル失敗は9行で、未知識別子 5、構文エラー 2、その他 2。**多い順に、(1) 固定命題の書き直し（`formal_harness_mismatch`）、(2) 未知識別子**。今回の再実行で初回失敗は nd_k2 が1件（`formal_harness_mismatch`）、nd_k2_names が1件（コンパイルエラー）、t2 が2件（未知識別子1、`formal_harness_mismatch` 1）、base が7件。Sketch 段の失敗は No-Sketch により消える。**上位1位（命題の書き直し）に対しては `fixed_statement_template`（既存のフラグ、本番設定で別途）や `harness_splice` が既にあり、今回の腕には入れていない。** 2位の未知識別子に対する名前の指示は上のとおり効果が見えなかった。

## 判断

- フラグは既定 off のまま。`nd_k2`（`PALS_T2_NO_DRAFT_ENABLED`＋`PALS_T2_PARALLEL_CANDIDATES_ENABLED`）は成功率を落とさず、14題すべてで速く安かったので、次の候補として最有力。ただし1回・n=14・高負荷の端末で、routine は easy の3題のみ。
- 次にやること: (1) 同じ腕を held-out ではなく別の tuning 題（残り56題から）で再測定し、本番に近い負荷で p50/p90 を確認する。(2) `nd_k2＋並列説明` を測る。(3) worker で査定の難度を `routine` に渡す配線（下記）。(4) 命題の書き直し（`formal_harness_mismatch`）を `fixed_statement_template` と合わせて測る。

## 限界・未確認

- 1題1回、n=14、負荷10前後の端末。両腕に同じ負荷がかかるが、同じ題で base の中央値が前回の測定（68.8 s）と今回（92.5 s）で24 s 違う。実行間のばらつきは大きく、絶対値は参考値。
- 「無負荷の Lean 1回」は測っていない（3 s は仮定）。
- routine の判定に査定の結果を使っていない（manifest の難度で代用）。worker 側は未配線: agent の worker のコードに、査定の難度を表す項目が見当たらない。パイプラインの入力（`run_statement(routine=...)`、`ProofRequest.routine`）まで用意した。配線先の項目名が分かれば1行で済む。
- 説明の出力レビュー（説明後の別呼び出し）は測っていない。
- 他セッションの「stage 0」（生成前の自動化）との合成: T2 はプロセス全体の状態を持たず（実行ごとの `ContextVar`）、stage 0 が早期に返してパイプラインを呼ばない場合も、呼んだ後でも干渉しない（単体テストで確認）。実際の統合は未実施。
