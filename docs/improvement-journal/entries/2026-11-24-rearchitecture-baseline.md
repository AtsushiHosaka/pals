# リアーキテクチャのベースライン: コードの規模、変更頻度、CI の時間(2026-11-24)

- 指標: 時間。修正1件の確認にかかる CI の時間と、ランナーの無駄。
- 仮説: 巨大で頻繁に変わるファイルと、全件を走らせる重い CI が、修正1件の時間と release の失敗を増やしている。
- 変更: なし(計測のみ。方針は [rearchitecture-plan-2026-11-24](../../rearchitecture-plan-2026-11-24.md)、親 Issue #493)。
- 測定の条件: 各 repo の origin/main(2026-11-24)。GitHub Actions の runs/jobs API の読み取り。重い CI は起動していない。モデル呼び出しなし。

## 結果

| release-cycle-regression.yml の変更回数(10/1以降) | 70回(100本のテストを名前で列挙しているため) |

取消しの割合は、最初は run の経過時間で49%と書きました(300件の標本)。経過時間は待ちを含むので、ランナーの占有ではありません。step の実行時間で数え直した値が19.8%です。

## 判断

段階1(#485)で、取消しの実占有を 19.8% → ≤ 5% に、テスト追加による workflow の変更を 0回にすることを目標にした。

- 費用: なし
- 限界・未確認: job の started_at〜completed_at は待ちを含むので使わず、runner の割り当たった job の step の時間を数えた。rehearsal の所要時間(約40分)は文書の記載値で、計測していない。
