## 条件（負荷は下がらなかった）

- 負荷ガード（1分平均 6 以下、最大45分待つ）は **12.3 > 6.0 のまま進行**。測定中の1分平均は両腕とも **平均 約11.5、最大 14**。
- Lean 探針（同じ小さな検査）は開始時 14〜40 s、終了時 約15 s。通常は2〜5 s。したがって **この数字も負荷に引きずられている。無負荷の値ではない。**
- 題・モデル・Lean 版・腕の上限（US$0.93/腕）は前回と同じ。1題1腕1回、n=14。

## 推計（測定ではない）: Lean 1回を3 s に切った場合

`--lean-normal-s 3`。Lean の区間（競争は重なりを1回分）を3 sに切り、モデル時間はそのまま。

- 前提: モデル呼び出しの時間は静かな端末でも同じ。負荷が OpenAI 側の呼び出しに与える影響は分からないので、この推計は下限寄りとして扱う。

## 読み方

- **p50 30 s は、実測では未達（40.0 s）。推計では達成（18.1 s）。** どちらが本番に近いかは、無負荷での再測定でしか決まらない。
- p90 は実測でも推計でも 30 s に届かない（112.5／83.9 s）。最大は615.9 s（修復を6回使い切って失敗した1題）。p50 の改善は、初回で通る題の速さ（Draft 待ち・レビュー待ち・説明待ちの除去）で、失敗する題の遅さは変わらない。
- 前回（負荷15前後）の `nd_k2_par` は p50 39.5 s だった。今回 40.0 s。負荷が15→11.5に下がっても p50 は動かず、p50 の題では **Lean より モデル生成（直接証明 約50 s の合計）が支配的** な可能性がある。無負荷でないため断定しない。
- 初回成功の +6 題（6→12）は前回（7→13）と再現した。ただし n=14、割れた題8、p=0.070。

## 限界

- n=14、1回、同じ題で再測定しただけ。held-out は開いていない。
- 端末負荷は下がらなかった。無負荷の測定ではない。
- 費用は記録した使用量×リスト単価の推計。`discarded.jsonl`（使われなかった先行呼び出し）US$0.016 を含む。
- ランナーの1回あたり上限は腕ごとに US$0.93。実行全体の累計（両腕＋待機中の探針）が US$1 を超えても、これは腕ごとの上限であり、1回の実行の合計は US$1.46 だった（`run_usd`）。腕ごと（base 0.847、nd_k2_par 0.609）は上限内。**「1回の実行は US$1 以内」を実行全体の合計と読むなら超過。** 確認の上で扱う。

## worker 配線と API の最小の契約

- worker は API の検証器（`api_reconcile`）にコンパイルを任せるため、2候補の競争は worker の preflight でしか選べず、**成功率は上がらない**（速いほうのモデル呼び出しと preflight 失敗の救済だけ）。今回の測定は worker にコンパイラのある `local` モード相当で、本番の `api_reconcile` の数字ではない。
- 成功率に効かせるには、API が省略可能な `alternates`（最大1件）を受け、主候補が失敗したら worker に戻さず alternate をコンパイルする契約が要る（詳細は `pals-agent/docs/t2-lane-followups.md` §4）。未実装。
- 検証器側の取り消しは依存として記録しただけ。
