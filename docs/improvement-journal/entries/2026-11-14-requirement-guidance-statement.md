# 命題に課される要件を生成プロンプトに伝える試み（不採用）（2026-11-14）

- 指標: 意味の審査の承認率、回答が返る割合（Lean 検証かつ承認）、費用、時間。
- 仮説: 「明示的な N」「定義を使え」のような要件を、命題の形式化の段に一般的な指針として伝えれば、意味の審査の却下が減り、回答が返る。
- 変更（pals-agent#135、draft、既定 off のフラグ。審査プロンプトは未変更）: 要件の種類（明示的な証人、指定された定義・方法）を検出し、Draft/Sketch/Prove/Repair の問題文の直後に一般的な指針を足す。
- 測定条件: 全工程（Draft → Sketch → Prove → Lean → 修復 3 回まで → 意味の審査 → 説明）、6 題（要件あり 4、対照 2）× 2 回 × 2 腕。Terra（中）、Luna（低）。負荷のある共有機で 2 腕を並行。推計費用 US$0.402（base）と US$0.577（指針あり）。実行日 2026-11-14。
- 結果: 回答が返る 11/12 → 9/12。意味の審査の却下 1 → 0 だが、定義を指定した題で検証に至らない実行が 3 件（修復 3 回まで）。要件あり 8 件のうち返る 7/8 → 5/8。費用 +43%。壁時計の中央値は 68.6 → 68.7 s（定義の題は 150〜220 s）。
- 判断: **不採用**（draft のまま、マージしない）。main の全工程では、「明示的な N」の題は最初から要件を満たす命題を書き 4/4 承認。却下を減らす効果は 1 件で、検証失敗が 3 件増えた。
- 限界・未確認: n が小さく有意ではない。検証失敗の原因は修復の予算が尽きたためと推測するが未確認。本番の修復上限は別の値。
- 次にやること: 却下理由を渡して 1 回だけ形式化をやり直す形（[契約案](../../semantic-review-rejection-contract-2026-11-14.md)の (b)）。API 側の対応が要るため別作業。
