## 1. 方針の変更と、その影響

ユーザーの決定により、人手でレビューされていない StacksFrontier（AI 生成）の定義を、命題の側でも使えるようにする。前回までの原則は「命題は Mathlib と StacksCore の定数だけ」だった。

この変更は、検証済みの意味を弱める。AI が書いた定義が、Stacks Project や Mathlib の意味とずれていても、Lean は気づかない。`verified` が保証するのは「書かれた命題が証明された」ことだけである。そのため、次の 3 点で補う。

- 命題が Frontier の定義を使う場合は、信頼レベル `frontier_statement`（Frontier、人手未レビュー）を記録し、利用者に見える形で表示できるようにする。実装は pals-agent の新プロファイル `stacks-frontier-defs-4.35` で、`PALS_LEAN_ALLOW_FRONTIER_STATEMENTS=true` のときだけ動く。既定は閉じている。
- `sorry`、追加公理、`native_decide` は禁止のままにし、カーネルの再検査も必須にする。
- 命題を固定し（`formal_statement`）、検証後に意味審査（独立した LLM セッション）を通す。Frontier の定義が Mathlib と同名・同意で二重化している場合は、検出して記録する（拒否はしない）。

## 5. 成功の定義

1 回の実行が成功となる条件は、次のすべてを満たすことである。

1. カーネル検査: 腕のプロファイルの検証が `verified`。コンパイル、信頼できる監査（カーネルでの再検査）、`sorry`・追加公理・`native_decide` の禁止を含む。
2. 命題の固定: 固定した Lean の命題が、最終ファイルに空白を無視して含まれる（`lean.formal_harness_mismatch` が出ない）。監査が、命題を `bound` と判定する。
3. 意味審査: 本番と同じ `LeanProofSemanticReviewer`（PROOF_REVIEW の既定モデル、最大 2 回の応答）が、抽出した 1 つの宣言について `approved` を返す。`rejected` は、`verified` でも失敗とする。

- 通信エラーなど、モデルの失敗ではない異常で終わった実行は、1 回だけやり直し、両方を記録する。集計には後の実行を使う。
- 修復上限 3 の成功: 上の条件を満たし、かつ `repairs_used ≤ 3`。`repairs_used` は、保存された試行ファイルの数から 1 を引いた値。上限 6 の実行は、途中までの経路が上限 3 の実行と同じなので、上限 3 の結果は、同じ記録から出せる。
- 信頼レベルは、成功した実行ごとに記録する（`mathlib`、`core`、`frontier_proof`、`frontier_statement`）。

## 6. 速さと費用の指標

- 1 枚あたりの時間: パイプライン開始から最終結果までの実時間（生成、検証、修復を含む。検索と意味審査を除く）。意味審査の秒数は別に記録する。中央値と p90 を、(i) 腕ごとの全実行、(ii) 成功した実行について出す。
- Lean の検証時間: 実行中の検証 1 回ごとの秒数を記録し、合計を出す。
- 実行時の負荷: 各実行の開始時の 1 分ロードアベレージを記録する。この機械では他のセッションも動いているため、時間は負荷の影響を受ける。

- 腕 d、c2 は、腕 a、b、c の数字と並べて、改善率や差の倍率を作らない。各カードについて、成功、修復回数、費用、時間、打ち切りの有無を、c、c2、d で並べるにとどめる。
- 腕 d の成功が c より多く見えても、c と c2 の間で同じカードの結果が入れ替わった数（c2 の枚数 n のうち何枚か）を上回らない限り、効果とは書かない。c2 が 5 枚未満なら、成功への効果の判定は保留にする。
- 範囲の拡張が効いたと書くのは、腕 d で成功した実行の最終ファイルが、B' にあって B にないモジュールを import している場合だけ。失敗した場合は、その補題が使われたか（`imports_outside_B`）と、失敗の診断だけを書く。
- 早期打ち切りは、腕 d で止まった実行の数と、止めた時点までの費用と時間を書く。止めなければ成功したかは、腕 d では分からない。この問いは、記録済みの 27 回についての机上計算（[スクリプト](scheme-theory-measurement-early-stop-calc-2026-11-09.py)）で答えており、実験の結果とは混ぜない。
- 速さの基準（中央値 120 秒以内）は、腕 d に対しても同じに置く。
- 腕 a の C01、C02 を足した後の腕 a の成功率は、Wilson 区間を併記し、基準 0.85 との関係を、7 節の規則で書き直す。
- Frontier の読み込み: B と B' のビルド（実時間、CPU、最大メモリ）と、全ハブを import する 1 ファイルの温かい状態での実時間と最大メモリを測り、記録する。外挿は測定と区別する。

### 12.4 運用メモ（次回以降の測定）

- 予算の開始停止の線は、上限から「1 枚あたりの最大費用」分だけ離す。今回の第 2 予算は、線（3.85 ドル）の手前（3.807 ドル）で F04 の c2 を始め、その実行の途中で上限 4.0 ドルを 0.023 ドル超えた。ハーネスは各リクエストの前に累計を見るため、最後の呼び出しの費用が超過分になる。1 枚あたりの最大は、今回の実績で約 0.8 ドル（最大 0.83 ドル）。したがって、線は上限 − 0.9 ドル程度に置く（上限 4.0 なら 3.1 ドル）。
- 生成の費用と審査の費用は、別の計量器で数えている。生成が上限の直前で検証に通ると、審査の呼び出しが上限を超える場合がある。次回は、生成と審査の合算で判定する。リクエストの途中で上限に達する超過は、合算でも防げない。
- 応答に使用量（usage）が含まれない場合、ハーネスは 0 トークンとして数える。保存した 41 行（試運転を含む）は、入力・出力トークンがすべて正で、使用量の欠落は個別には確認できていない。欠落があれば、費用は下限になる。次回は、使用量の欠落を検出して以後のリクエストを止める。
- 記録する項目は、実行前に決めたものをハーネスに実装してから走らせる。第 2 予算では `imports_outside_B` と `stopped_early` が実装されておらず、事後に計算した（結果文書 10.6 節）。
