# Lean 再検証を避ける方針 Phase 0 測定 2026-11-07

「検証済み補題を再コンパイルしない」方針で、短縮の上限がどこにあるかを測りました。ローカルの 1 台の Mac での測定で、AWS 本番の値ではありません。モデル呼び出しはなく、費用は0です。

## 結果

### 1. Lean の時間は elaboration ではなく、起動と import が占めます

PALS 固定版（Lean 4.32.0-rc1）で、`lake env lean` を各3回実行した中央値です。

| ファイル | `lake env lean` | `lean` 直接 |
|---|---:|---:|
| import なし（`example : True`） | 1.79秒 | 0.41秒 |
| `Mathlib.Algebra.Group.Basic` のみ | 2.48秒 | 1.17秒 |
| `Mathlib.RingTheory.Ideal.Operations` のみ | 3.48秒 | 未測定 |
| `import Mathlib` | 8.03秒 | 7.16秒 |
| カード43件（`calculus-v5-batch`、`import Mathlib`） | 9.67秒 | 8.83秒 |
| カード31件（`commalg-v3-batch`、`import Mathlib`） | 11.42秒 | 未測定 |

- カードの elaboration は、全体から `import Mathlib` を引くと1件あたり約40ミリ秒（calculus）〜110ミリ秒（commalg）です。
- `lake env` の起動だけで0.9〜1.4秒かかります。本番の検証器は `["lake", "env", "lean", "--threads=1", "Main.lean"]` で起動しています（`pals_agent/lean_verifier/http_server.py`）。環境再利用フラグ（`PALS_LEAN_REUSE_LAKE_ENVIRONMENT`）の中央値約1.2秒の短縮と、大きさが一致します。
- 狭い import ＋ `lean` 直接なら約1.2秒です。残りは、プロセスの下限0.4秒と import 0.8秒です。

つまり、補題を型だけのスタブに替えて import を省いても、狭い import からの上乗せ短縮は 1 秒程度です。証明を検証する時間は、全体の誤差の範囲です。

### 2. 証明の形（既存カード744件、静的分類）

| 形 | 件数 | 割合 |
|---|---:|---:|
| 単一の `exact` 引用（自動化なし） | 430 | 57.8% |

| 自動化なしの複数手順 | 109 | 14.7% |

分類は正規表現による粗いものです。対象はカタログ用に選ばれたカードで、利用者が実際に出す依頼の分布ではありません。

全体139〜449秒のうち、モデル呼び出し98〜360秒、Lean 検証12〜29秒、Lean 結果のポーリング待ち14〜39秒です（[詳細](answer-path-latency-tracing-2026-11-02.md)）。

- 本番（AWS）での起動時間と import 時間。

## 判断

- スタブ検証（層2）による Lean の短縮は、狭い import ＋ 起動の見直しを超える分が約1秒です。信頼境界の複雑さに見合いません。見送ります。
- 先に効くのは、`lake env` を避けること（環境再利用フラグの有効化）と、ポーリングの廃止です。どちらも新しい信頼境界を作りません。
- 層1（型ハッシュによる文の照合）は、Lean の短縮ではなく、Stacks などの大きなライブラリを**索引として**使うための手段として別に評価します。
- 修復の原因を記録する項目を足してから、補題検索への投資を判断します。
