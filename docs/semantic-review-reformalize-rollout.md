# 意味の審査の作り直し: 有効化の手順と危険（`PALS_SEMANTIC_REVIEW_REFORMALIZE_ENABLED`）

1. 前提: 有効化する候補ではpals-api#108の作り直し機構と、[#124](https://github.com/AtsushiHosaka/pals-api/pull/124)の設定・期限保持を含むAPIを、必要な検証後に署名リリースで配備する。フラグは既定offを維持する。作り直し機構自体のためのworker変更はない。有効化は、APIのランタイム環境に`=true`を足す署名リリースとして固定する。
2. 動作: 最初のLeanジョブが意味の審査で不合格になったdsp依頼に、新しいジョブを1つ作る。元のmodelと保存済みreasoning effortを保持する。ゲスト・後続ジョブ・最初のジョブの実行が600秒超の依頼は対象外。未検証の期限が有効なら、元のquota/token admissionからの経過時間が「期限−150秒」を超える依頼も対象外であり、job作成からの経過時間で期限を延長しない。2回目の不合格は従来どおり失敗。
3. 費用: 却下された依頼だけ、1 回分の生成費用が増える（約 US$0.04〜0.07/件。要件指定の題では全体で +27%）。却下されない依頼は変わらない。却下率の本番値は未確認（回帰セット: 要件指定の題 3/12、一般の題 1/12）。
4. 時間: 却下された依頼の回答が約 +100〜160 秒。本番の p90 877 s の依頼は 600 秒ガードで対象外になりうる。
5. 画面: 作り直しの間は`verifying`のまま。現行Web候補`aa1a6d4`はrequest.created_atから経過時間を表示するため、同じ依頼の新jobで0に戻さない。最終失敗の理由表示は[#382のWeb候補](https://github.com/AtsushiHosaka/pals-webfront/pull/94)で意味審査の不合格と利用不可を区別する。表示変更とflag有効化の配備・受け入れは別に確認する。
6. 監視: `failure_reason=semantic_review_failed` の件数、`proof_request_lean_jobs` が 2 件の依頼数（作り直し率）、作り直し後の `answered` 率、依頼の所要時間 p50/p90、依頼あたりの生成費用。
7. 判断の目安: 有効化後 1 日、作り直し後の `answered` 率が低い、または費用の増分が想定（却下件数 × 約 US$0.05）を超えるなら戻す。
8. 戻し方: 環境変数を外す（または `false`）署名リリース。進行中の作り直しジョブは通常のジョブとして完了し、新たな作り直しは起きない。DB 移行はなく、データの巻き戻しは不要。
9. 注意: 旧版 API へ戻す場合は、保存済みの `lean_semantic_review_*` が公開の `error_code` に出る（pals-api#106）。画面が未知のコードをどう表示するかを、戻す前に確かめる。
10. 根拠: [測定と設計](improvement-journal/entries/2026-11-14-semantic-review-reformalize-job.md)、pals-api#108、pals-agent#137、[2026年11月18日の実装候補と未確認範囲](382-answer-quality-candidate-2026-11-18.md)。費用・時間の数値は過去の測定で、今回の候補や本番の改善率として再計算していない。
