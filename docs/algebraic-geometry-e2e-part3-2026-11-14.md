# スキーム論の質問、第3回: 同値の質問、検証環境の振り分け、Stacks 環境の用意、30 秒の指標（2026-11-14）

[第1回](algebraic-geometry-e2e-2026-11-14.md)、[第2回](algebraic-geometry-e2e-part2-2026-11-14.md)の続き。修正は pals-agent#136、API 側は pals-api#107（どちらもマージ済み、配備なし）。

## 利用者にとって何が変わるか

- 「Spec R が連結 ⇔ 冪等元が 0, 1 のみ」のような、スキームの性質と環の性質の同値の質問で、同値の両方向が示されるようになった。連結性の題は、第 1 回で、修正の前（部分命題）も後（部分命題でレビュー却下）も通らなかった題である。新しい 4 題（v3）では、依頼どおりの通過が 1/4 → 4/4。
- 層のコホモロジーなど Mathlib に概念が無い質問を、Stacks の Frontier を含む検証環境へ振り分ける判断が、コードとして存在するようになった（質問から選ぶ関数。既定 off、ローカル検証のみ）。それまで、worker には検証環境を選ぶ処理が無かった。
- Stacks 用の検証環境を、この Mac でビルドできることを確かめ、起動・import・検証の時間を測った。

## 1. 同値の質問を両方向で述べる（pals-agent#136）

連結性の失敗は、質問を「スキームの性質 ⇔ 環の性質」の 1 つの定理として述べず、複数の事実の連言（コンパクト性 ∧ 冪等元の補題）や代数補題だけを証明していたことが原因だった（第 1 回）。一般的な手当てとして、スキーム論の質問に同値の cue（if and only if、iff、equivalent、同値、⇔ など）があるとき、案内に次を足す。

- 命題は `A ↔ B` の 1 つの定理で、両辺は質問に書かれた 2 つの性質そのものにし、両方向を証明する。連言、片方向、環だけ・空間だけの補題にしない。
- スキームと環の橋渡しは `have` で明示する。名前は、ピン留めした Mathlib で存在を確認したものだけ: `PrimeSpectrum.isIdempotentElemEquivClopens`、`connectedSpace_iff_clopen`、`isClopen_iff`、`isPreconnected_iff_subset_of_disjoint`、`PrimeSpectrum.irreducibleSpace_iff_isPrime_nilradical`、`affine_isIntegral_iff`、`affine_isReduced_iff`。
- 質問が空でない環を仮定しているときだけ `[Nontrivial R]` を置く（空の空間は連結ではない）。
- 圏の同値の質問や、`formal_statement` で命題を固定したときには付けない。

### 測定（v3、4 題、各 1 回）

評価の区分 `algebraic-geometry-v3`（pals-agent）: 連結性、既約性（冪零根基が素イデアル）、空（零環）、被約。条件は第 1 回と同じ（worker と同じ生成の経路、本番の役割割り当て、Lean v4.32.0-rc1、修復は最大 6 回）。

| 題 | 修正前（#134 まで） | 修正後（#136） |
|---|---|---|
| Spec R は連結 ⇔ 冪等元が 0, 1 のみ | 修復 6 回で失敗、699 秒 | 通過・承認、修復 5 回、708 秒 |
| Spec R は既約 ⇔ 冪零根基が素イデアル | 修復 6 回で失敗、553 秒 | 通過・承認、修復 1 回、152 秒 |
| Spec R が空 ⇔ R が零環 | 通過（初回）、104 秒 | 通過・承認、修復 1 回、232 秒 |
| Spec R は被約 ⇔ R が被約 | 修復 6 回で失敗、630 秒 | 通過・承認、初回、57 秒 |

| 指標 | 修正前 | 修正後 |
|---|---|---|
| 依頼どおり（通過かつレビュー承認） | 1/4 | 4/4 |
| 初回成功 | 1/4 | 1/4 |
| 回答完成 p50 / p90 | 592 / 678 秒 | 192 / 565 秒 |
| 費用（合計） | 0.92 ドル | 0.38 ドル |
| 30 秒以内の題 | 0 | 0 |

- 連結性の題は、第 1 回までの失敗（部分命題）が、定理文としては `ConnectedSpace (Spec (CommRingCat.of R)) ↔ ∀ e, e^2 = e → e = 0 ∨ e = 1` の 1 つの定理になった。ただし修復 5 回、708 秒かかっており（修正前の失敗は 699 秒）、この題については、通るようになった、であって速くなった、ではない。
- 実行の順序: 修正後が先、修正前がその直後の同じセッションで測った。修正後の実行は、StacksCore のビルド（重い処理）と一部（クローン・キャッシュ取得と、ビルドの最後の約 2 分）が重なり、負荷の影響を受けた。修正前は負荷の上限 10 で待ってから実行した（修正後は 40）。時間の比較は参考値にとどめ、通過の件数だけを結果とする。
- n=1、4 題。第 2 回までの連結性の失敗が、この案内で直ったのか、ばらつきなのかは、1 回の測定では区別できない。ただし 3 題が修正前の失敗から通過に変わった。

## 2. Stacks 用の検証環境を、手元で用意できるか

結論: 用意できる。Docker は使わず、この Mac の Lean v4.35.0 で、既存の `lean-workspaces/stacks-4.35`（lakefile と manifest のピン）のとおりにビルドした。リポジトリの作業コピーは汚さず、`~/ag-eval-out/stacks-ws/`（リポジトリの外）に置いた。

| 工程 | 時間 |
|---|---|
| Stacks のクローン（Frontier を外したスパースチェックアウトを含む） | 約 25 秒（端末の `time` 出力。記録ファイルは残っていない） |
| `lake exe cache get`（Mathlib のキャッシュ 5784 ファイル） | 21〜64 秒（上限は `build.log`、下限は端末の出力） |
| `lake build StacksCore`（4758 ジョブ、Mathlib はキャッシュから） | 116 秒 |

- 詰まった点: 初回に、Lake が `lake exe cache get` の中で Stacks をクローン・チェックアウトする最中に `fatal: unable to write new index file` で失敗した。そのあと Lake が Mathlib をソースからコンパイルし始めたので止めた（自分で起動したプロセスだけを指定して止めた）。原因は未確認。手作業でクローンしてスパースチェックアウトし、固定のコミットに合わせると通った。Dockerfile の手順は、Lake が内部でクローンする前提なので、この失敗に弱いかもしれない（未確認）。
- 検証環境のソースの `StacksFrontier` は、スパースチェックアウトで取り除いた（`test ! -e StacksFrontier` で確認）。

### 起動・import・検証の時間

同じ定理（`CompactSpace (Spec R)`、`inferInstance` の 1 行）を、検証器（`LeanVerifier`、信頼済み監査を含む）に 3 回通した値（import の行だけが違う 2 つのファイル）。表の値は 3 回の中央付近の値で、実測は、既定が [8.39, 8.28, 8.30] 秒と [4.85, 5.25, 4.99] 秒、Stacks が [24.16, 9.97, 9.93] 秒と [6.28, 6.19, 6.25] 秒。Mac の負荷は 7〜12 で、他の作業と共有。実行の記録ファイルは残していない（端末の出力のみ）。

| 環境 | `import Mathlib` | `import Mathlib.AlgebraicGeometry.AffineScheme`（絞った import） |
|---|---|---|
| 既定（`mathlib-4.32`、Lean 4.32） | 8.3 秒 | 5.0 秒 |
| `stacks-4.35`（Lean 4.35） | 初回 24.2 秒、2〜3 回目 9.9 秒 | 6.2 秒 |

- Stacks 環境の定常の 1 回は、既定より約 20% 遅い（9.9 秒 対 8.3 秒）。初回の 24 秒は、4.35 の Mathlib の olean がページキャッシュに無かったためだと考えている（キャッシュを冷やして比べる確認はしていない）。
- import を絞ると、どちらの環境でも約 40% 縮む（約 3.5 秒）。1 回の回答で検証は 2〜3 回なので、合計で約 7〜10 秒の短縮になる。`lean_import_plan`（既存の、既定 off の import 計画）が、この絞りの仕組みである。ただし 30 秒の目標に対しては、Sketch の省略に比べて効果が小さい。
- Frontier を含む環境（`stacks-frontier-4.35`）は、今回ビルドしていない。必要なモジュール（層のコホモロジー）の閉包は 75 モジュールで、第 2 回の前の測定（2026-11-08）では、ビルド前検査（`audit_frontier_closure.py`）が 15 モジュールを拒否した（属性 `implicit_reducible`、`instance_reducible`、`no_expose`、`attr` など）。許可する属性を増やす判断（命題の意味に影響しない属性かの確認）が先に要る。本番の画像に入れる判断と同じく、私が決めない。

## 3. 層のコホモロジーなどの振り分けが働くか

結論: 働いていなかった。原因は 3 つで、1 つ目だけをコードで直した。

1. worker に、質問から検証環境を選ぶ処理が無かった。`ProofPipeline.run_statement` は `library_profile` を受け取るが、呼び出し側は渡さない。`build_profile_verifiers` は定義だけで、どこからも呼ばれていない。
   - 修正（pals-agent#136）: `profile_selection.select_library_profile` が質問から選ぶ。スキームや層の文脈があり、層のコホモロジー・高次順像・導来関手なら `stacks-frontier-4.35`、Picard 群・豊富な層・可逆層なら `stacks-frontier-defs-4.35`、それ以外は既定（選ばない）。`ProofPipeline.route_library_profile`（既定 off、ローカル検証のみ）で使い、選んだ環境が提供されていなければ `LibraryProfileNotEnabled` で拒否する（既定のライブラリに暗黙に退避しない）。
   - 評価の 25 題（v1〜v3）に適用すると、選ばれるのは層のコホモロジーの 1 題だけで、残りは既定のまま。
   - 独立レビューが、選んだあとに再び選び直して必ず失敗するバグ、非スキームの質問（群のコホモロジー、グラフの acyclic など）への誤検出を見つけ、直した。
2. 本番の worker は検証せず、API 側の検証器（`api_reconcile`）が検証する。その検証器は 1 つのプロファイル（既定）だけを提供している。worker が環境を選んでも、API の検証がそれを受け取る仕組みが無い。これは API と検証器の配備の契約変更で、配備を伴うので案としてのみ書く。
3. Frontier の閉包が検査を通らない（上記）。

したがって、層のコホモロジーの質問が本番で検証済みの回答になるには、(2) と (3) の判断が要る。今回の測定では、ローカルでも Frontier の環境で検証した回答は作っていない（ビルドしていない）。

## 4. 信頼水準（library_trust）の契約と API 側の変更

契約の正本は [library-trust-contract-2026-11-14.md](library-trust-contract-2026-11-14.md)。API 側の変更は pals-api#107（マージ済み、配備なし）。

- `GET /v1/proof-jobs/{id}/status` に `library_trust`（検証済みならオブジェクト、それ以外は null）を足す。水準は、検証器の診断だけから作る（ジョブに保存された診断は worker 由来がありうるので使わない）。
- フラグ `PALS_LIBRARY_TRUST_FIELD_ENABLED`（既定 false）。無効のときは、応答の本文、DB、保存内容が従来と同一。スキーマの変更は無い。
- 注意（PR の独立レビューと私の確認）:
  1. この変更だけでは、`frontier_*` は出ない。検証器の成功応答（attestation）は閉じた形で診断を持たず、失敗時の診断も `lean.library_trust` を許さない。出すには、検証器側の変更、attestation 検証の拡張、`proof_jobs` への nullable 列の追加が要る（pals-infra の契約変更を伴い、配備しない）。今は検証済みが常に `mathlib`、`recorded=false`。
  2. 対象の面は status だけ。詳細、一覧、SSE、チャット回答には足していない。画面がどの面で読むかは未確認。
  3. 配備済みの web クライアントは未知のキーを拒否する。フラグの有効化は、画面が受け入れてからにする。

## 5. 30 秒以内の題数（主な指標に追加）

回答完成（`answer_s`）が 30 秒以内の題数と、そのうち依頼どおり（通過かつレビュー承認）の題数。

| 評価・経路 | 題数 | 30 秒以内 | 60 秒以内 | 30 秒以内かつ依頼どおり |
|---|---|---|---|---|
| v1 修正前 | 10 | 0 | 0 | 0 |
| v1 修正後 | 10 | 0 | 2 | 0 |
| v2 修正前 | 11 | 0 | 1 | 0 |
| v2 修正後（既定） | 11 | 0 | 4 | 0 |
| v2 修正後 + T2 経路 | 11 | 3 | 6 | 2 |
| v3 修正前 | 4 | 0 | 0 | 0 |
| v3 修正後 | 4 | 0 | 1 | 0 |

30 秒を満たすのは、Tag を名指しして Mathlib に補題がある題を T2 経路（Sketch を省く）で測った 3 題だけで、そのうち依頼どおりなのは 2 題。一般の題で 30 秒を満たすには、Sketch の省略に加えて、補題の発見（Tag を名指ししない質問への引きの拡張）と、修復の見直しが要る。

## まだ通らない題と次に効く対策（優先順）

1. 層のコホモロジー（高次順像の消滅）: 振り分けの判断は入った（上記 3 の 1）。残りは、API の検証器が環境を受け取る契約（配備を伴う案）、Frontier の閉包を検査に通す判断、Frontier 環境のビルドと時間の測定。
2. 30 秒: Sketch を省く T2 経路の有効化（別の作業の判断）と、Tag を名指ししない質問への補題の引き。
3. 自称しない部分命題（基本開集合の切断が大域切断の同型にすり替わる例）: 固定した形式化で縛る。意味レビューが現状の唯一の防御。
4. 意味レビューのぶれ（正しい命題の誤却下）。審査プロンプトは対象外。
5. import の絞り（`lean_import_plan`）の有効化: 1 回の検証が約 3.5 秒短くなる。

## 限界

- 各題 1 回、n が小さい（v3 は 4 題）。
- 「依頼どおり」は、意味レビュー（モデル）の承認による。
- v3 の修正後の実行は、StacksCore のビルドと一部が重なった（修正前は直後の実行で、負荷の上限が違う）。時間の比較は参考値。
- Frontier を含む環境のビルドと、そこでの検証は行っていない。
