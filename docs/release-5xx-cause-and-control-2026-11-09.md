# リリース中の5xx通知の原因と対策

添付通知に加えて後続の受信メール二通を確認したところ、三通とも、リリース処理が唯一のALB接続先を外していた時間帯と一致しました。最初の区間では、接続先を外した後に実行中ジョブの停止待ちが続き、再び正常な接続先を確認するまで約8分半かかっていました。今回のローカル試験や、以前の通知専用テストが、添付通知を起こした証拠はありません。

添付されたのは、HTTP 500だけを数える通知ではありません。`pals-prod-incident-alb-5xx-observed`は、ALB自身と接続先アプリの5xxを合算します。直近3つの1分区間のうち、一つでも1件以上あれば通知する設定です。ALBのディメンションしか持たず、利用者・内部テスト・監視・botの内訳は分かりません。[確認した定義](https://github.com/AtsushiHosaka/pals-infra/blob/52c9c3f2a8bf58ee436f9f67373b510e9291169c/terraform/incident-alerting/main.tf#L161)

登録解除から正常確認までは約8分31秒です。これは操作記録から求めた区間で、利用者一人ひとりの待ち時間ではありません。接続先がなくなると、ALBは新しい要求を転送できず503を返します。120秒のdrainingは既存の通信を待つ設定で、新しい通信の受け口を維持する設定ではありません。[AWSの503の説明](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-troubleshooting.html)、[登録解除の動作](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-register-targets.html)

drainが実行中ジョブを検出して停止を拒否したこと自体は、安全のための動作です。問題は、その前に公開容量を0にしていた順序と、拒否が続く間も停止状態が長引いた点にあります。改善済みの切替実行器は、事前検査が通る前の登録解除を防ぎ、解除後の失敗では安全に復旧できる状態かを独立して確認します。[切替修正](https://github.com/AtsushiHosaka/pals-infra/pull/108)

実行中ジョブ数を公開停止前に読み、待つか延期する事前drain確認は、正規実行器へまだ接続していません。停止後の確認は安全のために残す必要があります。今回追加する通知制御を、この可用性改善の完了とは扱いません。

当該1分の全5xxが503だったか、どの要求が内部テストだったかは未確定です。AWS SSOの期限切れで、今回の新しいCloudWatch内訳やアクセスログは取得できていません。保存済みの時刻相関を、個々の要求の完全な原因特定や現在の稼働確認へ広げません。

## テストはどこを通るか

| 種類 | 本番5xxへの影響と今後の扱い |
| --- | --- |
| ローカルの故障注入・回帰 | loopback内だけで実行。通信断もブラウザ内のabortで起こす。本番ALBは通らない |
| リリース前の回答受入 | 承認済みのローカル実DB・実Lean・実モデルを使う。完了・保存・表示・再読込が未達なら切替を止める |
| 通知専用テスト | 既存の別namespaceと専用アラームを使う。本番HTTPや本番の失敗メトリクスへ人工的な障害を入れない |
| 本番の公開監視・評価 | 実際にALBを通り、停止中の応答を観測すれば5xx件数へ加算される。通知の原因と、停止を作った原因を分けて記録する |
| 配備後の本番受入 | 健康確認と公開経路復旧後に、承認済みアカウントの一件で回答完了・保存・再表示まで確認する |

通知専用テストは11月6日、`PALS/IncidentNotificationProbe`の`DeliveryProbe`で行い、専用アラームは回収済みです。今回のローカル試験は通知の後に始まっており、時系列からも原因にはなりません。[通知テストの記録](incident-notifications-2026-11-06.md)、[ローカル試験の記録](local-release-qualification-2026-11-09.md)

本番にテスト専用URLを足すだけでは、共有する接続先が0になる問題は直りません。故障注入は上記の別経路に保ち、本番の確認には同じ認証・保存・表示の経路を使います。他チャットの公開評価が当該時刻に動いていたか、残っていたclaimがテスト用か利用者用かは未確認です。今回は他者の評価処理を停止・変更していません。

## リリース時の通知をどう扱うか

通常時の検出条件は維持します。予定した切替に限り、この5xxアラーム一つの通知を、一回限りの短い窓で抑える処理を追加します。CloudWatchの評価と生メトリクスは残し、他のアラームは対象にしません。

手動で`disable-alarm-actions`を実行し、最後に戻す方式は使いません。処理が落ちると戻し忘れが起こり、再有効化時にも継続ALARMの通知を取り逃す可能性があるためです。AWSの一回限りのmute ruleを使い、開始・終了時刻と最大10分の期限を固定します。AWS側で失効するため、実行器が停止しても通知抑制が残り続けません。期限後にも障害状態が続けば、抑制されていた通知が再実行されます。[AWSのmute rule](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-mute-rules.html)

実行器は、候補に結び付けた通知用UUID・対象アラーム・期限を照合し、AWSでACTIVEと確認するまで公開接続先を外しません。実際のリリース所有権は、既存のnative claimとadmissionの検査で別途確かめます。失敗時は早期解除を試みます。正常復帰後に残すメトリクス遅延用の猶予も最大3分で、元の期限を延長しません。事前から障害中のアラームを黙らせたり、期限が来るたびに自動延長したりする処理にはしません。通知の期限切れが安全な復旧そのものを妨げないよう、不可逆なDB切替後の候補の復旧と、通知の制御を分けます。

この変更は通知の扱いを整えるものです。現在のDB切替は全クライアントの停止を要求し、API・Web・Caddyも入れ替えるため、切替中の503を完全になくすものではありません。無停止化には、旧版と新版を同時に動かせるDB・admission・認証の互換設計と、その実検証が必要です。メンテナンスをHTTP 200で成功に見せる変更も行いません。
