# 障害通知の要件

2026年11月6日のオーナーの追加依頼は、今回の障害の再発防止と、発生時に本人が気づける通知環境の整備である。既存の品質監視仕様が通知を対象外としていた方針を、この通知範囲について更新する。品質計測全体の実装や受入条件を置き換えない。進行は既存Issue #217、今回の障害は#223で追う。

| ID | 要件 |
|---|---|
| INA-001 | 本番computeの説明生成の最終失敗ログを、直近5分に観測したかのbooleanとして1分ごとに監視する。確定したDB終端件数、要求の総失敗数、数学的な精度とは呼ばない。 |
| INA-002 | 1件の観測でも通知する。少数の利用で率の最小標本数に届かなくても通知を抑制しない。目標はログ出力から数分以内で、AWS障害や配送遅延時の即時到達を保証しない。 |
| INA-003 | 監視に必要な読取が失敗した場合は正常の0を送らない。定期処理やメトリクス発行の停止による欠測も別アラームで通知する。SNS以降の配送障害をheartbeatだけで検知できるとは扱わない。 |
| INA-004 | 質問、回答、Lean、診断本文、利用者、IP、要求ID、資格情報を外部へ送らない。observerが外へ送る測定値は固定3メトリクスの0または1だけとする。ALBの既存ネイティブメトリクスと、固定した監視設定・配送経路の管理情報は別に扱う。 |
| INA-005 | 本番3actorのhealthと、既存ALBの正常なtarget不足・HTTP 5xxを別に監視する。既存コンテナ、アプリ、DB、ネットワーク、復旧設定を変更したり自動再起動したりしない。 |
| INA-006 | 既存の確認済みPALS用メール購読へCloudWatchアラームを接続し、テスト通知の受信箱到達まで確認する。メール受信と端末の音・バナー表示は区別する。 |
| INA-007 | 失敗観測が5分窓から消えたことを、数学回答の復旧と通知しない。同じALARM状態中の追加観測で通知を連発しない。 |
| INA-008 | 新規Terraform rootで5アラームとhost専用のnamespace限定発行権限を管理する。既存SNS購読、既存アラーム、他state、ワーカー権限を変更しない。 |
| INA-009 | 追加月額を公式の東京料金で見積もり、メトリクス数やディメンションを固定する。定期的な有料モデル実行は行わない。 |
| INA-010 | 実際の保存済み失敗ログの読取、実メトリクス、監視タイマー、ALBの実dimension、独立した通知用probeの実ALARM遷移、メール受信、probe回収を受け入れ条件にする。本番障害を注入しない。 |

説明生成の修正配備と同一質問の公開受入は#223で別に追う。通知の検証完了を、数学的な復旧、Recipeの正規公開、品質collectorを含むPQO全体の完了とは扱わない。一般のLean失敗と個別ジョブの停滞は網羅せず、電話端末の音・バナー表示は未検証とする。

実配備と通知経路の証跡は[通知検証記録](../../docs/incident-notifications-2026-11-06.md)にまとめる。メールの受信箱到達は確認済みだが、継続的な配送保証やすべての障害の検知率を測定したものではない。
