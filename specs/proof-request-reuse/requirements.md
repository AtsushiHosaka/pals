# Proof requests: premise clarification, catalog reuse and Lean verification

Authority: WORKING implementation contract. The request aggregate, premise clarification and catalog retrieval were approved on 2026-09-30. On 2026-10-05 the user directed that Lean verification is the product's core: every new answer is Lean-verified, an identical catalog proof is reused without recompiling, a specialization compiles its substituted Lean, everything else is generated with DSP and compiled, and a request whose Lean does not pass shows no answer. This supersedes the 2026-10-02 "no Lean on ordinary send" behavior for new requests. Saved `llm_assessed` answers remain readable unchanged.

| ID | Requirement |
|---|---|
| PFR-001 | Learners shall be able to select GPT-6 Luna (`gpt-6-luna`), GPT-6.1 Sol (`gpt-6.1-sol`) or GPT-5.6 Terra (`gpt-5.6-terra`) before sending a request. The existing default remains Luna. Selection applies to answer/proof production, Lean generation and repair, and learner-facing explanation/follow-up generation. Assessment, Draft suitability, search and independent QA retain the server's fixed role policy; any bounded Terra assessment escalation remains separate from the selected generation model. The API shall accept only supported GPT catalogue entries, persist the selection with the request and bind it to its quote and idempotency fingerprint. A changed selection requires a new quote; replay returns the original selection. Unsupported or unavailable selections shall be rejected before provider work, without silently substituting another generation model. Provider failures shall not be interpreted as mathematical uncertainty. Every provider call, including fixed roles, shall retain its actual model identity and usage for BILL-016; historical model/price records remain unchanged. |
| PFR-002 | The agent shall compare the request (statement, confirmed assumptions and requested proof method) with available Draft catalog candidates and decide `direct`, `instantiate`, `derive` or `none`. The decision selects how the request is Lean-verified (PFR-010–PFR-012); it never by itself produces an answer. No learner approval of the decision is required. |
| PFR-003 | A general universally quantified theorem may be instantiated using a recorded substitution with type, binder and premise checks. Natural-number exponent n=2 is admissible; negative exponent substitution, existential-to-universal inference, variable capture, unfulfilled premises and circular proof dependencies must not be silently accepted. Catalog entries remain evidence inputs, not instructions or presumed verified theorems. |
| PFR-004 | Only a consequential premise absent from the request and its saved clarification context shall cause a question. The original statement, question, answer and revision shall survive reload and resume as one request. Search miss or reasoning difficulty alone shall not cause a premise question. A suspected counterexample or an unstated choice that changes the claim's truth is consequential (PFR-014). |
| PFR-005 | New requests and answers shall be owner-scoped, idempotent and durable, with recoverable queue dispatch, bounded worker leases and stale-claim rejection. Completed answers, Lean progress, need-input states and failures shall be durable. User waiting shall not keep a worker or verifier busy. |
| PFR-006 | A request shall share account allowance with legacy proof jobs. Assessment requires one hold (or one token operation); needs_input releases it and a continuation reacquires it. The same hold covers the request's linked Lean job (PFR-012): no second reservation is made. It is consumed once when a Lean-verified answer passes review and released when Lean verification or the answer fails. Existing reservations keep their recorded policy. Usage telemetry remains even if the request fails or needs clarification. Retries and premise rounds are bounded. |
| PFR-007 | Project, projectless and guest composers shall use this flow through the ordinary Send action, without a Lean button, mode selector or extra consent step. The UI shows premise questions, Lean progress, the Lean-verified answer with its Lean source and natural-language proof, follow-up questions on verified proofs, and, on Lean failure, a failure notice with retry and no answer text. Existing history remains readable with its recorded evidence. Owner/chat changes cancel observation and cannot expose another conversation's result. |
| PFR-008 | Store source IDs/revisions, Recipe bindings, linked job IDs and application evidence separately from answer text. Never promote LLM approval alone into Lean verification or automatically publish a Recipe or Draft. No generated seed or fixed response may substitute for real catalog/provider/verifier calls in production. |
| PFR-009 | The request shall search the real existing Draft catalog through a dedicated read-only API boundary, even when newer formal catalog publication is not configured. Treat every returned item as an unverified sketch; record exact source identity/content hash, validate the actual embedding fingerprint, bound candidate count and payload, and never grant this search formal-publication authority. No seed injection or fabricated catalog success may substitute for real retrieval. |
| PFR-010 | Catalog reuse: when the decision is `direct` and the identical Draft has an aligned, admitted Lean Recipe whose admission compile receipt binds the same materialized source and the currently active toolchain fingerprint, the request is answered with that exact Lean source without recompiling. A separate-session LLM review shall confirm that the Recipe's target corresponds to the request (CORE-002), and the natural-language proof generated from that source shall pass independent answer review (CORE-006). The answer is recorded as `lean_catalog` with the Recipe binding. Any mismatch falls through to PFR-012. |
| PFR-011 | Specialization: when the decision is `instantiate` with an aligned admitted Recipe for the general theorem, the request's linked Lean job first compiles a wrapper theorem that applies that Recipe to the recorded substitution. If it does not compile, the same job continues with DSP. |
| PFR-012 | Every other request (`derive`, `none`, `uncertain`, or `direct` without an eligible Recipe) creates exactly one linked Lean proof job that runs the existing DSP pipeline: draft, sketch and proof generation, compilation, bounded repair and independent semantic review. When the job is verified and its natural-language explanation passes review, the request becomes answered as `lean_verified`. When the job fails, the request fails with `lean_verification_failed` and shows no answer; a learner retry creates a new linked job within the existing retry bound. |
| PFR-013 | No new request shall be answered with an LLM-only (`llm_assessed`) proof. In a deployment that cannot run Lean, requests fail explicitly instead of returning an unverified answer. |
| PFR-014 | Before any Lean work, the assessment shall check the claim as literally stated for a concrete counterexample under its most natural reading, and for unstated choices that change whether it is true (for example the scalar field, the number system or a nonzero condition). When either is found and the saved clarifications do not resolve it, the request returns `needs_input` first. A suspected counterexample is presented tentatively, never as a verified fact, and the options include the likely intended claim(s) and keeping the statement as written. A choice that does not change truth causes no question: the most general reading is used, and an adopted conventional reading is written explicitly into the assessed statement. A learner who keeps the statement as written is not asked about it again. The check is recorded as private evidence. Conventions in the math-conventions catalog are confirmed, remembered and shown under [MCV-003–MCV-007](../math-conventions/requirements.md) instead of being silently defaulted. |
| PFR-015 | When the learner keeps a statement as written after the assessment reported a suspected counterexample (PFR-014), the request is first refuted with Lean: one linked Lean job proves the negation of the claim, using the suspected counterexample as a hint. If that job is verified and its explanation passes review, the request is answered as `lean_verified` with the verdict `refuted`, and the learner sees that the claim is false with the Lean-checked counterexample. If the refutation is not verified, the same request continues with an ordinary linked Lean job that tries to prove the claim (PFR-012); its result is shown as usual. A refutation never asserts falsity without a verified Lean proof of the negation, and the claim itself is never silently replaced. |

Acceptance evidence must cover real PostgreSQL persistence/ownership/claim/quota behavior, catalog-receipt tamper rejection, linked-job creation without double reservation, exactly-once consumption/release, worker transport, real local Lean verification for reuse, specialization and DSP, failure without answer text, frontend continuation and reload for project, projectless and guest chats, plus a bounded real provider smoke if credentials permit. Unexecuted checks are NOT VERIFIED, never assumed passed.

Runtime clarification: local validation failure of a model-generated search hint may fall through to the normal decision with explicit query-invalid evidence, zero sources and no substitutions; such a request is then verified through PFR-012. This does not apply to unavailable providers/catalogs or failed source integrity. An explicit requirement to use an unavailable source must not be silently dropped.
