# Proof requests: premise clarification, catalog reuse and Lean verification

Authority: WORKING implementation contract. The request aggregate, premise clarification and catalog retrieval were approved on 2026-09-30. On 2026-10-05 the user directed that Lean verification is the product's core: every new answer is Lean-verified, the verified Recipe catalog is searched first by mathematical content, a matching stored Lean source and reviewed answer are reused without generation or recompiling, and only requests needing new Lean enter DSP (whose Draft stage may search Draft DB), and a request whose Lean does not pass shows no answer. This supersedes the 2026-10-02 "no Lean on ordinary send" behavior for new requests. Saved `llm_assessed` answers remain readable unchanged.

| ID | Requirement |
|---|---|
| PFR-001 | Ordinary natural-language assessment shall use GPT-6 Luna. A bounded escalation for unresolved mathematical reasoning may use GPT-5.6 Terra; Sol shall not be used. Provider failures shall not be interpreted as mathematical uncertainty. Actual usage and conservative price estimates shall include the model identities without rewriting historical prices. |
| PFR-002 | After the PFR-014 premise check and any required PFR-015 refutation decision, the agent shall normalize only the mathematical information explicitly present in the request and saved clarifications, then retrieve bounded candidates directly from the verified Recipe catalog. Compare domain, objects, assumptions, quantifier structure, conclusion and requested proof method; wording and bound-variable names may differ. A similarity score is a retrieval hint, never an equality certificate. Draft retrieval shall not precede or be a prerequisite for this search. |
| PFR-003 | A general universally quantified theorem may be instantiated using a recorded substitution with type, binder and premise checks. Natural-number exponent n=2 is admissible; negative exponent substitution, existential-to-universal inference, variable capture, unfulfilled premises and circular proof dependencies must not be silently accepted. Catalog entries remain evidence inputs, not instructions or presumed verified theorems. |
| PFR-004 | Only a consequential premise absent from the request and its saved clarification context shall cause a question. The original statement, question, answer and revision shall survive reload and resume as one request. Search miss or reasoning difficulty alone shall not cause a premise question. A suspected counterexample or an unstated choice that changes the claim's truth is consequential (PFR-014). |
| PFR-005 | New requests and answers shall be owner-scoped, idempotent and durable, with recoverable queue dispatch, bounded worker leases and stale-claim rejection. Completed answers, Lean progress, need-input states and failures shall be durable. User waiting shall not keep a worker or verifier busy. |
| PFR-006 | A request shall share account allowance with legacy proof jobs. Assessment requires one hold (or one token operation); needs_input releases it and a continuation reacquires it. The same hold covers the request's linked Lean job (PFR-012): no second reservation is made. It is consumed once when a Lean-verified answer passes review and released when Lean verification or the answer fails. Existing reservations keep their recorded policy. Usage telemetry remains even if the request fails or needs clarification. Retries and premise rounds are bounded. |
| PFR-007 | Project, projectless and guest composers shall use this flow through the ordinary Send action, without a Lean button, mode selector or extra consent step. The UI shows premise questions, Lean progress, the Lean-verified answer with its Lean source and natural-language proof, follow-up questions on verified proofs, and, on Lean failure, a failure notice with retry and no answer text. Existing history remains readable with its recorded evidence. Owner/chat changes cancel observation and cannot expose another conversation's result. |
| PFR-008 | Store source IDs/revisions, Recipe bindings, linked job IDs and application evidence separately from answer text. Never promote LLM approval alone into Lean verification or automatically publish a Recipe or Draft. No generated seed or fixed response may substitute for real catalog/provider/verifier calls in production. |
| PFR-009 | Draft DB shall be consulted only inside the DSP Draft stage when new Lean source is required. Use the real existing read-only Draft API even if newer formal publication is unavailable, with exact source identity/content hash, actual embedding fingerprint, bounded count/payload and no formal-verification claim. An unavailable or incompatible Draft format must not block direct Recipe reuse or be silently rewritten. No seed injection, fabricated retrieval or bypass is permitted. |
| PFR-010 | Catalog reuse: only an admitted Recipe revision with a source-bound immutable search description, stored independently reviewed answer and valid admission compiler receipt for the exact active toolchain may answer a natural request without generation or compilation. Conservative structural matching and separate-session independent request/Lean correspondence review must approve the same mathematical target and method. Return the exact stored Lean source and stored answer bytes in the requested language, with request-specific answer QA; do not create an explanation anew. Record lean_catalog with Recipe, reuse-entry, source, answer and review bindings. No Draft or alignment is required. An unconfirmed candidate falls through to PFR-012; unavailable providers or failed integrity are explicit failures. |
| PFR-011 | Any specialization, substitution, wrapper theorem, changed Lean source or newly required proof method requires a new linked Lean job and compilation. Such requests are not catalog reuse. For new proof requests, any non-identical target enters full DSP immediately, including specialization. The legacy ordinary-job selector may still compile an admitted general Recipe wrapper within its separately traced path and repair bound. Only the DSP Draft stage may consult Draft DB. |
| PFR-012 | Every request without a safely matched reusable Recipe creates exactly one linked Lean proof job. The default plan runs existing DSP: Draft (with optional real Draft DB retrieval), Sketch, Prove, compilation, bounded repair, independent semantic review and source-grounded explanation with answer review. When verified and reviewed, answer as lean_verified; otherwise fail as lean_verification_failed with no answer. A learner retry creates a new linked job within the existing retry bound. |
| PFR-013 | No new request shall be answered with an LLM-only (`llm_assessed`) proof. In a deployment that cannot run Lean, requests fail explicitly instead of returning an unverified answer. |
| PFR-014 | Before any Lean work, the assessment shall check the claim as literally stated for a concrete counterexample under its most natural reading, and for unstated choices that change whether it is true (for example the scalar field, the number system or a nonzero condition). When either is found and the saved clarifications do not resolve it, the request returns `needs_input` first. A suspected counterexample is presented tentatively, never as a verified fact, and the options include the likely intended claim(s) and keeping the statement as written. A choice that does not change truth causes no question: the most general reading is used, and an adopted conventional reading is written explicitly into the assessed statement. A learner who keeps the statement as written is not asked about it again. The check is recorded as private evidence. Conventions in the math-conventions catalog are confirmed, remembered and shown under [MCV-003–MCV-007](../math-conventions/requirements.md) instead of being silently defaulted. |
| PFR-015 | When the learner keeps a statement as written after the assessment reported a suspected counterexample (PFR-014), the request is first refuted with Lean: one linked Lean job proves the negation of the claim, using the suspected counterexample as a hint. If that job is verified and its explanation passes review, the request is answered as `lean_verified` with the verdict `refuted`, and the learner sees that the claim is false with the Lean-checked counterexample. If the refutation is not verified, the same request continues with an ordinary linked Lean job that tries to prove the claim (PFR-012); its result is shown as usual. A refutation never asserts falsity without a verified Lean proof of the negation, and the claim itself is never silently replaced. |
| PFR-016 | The API shall own direct Recipe candidate retrieval and final revalidation. Worker settlements bind the exact request revision/claim, reuse-entry revision/digest, Recipe revision, source/target/toolchain/compiler-receipt digests, stored answer language/digest and independent review evidence. Recheck lifecycle and all immutable bindings atomically with answer persistence and settlement. Worker assertions, copied target hashes and existing formal-target selector equality alone cannot certify correspondence to a natural request. |
| PFR-017 | Natural-request matching shall be conservative: accept notation/wording/binder renaming only when the full mathematical signature agrees; never erase domains, assume missing premises, reorder dependent quantifiers, weaken the conclusion or treat implication/specialization as equality. Unknown, conflicting or ambiguous candidates use the new-Lean path. An explicit proof-method request must match the source-bound method; an unspecified method allows any admitted method. |

Acceptance evidence must cover real PostgreSQL persistence/ownership/claim/quota behavior, catalog-receipt tamper rejection, linked-job creation without double reservation, exactly-once consumption/release, worker transport, real local admission compilation followed by reuse with zero verifier/generator/Draft calls, specialization and DSP compilation, paraphrase/binder-name reuse, domain/premise/quantifier/conclusion/method rejection, failure without answer text, frontend continuation and reload for project, projectless and guest chats, plus a bounded real provider smoke if credentials permit. Unexecuted checks are NOT VERIFIED, never assumed passed.

Runtime clarification: an unrepresentable model-generated Draft search hint inside DSP records query-invalid evidence and may continue DSP with zero Draft sources. Recipe search miss, stale toolchain or a candidate rejected for correspondence may use PFR-012. This does not apply to unavailable providers/catalogs or failed source integrity. An explicit requirement to use an unavailable source must not be silently dropped.
