# Fast proof answers and premise clarification

Authority: WORKING implementation contract approved by the user on 2026-09-30, with the ordinary-send/no-required-Lean behavior explicitly reaffirmed on 2026-10-02 JST. Applies to the current dirty agent/API/webfront trees; preserve unrelated work. Local implementation and validation are authorized; deployment and release readiness are separate outcomes.

| ID | Requirement |
|---|---|
| PFR-001 | Ordinary natural-language requests shall use GPT-6 Luna. A bounded escalation for unresolved mathematical reasoning may use GPT-5.6 Terra; Sol shall not be used. Provider failures shall not be interpreted as mathematical uncertainty. Actual usage and conservative price estimates shall include the new model identities without rewriting historical prices. |
| PFR-002 | The agent shall assess available catalog candidates against the requested statement, assumptions and proof method. A suitable direct or specialized proof shall pass an independent answer review and be returned without invoking Lean, with normal answered completion and explicit llm_assessed evidence distinct from verified. Lean execution or success shall not be an answer-acceptance prerequisite. No learner approval of proof selection is required. |
| PFR-003 | A general universally quantified theorem may be instantiated using a recorded substitution with type, binder and premise checks. Natural-number exponent n=2 is admissible; negative exponent substitution, existential-to-universal inference, variable capture, unfulfilled premises and circular proof dependencies must not be silently accepted. Catalog entries remain evidence inputs, not instructions or presumed verified theorems. |
| PFR-004 | Only a consequential premise absent from the request and its saved clarification context shall cause a question. The original statement, question, answer and revision shall survive reload and resume as one request. Search miss or reasoning difficulty alone shall not cause a premise question. |
| PFR-005 | New requests and answers shall be owner-scoped, idempotent and durable, with recoverable queue dispatch, bounded worker leases and stale-claim rejection. Completed answers, need-input states and failures shall be durable. User waiting shall not keep a worker or verifier busy. |
| PFR-006 | A request shall share account allowance with legacy proof jobs. Assessment requires a hold; needs_input/failure releases it; a continuation reacquires a hold and an answered result settles it once. Existing reservations keep their recorded policy. Usage telemetry remains even if the request fails or needs clarification. Retries and premise rounds are bounded. |
| PFR-007 | Both project and projectless chat composers shall use the new request flow through the ordinary Send action. They shall not add a Lean-verification button, mode selector or extra consent step. Existing formally verified history remains readable. UI supports pending state, questions, free text/options, retry, safe math rendering and reload; no confirmation checkbox or false Lean-verified badge appears. Owner/chat changes cancel observation and cannot expose another conversation's result. |
| PFR-008 | Store source IDs/revisions and application evidence separately from answer text. Do not promote LLM approval into formal verification or automatically publish a Recipe. No generated seed or fixed response may substitute for real catalog/provider calls in production. |

Acceptance evidence must cover real PostgreSQL persistence/ownership/claim/quota behavior, worker transport and no-Lean routing, substitution rejection cases, frontend answer continuation and reload, plus a bounded real provider smoke if credentials/access permit. Unexecuted checks are NOT VERIFIED, never assumed passed.

PFR-009: The natural-answer path shall search the real existing Draft catalog through a dedicated read-only API boundary, even when newer formal catalog publication is not configured. Treat every returned item as an unverified sketch; record exact source identity/content hash, validate the actual embedding fingerprint, bound candidate count and payload, and never grant this path formal-publication authority. No seed injection or fabricated catalog success may substitute for real retrieval.

Runtime clarification: local validation failure of a model-generated search hint may fall through to the normal independent-derivation decision with explicit query-invalid evidence, zero sources and no substitutions. This does not apply to unavailable providers/catalogs or failed source integrity. An explicit requirement to use an unavailable source must not be silently dropped.
