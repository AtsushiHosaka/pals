# Proof reuse: 抽象から具体への代入ルート

Status: WORKING(2026-11-06 改訂: 単一化をLeanのelaboratorへ委ねる方針に変更。実装は pals-agent / pals-api の `claude/recipe-specialization-reuse`)。オーナーの2026-11-06の依頼に基づく。実装前の仕様であり、実装の承認、`terraform apply`、本番配備は、この文書では承認されない。

関連: [requirements](requirements.md) の PFR-003、PFR-011、PFR-017。本番の事例は #223、平方専用Recipeは #287。

## 背景

2026年11月6日の本番で、「x²は連続である」という日本語の要求が、保存済みの一般Recipe（自然数 n について xⁿ は連続）を候補に挙げながら、範囲の判定で選ばれなかった（`dsp_scope_mismatch`）。結果として新規生成に進み、証明の候補が5回連続で検証に失敗し、完了までに約3〜6分かかった。

一般の結果を具体値に落とす操作は、Recipe 1件に限らない。抽象度が上がるほど、この操作は増える。したがって、n=2 の例だけでなく、代入を一般に扱う専用の経路を持つ。

現行の仕様は、PFR-003 で n=2 の代入を許し、PFR-011 で「特殊化には新しい検証ジョブとコンパイルが必要」としている。この文書の経路は、その両方に従う。新しい検証ジョブとコンパイルは行い、証明の生成（スケッチ、証明、修復）は行わない。

## Requirements

| ID | Requirement |
|---|---|
| PIR-001 | 要求した命題が、承認済みRecipe（または検証済みの定理）の全称命題の具体化であるとき、DSP（生成）に入らず、この代入ルートで処理する。ルートの名前は `catalog_reuse_instantiation` とし、既存の `catalog_reuse` と区別する。 |
| PIR-002 | 代入ルートは、スケッチ・証明の生成・修復のモデル呼び出しを0回とする。コンパイルは検証器で行う。現在の実装は、`settle` の前段でAPI所有の検証器を同期的に呼ぶ（注入された `recipe_instance_verifier`。未注入なら承認せずDSPへ）。PFR-011 の形（候補として提出し、既存のreconcilerがコンパイル）に寄せる方が望ましいが、(1) 候補の出所の束縛（`RecipeCandidateSourceV2`）が選択受領書（API所有の選択器、DBのスキーマ）を要求し、インスタンス用の受領書にはDBの移行が要る、(2) チャット要求の流れ（要求の `settle` → 1件の検証ジョブ → 説明 → 回答）に、説明を作らない短絡を足す必要がある、という理由で今回は見送った。Mathlib込みで初回約48秒かかるため、同期の呼び出しはワーカーの `settle` タイムアウトを超える恐れがあり、非同期化（検証ジョブ方式）が次の課題。 |
| PIR-003 | 要求は「要求のLean命題」（1行の命題）として扱う。自然言語の要求にはこれが存在しない（`pipeline` の `formal_statement` は利用者が与えた場合だけで、通常は生成モデルが候補の中で書く）。したがって形式化は提案の1回の呼び出しで得る。形式化が既にある経路（利用者指定の `formal_statement`）では追加0回とする。型付き正規形（OpenMath）での比較は行わない。 |
| PIR-004 | 引数の推論（複数束縛、入れ子の全称、依存束縛、関数引数、暗黙・型クラス引数）は、自前の単一化器を持たず、Leanのelaboratorに委ねる。雛形の `exact <一般定理> _ … _` が、高階パターン単一化と型クラス解決を行い、カーネルが検査する。検査は、(a) 雛形が要求の命題を構文的にそのまま宣言していること（alignment）、(b) 公理の監査、(c) コンパイル、の3つ。上限: 明示引数は6個まで、命題は2000文字、コンパイルは検証器のタイムアウト。 |
| PIR-005 | 側条件（型・定義域・前提）はLeanが確かめる。前提が閉じた式になる場合に限り、雛形の許可集合に含まれる `(by decide)`、Mathlibを読み込むRecipeでは `(by norm_num)` で閉じる。閉じなければコンパイルが失敗し、DSPへ進む（`inst_compile_failed`）。モデルに前提を証明させない。 |
| PIR-006 | Leanのソースは決定的な雛形から作る。一般定理に名前を付け（`example` は `pals_recipe_general` に改名）、末尾に `theorem pals_recipe_instance : <要求の命題> := by first | exact G _ … _ | …` を追加する。tactic・項の語彙は次の閉じた集合に固定する: `first`、`exact`、`_`、名前付き引数 `(name := 整数リテラル)`（提案のヒントのみ）、`(by decide)`、`(by norm_num)`（Mathlib読込時のみ）。`show`、`change`、`unfold`、`simp` など目標の型を書き換える構文は集合に含めない。モデル由来の文字列は「要求の命題」だけで、1行・括弧の対応・禁止語（`by`、`show`、`from`、`:=`、`;`、`sorry`、コメント等）を検査してから、定理の型としてそのまま入れる。 |
| PIR-007 | 検証は通常の検証器の経路で行う。要求した命題とLeanの定理の一致（statement alignment）、禁止公理の監査、元のRecipeの compiler receipt と toolchain の一致を、すべて通常のRecipe再利用と同じ基準で確かめる。元のRecipeの source digest と receipt digest を、代入の証跡に結び付ける。 |
| PIR-008 | 提案は構造化出力で1回だけ。内容は、Recipeの選択、要求のLean命題、任意のヒント（束縛名→整数リテラル）。ヒントは名前付き引数として最初に試す選択肢に入るだけで、外れても他の選択肢（`_`）が残り、正しい定理を妨げず、誤った命題を通すこともない。形式化が既にあれば提案は不要。独立したレビュー1回（要求の自然言語 ≡ Lean命題）を行う。これは既存のDSP経路の「形式化と意味審査」と同じ責任であり、この経路は新しい信頼を足さない。承認の権限はLean（API所有のコンパイル）とレビューの両方が揃ったときだけ。 |
| PIR-009 | 次の形は、このルートで扱わない。存在量化から全称への推論、変数の捕獲、型や定義域の拡大（自然数の束縛へ負の数を入れる、など）、仮定の追加と弱化、結論の変更、循環する参照。 |
| PIR-010 | 一般性として、次を扱う。複数の束縛、入れ子の全称、依存する束縛（後の束縛の型が前の束縛に依存する）、関数を引数にとる束縛（`f := fun x => ...`）、型クラスの引数、代入の連鎖（具体化された結果をさらに具体化する）。束縛数、項の大きさ、連鎖の深さに上限を置き、超えたときはDSPへ進む。 |
| PIR-011 | 回答は決定的な定型で作る。(1) 求める命題が一般の結果の特別な場合であること、(2) 一般の結果、(3) 元の保存回答（バイト列そのまま）、(4) 結び、の順。引数はelaboratorが決めるため、本文では断定しない（リテラルのみの旧文法の経路では `$n=2$` を明示する）。文字列置換した回答は作らない。4言語。モデルを呼ばない。 |
| PIR-012 | 証跡として、Recipeの ID・revision・entry digest、代入 σ、Leanソースの digest、compiler receipt を保存する。課金は検証の分だけとし、生成トークンは0とする。品質イベントにルートを出す。 |
| PIR-013 | このルートが適用できないとき、理由を型付きの分類（`inst_no_unifier`、`inst_ambiguous`、`inst_premise_unprovable`、`inst_compile_failed`、`inst_limit_exceeded` など）で記録し、DSPへ進む。承認しない形で失敗してはならない。 |
| PIR-014 | 性能の目標は暫定。モデル呼び出しは提案とレビューの2回で、範囲判定（2並列、約27秒）の前に試し、成功すれば範囲判定を飛ばす。コンパイル時間の実測（ローカル、Lean v4.32.0-rc1）: Mathlib込みの本番Recipe `natural_power_continuous` で、初回（oleanキャッシュが冷えた状態）約48秒、2回目以降約10秒。core Lean のみの小さな例は約0.4〜2秒。したがって10秒以内は達成できず、同期の単一リクエストで待つかどうかは次のPIR-002の判断に依る。 |

## Design

### 全体の流れ

```
解決済みの命題 ─┐
                ├─ 正規化 → 候補（Recipe）の正規形と単一化 → σ
候補の検索 ────┘                        │
                                        ├─ 一意でない / 失敗 → [モデルの提案（任意）] → 同じ検査へ
                                        ▼
                         側条件の確認（型・定義域・前提）
                                        ▼
                    決定的な雛形で Lean を作る → 検証器でコンパイル → alignment・公理の監査
                                        ▼
                     決定的な回答（代入の明示 + 元の保存回答）→ 証跡を保存
                    （どこかで失敗 → 理由を分類して DSP へ）
```

### 単一化（Leanのelaboratorに委ねる）

旧案（自前の型付き項の単一化器）は採らない。Leanは `exact G _ … _` で高階パターン単一化と型クラス解決を行い、カーネルが検査するため、同等以上の一般性を、新しい信頼なしに得られる。以下の旧案の記述は参考として残す。

- 候補の命題 `∀ x₁:τ₁, …, ∀ xₖ:τₖ, P(x₁…xₖ)` と、要求の命題 `Q` を、同じ型付き正規形に直す。`P` の中で `xᵢ` の位置に現れる項を、`Q` の対応する位置から読み取る。
- 同じ変数が複数の位置に現れるときは、すべての位置の項が一致することを確かめる。一致しなければ失敗とする。
- 関数を引数にとる束縛は、束縛変数への適用が `x y` の形に限られる範囲（高階パターン）で、λ項を復元する。それ以外は `inst_no_unifier` とする。
- 型 `τᵢ` に属することは、正規形の型情報で確かめる。自然数の束縛へ負の数を入れる形は、ここで失敗する。

### 側条件

- 前提 `H(σ)` は、閉じた式になった場合に限り、固定した手続きの集合で証明する。集合は小さく保ち、拡張はこの仕様の更新を要する。
- 手続きが失敗したときに、モデルに前提を証明させない。DSPへ進む。

### モデルの提案（任意の段）

- 単一化が失敗する理由が、表記や形式化の差にあるときに限る。
- 入力は、候補の束縛の一覧（名前と型）と、要求の命題。出力は、束縛名から項への対応（構造化出力）。自由な文章は受け付けない。
- 提案の項は、PIR-004〜PIR-007 と同じ検査にかける。検査を通らない提案は捨てる。
- この段のモデル呼び出しは、1回までとする。結果にかかわらず、回数と理由を証跡に残す。

### 実装の場所（現行の本番を起点にした目安）

- `pals_agent/proof_reuse.py`: 決定の種類 `instantiate` の扱い、Recipeの範囲判定の前に代入ルートを試す。
- `pals_agent/proof_instantiation.py`: `instantiate_universal` を一般化し、複数の束縛、依存、関数引数に対応する。
- pals-api: 新しいルートの証跡を受け付けて再検証する経路。これはRecipeの exact input の考え方と同じく、証跡が揃わないと受け付けない。

### 受け入れ条件

- 正例: x² の連続（n=2）、x³ の連続（n=3）、別の全称Recipeの具体化、2つの束縛をもつRecipeの具体化、入れ子の全称、関数引数の具体化、具体化の連鎖。いずれも生成のモデル呼び出しが0回で、検証器のコンパイルを1回通り、決定的な回答が返る。
- 負例: 存在量化の束縛、負の指数（自然数の束縛）、有理数や実数の指数、仮定の追加、結論の変更、変数の捕獲、前提が証明できない代入、型が合わない引数、改ざんしたルート証跡。いずれも承認されず、理由の分類つきでDSPへ進む。
- モデルの提案が誤った代入を返しても、検査とLeanが拒否し、承認されない。
- 通常の `catalog_reuse` の挙動と証跡は変わらない。
- 実Leanの試験は、固定版 Lean v4.32.0-rc1 で行う。

## 実装との対応（2026-11-06）

- 実装済み: PIR-001（ルート名 `catalog_reuse_instantiation`）、PIR-004/006（elaborator雛形、`pals_agent/recipe_instantiation.py` と `app/domain/recipe_instantiation.py` の同一コピー）、PIR-008（提案1回+独立レビュー1回）、PIR-009（拒否: 存在量化、負/有理/実数の指数、仮定の追加、結論の変更、型不一致、`by` 内の型の書き換え。いずれもLeanまたは雛形の検査で拒否）、PIR-011、PIR-012（証跡: Recipe ID・revision・entry digest、ヒント、Leanソースのdigest、API所有のコンパイル記録）、PIR-013（`inst_*` 分類）。
- 候補選択: 検索上位3件を提案に見せ、モデルが1件を選ぶ。**Lean側で複数候補を順に試す機構は未実装**（コンパイルがAPI側で1件ずつ非同期になるため）。
- 未達: PIR-002 の検証ジョブ方式、PIR-005 の側条件のうち `decide`/`norm_num` 以外、PIR-010 の「代入の連鎖」、PIR-014 の10秒（上記の実測を参照）、PIR-003 の「追加0回」（形式化が既にある経路への接続）。
