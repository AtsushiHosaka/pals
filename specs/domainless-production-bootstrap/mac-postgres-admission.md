# Mac PostgreSQL signed admission (WORKING addendum)

This bounded backend extension is authorized by the October 2 direct working instruction and `task-3/deployment/mac-postgres-admission-design.md`. It extends DPB-005/010/014 for a Mac production PostgreSQL container without changing Aurora v1 admission, public ordinary proof-request behavior, or canonical task completion status. This document records implemented admission boundaries; it is not proof of Mini deployment, live KMS signing, backup restoration or a production release.

| ID | Working contract |
| --- | --- |
| MAC-DB-001 | A separate `--apply-mac` entry accepts only canonical `pals.production-database-bootstrap.mac.v1`. It forbids an Aurora resource field and does not translate signed Mac bytes into another schema. Verify the complete canonical manifest SHA-256 through the independently pinned account/region/KMS key using ECC_NIST_P256, DIGEST and ECDSA_SHA_256; bind trust to the exact returned SPKI and key ARN. Retain the existing bounded release window, UUID, sequence, source commits, immutable image, checked-in artifact and toolchain contracts. |
| MAC-DB-002 | The signed deployment identity has exactly backend `mac-postgresql-container-v1`, environment UUID4, Mini host binding SHA-256, compose project `pals-production`, actual PostgreSQL system identifier decimal uint64, production volume UUID4, database `pals`, PostgreSQL major 16, and five source-tree SHA-256 values for the existing source repo set. Compare every value with independently provisioned operator expectations before any DDL. Read the actual database system identifier/version/name from the target master connection. Read a host identity marker and volume marker from trusted deployment mounts; never treat manifest values as observations. |
| MAC-DB-003 | Expected identity, host marker, volume marker and deployment lock paths are operator inputs, never HTTP input. Require absolute paths without symlink parents, regular single-link files owned by root or the executing deployment UID, and no group/other write permissions. Ancestor directories must also be trusted (root sticky temporary roots are allowed). The volume marker belongs to the exact production data volume and is UUID4, optionally LF terminated. The opaque host marker is hashed as exact bytes. Provisioning must bind these read-only mounts to the confirmed Mini and production volume; the API cannot infer a hardware or Docker mount identity from arbitrary files. |
| MAC-DB-004 | Configured master/release/runtime/reconciler/selector/reader URLs must have identical PostgreSQL host/port/database and no libpq endpoint overrides. Login identities and their 24–256 printable-character passwords must be distinct. Before DDL, the master must be the authenticated superuser and existing application logins must lack administrative flags; serving/read/selector/reconciler logins must lack database/schema CREATE and membership in release/schema-owner/cutover authorities. Recheck least privilege and normal login readiness after installation. Do not expose URLs/passwords in errors or receipts. |
| MAC-DB-005 | Hold an exclusive nonblocking host deployment lock and a PostgreSQL session advisory lock over observed identity, signature checks, state preflight, complete installer and readiness. Keep the host lock inode after release to avoid replacement-inode lock races. Session lock contention fails closed; do not confuse the existing roles transaction lock with whole-bootstrap exclusion. |
| MAC-DB-006 | Fresh admission requires no non-extension application objects. An existing database is accepted only for an exact current admission tuple and matching trust fence with complete read-only runtime/reconciler/selector/reader readiness; that replay returns without bootstrap DDL, preserving user data. Stale, changed, mixed, partial or incomplete bootstrap states fail before role/password/extension/schema mutation. Automatic partial-state repair is excluded from this initial implementation; a signed recovery workflow requires separate reviewed evidence. |
| MAC-DB-007 | Only verified fresh Mac identity reaches the common existing installer order: roles/extensions → admission control → signed admission → PJR → empty base → PEX → billing → ordinary migrations → runtime grants → readiness. Mac admission uses `production-bootstrap-mac-v1:<manifest SHA-256>` as the carrier storage version and the exact KMS/SPKI trust. Existing PJR/PEX bounded printable storage-version schema permits this without canonical migration rewriting. Aurora's existing `production-bootstrap-v1` value and schema remain unchanged. |

The operator expected identity file records independently obtained actual build-context hashes, environment/host confirmation, database system ID and volume ID. A separate deployment receipt captures actual source revisions, image digests and toolchain identity; Python signature-binds those manifest fields but does not independently observe the running images or their source revisions. Producing those hashes and protecting the host/volume mounts belong to host deployment tooling; supplying a signed manifest alone is insufficient. No signing private key, production credential generation, serving DDL, local-runtime bypass, quota expansion or mandatory Lean step is introduced.

Verification must distinguish local cryptographic/HTTP boundary tests from real AWS KMS evidence. Disposable isolated PG16+pgvector tests may prove identity reads, session locking, schema installation, readiness and exact replay without touching any shared user database or cluster roles. Live Mini mount provenance, exact deployed build trees/images, KMS authorization/revocation and dump/restore/re-admission remain separate deployment gates.
