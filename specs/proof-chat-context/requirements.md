# Proof chat context requirements

Status: **WORKING proposal** for [parent issue #39](https://github.com/AtsushiHosaka/pals/issues/39). This is a reviewable implementation slice, not approved product policy or a completed repair. No production operation is authorized by this document.

## Outcome and authority

An authenticated learner who refers to an earlier theorem or proof in the same chat can continue from that exchange without unnecessarily restating available information. Mathematical correctness, ownership, independent review, Lean verification and accounting retain their existing requirements.

This additive proposal extends reference resolution under [PFR-002, PFR-004–PFR-008 and PFR-010–PFR-017](../proof-request-reuse/requirements.md). It preserves [PCS-003–PCS-004](../projectless-chat-start/requirements.md), [LRC-014–LRC-018](../lean-recipe-catalog/requirements.md), [BILL-013 and BILL-015](../individual-billing/requirements.md), [MAT-005–MAT-008](../project-materials/requirements.md), [MCV-005–MCV-006](../math-conventions/requirements.md), and the signed, DDL-free runtime boundary in [DPB-005](../domainless-production-bootstrap/requirements.md). Those canonical contracts remain authoritative: historical `llm_assessed` answers may be input evidence, but new answers must satisfy PFR-013. No natural-response exception is granted.

## Scope and working assumptions

Scope is authenticated Project and projectless proof-request chats. A complete prior exchange means the stored original user statement, all its ordered clarification question/answer turns, its delivered assistant answer with recorded evidence kind, and its recorded mathematical conventions/adopted readings or authoritative resolved proposition. The client does not supply history. Guest flow and historical standalone proof-job/explanation records retain current behavior; importing those other record types is outside this slice.

**Implementation assumptions awaiting review:** select at most three recent complete exchanges; bound the final canonical snapshot, including selection/omission metadata, to 128 KiB of UTF-8. These limits are proposed operational bounds, not approved product policy. Complete exchange omission is allowed; mathematical text truncation is not. The exact bounds, older-record coverage and live acceptance environment must be settled before declaring implementation readiness.

Non-goals: model switching, uploads/OCR UI, sharing, cross-chat or project-wide retrieval, memory summaries, rewriting prior messages, publishing proof material, changing review/Lean gates, adjusting billing policy, automatic retries, or production rollout in this task. No production mock, fixed answer, hidden fallback or bypass can satisfy completion.

## Requirements and observable acceptance

| ID | Requirement and acceptance criteria | Priority | Source |
|---|---|---|---|
| PCX-001 | When a new authenticated proof request explicitly refers to an available earlier exchange in the same chat, the system shall provide that exchange to reference resolution and all subsequent assessors/reviewers. A sufficiently determined theorem shall not trigger a request to restate it solely because earlier context was omitted. Genuine mathematical ambiguity still follows PFR-004/PFR-014. Acceptance includes a prior strict-monotonicity theorem followed by dropping endpoint continuity, and a reference to a step in the delivered proof. | Must | Issue #39; PFR-004/PFR-007 |
| PCX-002 | At admission, the system shall select complete delivered exchanges from the exact authenticated owner and chat, exclude the new request and unfinished/failed exchanges from full content, apply deterministic ordering and whole-exchange bounds, and preserve statement, clarification order, answer bytes, evidence kind and recorded mathematical readings. Bounded ordered visibility markers shall retain omitted positions and newer failed/unfinished visible requests, including the latest visible request, so an older included theorem cannot silently become the antecedent of “above.” Empty history is valid; mathematical text is never truncated. | Must | Ownership contracts; MCV-005/MCV-006; working bounded-input assumption |
| PCX-003 | The admitted context shall be immutable for the request. Idempotent create, clarification, Retry and claim redelivery shall use the same snapshot and digest even if an earlier request is subsequently retried or its current result changes. Current-request clarification remains a separate evolving record. | Must | PFR-005/PFR-016 |
| PCX-004 | Prior text and recorded mathematical readings shall be treated as untrusted conversational scope evidence. They may identify an explicit reference or earlier argument; they shall not override current instructions, establish truth/Lean verification, introduce unrelated assumptions, execute embedded instructions, or confirm an OCR-extracted proposition. A changed account convention shall not rewrite the scope of an earlier theorem; use its recorded reading, never today's default. Missing/omitted/ambiguous references, including newer excluded visible turns, cause a concrete clarification rather than substitution of an older theorem. | Must | PFR-008/PFR-014; MAT-006/MAT-007; MCV-005/MCV-006 |
| PCX-005 | When a quote admits a new context-aware request, its payload shall bind the selected context digest and its conservative cost estimate shall account for the actual context content supplied to applicable model calls, not only digest bytes. If history changes before admission, the system shall reject the stale quote before any request, reservation or outbox commit and obtain a fresh quote through the existing error/retry flow. Continuations bind the request's stored context; the existing single operation/hold, prices, limits and exactly-once settlement remain unchanged. | Must | BILL-013/BILL-015; PFR-006 |
| PCX-006 | Every accepted context-aware assessment settlement and Recipe/correspondence decision shall bind the exact immutable context digest, including recorded mathematical readings and ordered visibility markers, together with existing claim/revision/request bindings. API revalidation shall reject missing, changed or mismatched binding. All relevant model roles receive identical context. A linked formal job retains the resolved proposition and originating request/context binding; previous answers never substitute for compilation or review. | Must | PFR-010–PFR-017; LRC-018; MCV-005/MCV-006 |
| PCX-007 | A request carrying context shall be claimed only by a worker advertising the supported context contract version. Missing/incompatible capability shall fail before claim acquisition or provider spend; malformed context shall not be silently dropped. Disabled and legacy flows retain their existing payload/hash semantics. | Must | Compatible-worker safety; PFR-005/PFR-008 |
| PCX-008 | Storage shall be introduced through an additive, fingerprinted migration and reviewed signed release registry. Application startup remains DDL-free. Runtime roles cannot overwrite snapshots; schema/grant/manifest drift prevents enabling the flow. Production enablement requires compatible pinned API and worker artifacts, approved bounds and signed admission. Existing predecessor digests and trust boundaries remain unchanged. | Must | DPB-005; existing release contracts |
| PCX-009 | Historical requests without a bound snapshot and existing saved answers remain readable with original evidence; no retrospective reconstruction/backfill modifies their meaning, usage or digest. Disabling new admission shall not unbind accepted requests. An incompatible API or worker rollback shall be blocked by reviewed signed admission/runtime catalog gates, or by a verified pause/drain preventing claim and settlement against bound requests; old binaries' absent capability checks are not a safeguard. | Must | PFR-005/PFR-008; PCS-004; DPB-005 |
| PCX-010 | Completion evidence distinguishes source facts, executed tests and live behavior. Tests cover owner/chat isolation, completeness/bounds/readings/visibility, immutable retries, quote races, hash tampering, both API and worker incompatibility, and migration/runtime privileges. Live issue closure reproduces theorem and proof-step references through real admitted services with independent mathematical review and new answers satisfying PFR-013: `lean_catalog` with valid admission receipt or `lean_verified` with actual compiler evidence. ## Readiness decisions

The full-exchange representation and immutable owner/chat boundary are selected for this working design. The parent must review the proposed count/byte bounds, omission UX and coordinated release gate before implementation readiness. A working spec can be reviewed while those choices remain open; it cannot serve as approval for production migration or a claim that issue #39 is fixed.
