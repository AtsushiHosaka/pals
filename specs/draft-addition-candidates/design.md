# Draft addition candidates design

## Storage and actual verifier provenance

Release migration installs additive `pals_draft_candidates` storage; serving never creates or repairs it. `candidates` stores exact verified source/source SHA-256, actual verifier release/deployment/image/verifier SHA-256, canonical target/target SHA-256, accepted-attestation hash, semantic/output review hashes, exact reviewed output, answer/answer SHA-256, language and creation time. Deduplication is `(lean_sha256, verifier_image_digest, verifier_toolchain_sha256, output_language, answer_sha256)`, preserving independently reviewed language/answer variants. No question, conversation, owner, account, project or proof-job identifier is in the candidate payload. Private `origins(candidate_id, proof_job_id)` relates candidates to follow-up questions; catalog payload never contains these links.

The normal API reconciler checks fresh readiness, pinned release/deployment/image/toolchain identity and mTLS verifier success, then records `verification_receipts` in the same fenced transaction as acceptance of the attestation. The canonical `pals.current-verification-receipt.v1` binds candidate/job IDs, exact source digest, `verifier_release_id`, `deployment_binding_sha256`, `verifier_image_digest`, `verifier_toolchain_sha256`, accepted attestation and its digest. This is actual runtime evidence, distinct from historical `verified_reconciliation_audit` migration evidence. Historical audit rows are neither prerequisites nor fabricated. Missing current receipt means no candidate is captured.

Candidate capture occurs in the transaction that applies an answered `lean_verified` request. It requires matching current source/attestation receipt, independently approved source-bound semantic review, and the exact approved explanation. Before capture, the repository locks the explanation row and recomputes `proof_explanation_output_sha256` from actual stored content; a review of an older output cannot authorize a newer explanation. Answer text uses the same Python `_answer` flattening routine as request presentation, preserving exact Unicode whitespace behavior; SQL never independently reformats the answer. Missing evidence leaves the proof answer intact but produces no addition candidate. Reuse answers never invoke this capture path. All receipts, candidates, private origins, decisions, publication stages and admitted Drafts are append-only, including a TRUNCATE prohibition. Runtime has only fixed-search-path capture/receipt functions, with no direct candidate/origin listing or decision authority.

## Eligibility and concurrent follow-up

Each private origin has an immutable `recorded_at`. Eligibility requires every origin to have passed `recorded_at + 24 hours`, with no clarification before its individual cutoff. Capturing an additional origin acquires the same candidate advisory lease; finalized candidates do not acquire additional origins. Decisions use a canonical candidate identity, expected undecided state, reason code and candidate row lock. Operator publication holds a candidate advisory lease; insertion of a related clarification acquires the same lease before its timestamp is committed. Eligibility is checked again at final publication. A concurrently arriving question cannot be skipped by an approval snapshot. Rejected or fully approved candidates cannot receive another decision; exact publication replay returns the existing result.

## Operator preparation and resumable publication

`python -m app.release.draft_candidates list|prepare-recipe|approve|reject` runs only with an operator release login, outside the web application. `prepare-recipe --candidate-id ... --recipe-manifest ...` admits the exact candidate source through the real pinned isolated compiler and returns its immutable compiler receipt, which an independent reviewer binds into the sealed entry. Preparation publishes no searchable entry or approved Draft. Existing formal v1 selection explicitly calls the least-privilege `legacy_policy_allows` boolean function and rejects raw-policy sources (LRC-019). Listing includes decision and completed publication stages so a failure can be inspected without claiming rollback.

Approval consumes canonical closed `pals.candidate-publication.v1` containing `candidate_id`, `recipe_manifest`, `draft_manifest` and `entry_manifest`; operator intent alone is not a compiler or review result. The raw Recipe manifest follows LRC-019. The signed entry uses `pals.sealed-recipe-search-entry.v1` (LRC-017). The signed `pals.candidate-draft.v1` binds the closed five-field Draft payload, exact OpenMath embedding input, versioned embedding binding and an independent source/answer/Draft review. Both Ed25519 reviews are verified against pinned release keys before publication effects. Review principal differs from the source author. Entry source, target, language and answer bytes must equal the captured candidate. Captured runtime `verifier_toolchain_sha256` is the verifier digest, not the SHA-256 of the complete Recipe fingerprint. Raw admission checks the exact release/deployment/image/verifier binding tuple and fingerprint `verifier_sha256` against the captured receipt, then binds the actual full fingerprint SHA-256 returned by admission into the Recipe entry.

Publication stages are real operations: (1) exact-source Recipe admission and compiler receipt; (2) Draft payload insertion with a real provider embedding and immutable provider request/input/vector/binding receipt; (3) searchable entry admission, stage receipt and final `approved` decision in one transaction. The entry is last. Every completed stage stores candidate/bundle SHA-256 and immutable catalog identity; retries resume only unfinished stages and reject different bundles or payloads. Partial failures remain undecided and retain their stage receipts. No false rollback or complete status is reported. Only the final transaction means both catalogs are published. Optional historical alignment is admitted separately and is not a prerequisite for direct Recipe reuse.

## Draft projection and privacy

The sealed legacy `public.dsp_drafts` population and metadata remain unchanged. Additional verified Drafts live in append-only `published_drafts`; `selectable_drafts` exposes only rows whose candidate has a final approved decision. The read-only natural Draft reader unions the sealed base with this view in its existing repeatable-read snapshot. It checks all additions use the exact active `openai` / `text-embedding-3-small` / 384 / OpenMath-v2 binding, hashes the actual combined population and rejects duplicate IDs, incompatible dimensions or binding. A prepared or partially published candidate is absent from both search paths. New code generation can use this projection inside DSP Draft. Recipe-first reuse remains independent of Draft projection availability.

Description, method and Draft content are derived from the closed formal target, verified source and reviewed explanation. Independent admission review must confirm the description and exact answer correspond to that source, including domain, hypotheses, quantifiers, conclusion and method. No original learner message is copied. Immutable per-language entry variants are reviewed separately; missing variants fall back to DSP and never trigger runtime translation on the no-generation reuse path. Production authorization/sharing and the signed catalog release remain separate release concerns; a local operator publication does not claim those deployments are complete.

Operator credentials are provisioned explicitly by the release administrator. The login is a member of `pals_draft_candidate_operator`, `pals_api_schema_owner` and `pals_api_recipe_catalog_owner` and can SET ROLE to each; no serving/worker login gets this combination. Migration creates the NOLOGIN operator role but does not silently grant it to existing logins. Inadequate role membership fails before catalog mutation. Pinned review public keys and mTLS release credentials are release-only configuration.

The raw syntactic policy permits parameterless declaration headers but does not infer absence of Lean auto-implicit binders from a regex. Independent target/source admission review must inspect the actual elaborated mathematical target and reject hidden premises or auto-implicit assumptions. Unsupported candidates are held rather than changing source bytes or claiming a closed proof from syntax alone.
