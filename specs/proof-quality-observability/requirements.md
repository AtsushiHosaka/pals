# Proof Quality Observability Requirements

Status: WORKING — オーナーの2026-11-03の依頼（[Issue #217](https://github.com/AtsushiHosaka/pals/issues/217)）に基づく。依頼の趣旨は次のとおり。本番はAWSで動いており、Mac miniは使っていない。即時通知やファンアウトの仕組みは要らない。Lean証明の失敗はCloudWatchのログ・メトリクス・アラームとして出し、定期的にCloudWatchを読みに行く外部の機能（オーナーの言う「ドッツ」）が拾う。「ドッツ」はChatGPT の dots（OpenAI の常駐エージェント）であることを、コーディネーターが2026-11-03に確認した。公式の一次情報ではなく、第三者の記事（[Flavio Copes](https://flaviocopes.com/openai-dots/)、[Composio](https://composio.dev/content/a-guide-to-chatgpt-dots-how-openai-s-always-on-agents-work)）が出典である。失敗の種類と、精度がどれだけ上がったかを一か所に記録し、グラフで見たい。仕様の承認前に、アプリの実装、`terraform apply`、本番配備は行わない。

失敗の分類と評価台帳は [Issue #216](https://github.com/AtsushiHosaka/pals/issues/216) が並行して作っている（`docs/quality-ledger/taxonomy.md`）。この仕様はその分類を参照し、複製しない。分類が未マージの間は [design.md](design.md) の暫定分類を使い、#216 の分類が確定した時点で合わせる。

## Overview

本番の証明パイプラインは、失敗を種類つきの構造化イベントとして CloudWatch に出す。種類ごとの件数、失敗率、評価実行ごとの成功率を CloudWatch のメトリクスにし、1枚のダッシュボードで見られるようにする。インフラと検証器の失敗にはアラームを付け、モデルの失敗は率で監視し、正規の拒否は数えるだけにする。外部の読み取り機能には、読み取り専用の IAM ロールと、文書化したクエリを渡す。

## Goals

- どの種類の失敗が、いつ、どれだけ起きたかを CloudWatch で見られる。
- 評価実行ごとの成功率を時系列で見られ、精度の向上を確認できる。
- 失敗の性質（基盤・検証器・モデル・審査・拒否）に応じて、アラームの出し方を分ける。
- 質問本文・利用者情報・秘密を、ログにもメトリクスにも出さない。
- 追加費用を、金額の上限つきで見積もる。

## Non-goals

- 即時通知、SNS、メール、チャットへの通知、ファンアウトの仕組み。
- 外部の読み取り機能（ChatGPT の dot）そのものの設定と実装。この仕様は、読める権限、読む経路の比較、手順だけを定める。
- Langfuse を本番の実行経路に入れること。
- 評価台帳の形式と過去の評価結果の集約。これは #216 の範囲である。
- 回答までの時間の段階別計測。これは `latency_stage`（pals#149）の範囲であり、この仕様は変えない。
- 既存の CloudFormation 管理の machine-auth モニター、既存の SNS トピック、AWS Budgets の変更。
- 過去の失敗（CloudWatch の導入前）の取り込み。

## Functional requirements

### 分類と発行

| ID | Requirement |
|---|---|
| PQO-001 | 終端に達した証明要求と、評価実行の各ケースは、#216 の分類から選んだ `FailureClass` をちょうど1つ持つ。成功した要求は `FailureClass` を持たない。分類に載っていないコードは `unclassified` とし、黙って他の分類へ入れない。 |
| PQO-002 | 終端イベントは、1つの要求につき1回、終端状態を確定した側が、その DB コミットの後に発行する。ワーカーの再配信が既に終端の要求を見つけたときは、発行しない。重複を許す箇所は設計で明示する。 |
| PQO-003 | メトリクスは名前空間 `PALS/ProofQuality` に置く。名前、単位、ディメンションの組は [design.md](design.md) の一覧に従う。 |
| PQO-004 | 分類コードからメトリクスへの対応は機械的にする。`FailureClass` と `FailureCode` の値は、#216 の分類の識別子をそのまま使う。メトリクス側で独自の別名や言い換えを作らない。 |
| PQO-005 | ディメンションは `Environment`、`Route`、`FailureClass`、`FailureCode`、`Suite`、`ModelConfig`、`State` に限る。各メトリクスにはD4の正確な組だけを使う。`State` は `accepted`、`queued`、`verifying`、`explaining`、`awaiting_application` の5値に限り、在中の件数と経過秒数だけに使う。`Route` を状態の代用にしない。状態の未知値・欠落・重複は拒否し、`unrecognized` や別の状態へ置き換えない。リビジョンと要求の相関 ID はログの項目に置き、ディメンションにしない。distinct なメトリクス数は150以下にする。 |
| PQO-006 | 成功率は `成功 / (成功 + 失敗)` とする。`policy_refusal` と、利用者の入力待ち（`needs_input`）は分母にも分子にも入れない。 |

### ログ

| ID | Requirement |
|---|---|
| PQO-007 | 品質イベントは1行の JSON（CloudWatch Embedded Metric Format）で、項目は許可リストにある値だけとする。ラベルは閉じた語彙から選び、語彙にない値は `unrecognized` に置き換える（`proof_request_worker.py` の `_diagnostic_label` と同じ方針）。ただし `State` と完走性メトリクスの契約違反はPQO-005とD4に従って拒否する。 |
| PQO-008 | ログとメトリクスに出さないもの: 質問本文、回答本文、Lean のソースと診断メッセージ、例外メッセージ、利用者・アカウント・IP・セッションの識別子、トークン、秘密、プロバイダの要求 ID。要求の相関には、正規形の UUID の SHA-256 だけを使う（`runtime_latency.py` と同じ）。 |
| PQO-009 | 品質イベントの発行は、要求の処理を遅らせず、失敗させない。発行の失敗は握りつぶし、件数を数える（`QualityEventsDropped`）。 |
| PQO-010 | 品質イベントだけがホストの外へ出る。他のアプリログは、この仕様ではホストの外へ出さない。専用ロググループ `/pals/prod/quality-events` に置き、保持期間は Terraform の変数で決める（既定30日、[Open questions](#open-questions) を参照）。 |

### アラーム

| ID | Requirement |
|---|---|
| PQO-011 | アラームは3つの系統に分ける。(a) インフラと検証器の失敗は、件数で警報にする。(b) モデルの証明失敗と審査の却下は、率で警報にする。(c) ゲスト向けなどの正規の拒否（`policy_refusal`）は、警報にしない。 |
| PQO-012 | インフラと検証器のアラームは、次のしきい値を初期値とする。これらは件数が少ない事象を拾うためのもので、根拠は設計の表に書く。 |
| PQO-013 | 率のアラームは、最小サンプル数を下回る期間では `OK` を保つ。しきい値は暫定であり、配備から14日分の実測で見直す（[tasks.md](tasks.md)）。 |
| PQO-014 | ワーカーの定期ハートビートが途絶えたとき（ワーカー停止、またはログの経路の停止）を、欠測を異常とみなすアラームで検出する。 |
| PQO-015 | 分類されなかった失敗（`unclassified`）が出たとき、分類の漏れとして警報にする。 |
| PQO-016 | アラームの動作（`alarm_actions`）は空を既定とし、SNS トピックを新設しない。状態は `DescribeAlarms` と `DescribeAlarmHistory` で読める。通知の追加は、変数で後から足せる形にする。 |

PQO-012 の初期値:

| アラーム | 条件 | 評価 |
|---|---|---|
| 検証器の失敗 | `FailureClass=verifier` の失敗が1件以上 | 5分 × 3期間のうち1期間 |
| インフラの失敗 | `FailureClass=infra` の失敗が1件以上 | 5分 × 3期間のうち2期間 |
| ジョブキューの滞留 | `proof-jobs` の `ApproximateAgeOfOldestMessage` が900秒超（キューの可視性タイムアウトと同じ） | 5分 × 3期間すべて |
| DLQ | `proof-jobs-dlq` の `ApproximateNumberOfMessagesVisible` が1以上 | 5分 × 1期間 |
| ホスト | EC2 の `StatusCheckFailed` が1以上 | 5分 × 2期間 |

PQO-013 の初期値（暫定）:

| アラーム | 条件 | 評価 |
|---|---|---|
| モデルの証明失敗率 | `proof` 失敗 / (成功 + 失敗) が60%超。ただし1時間の要求数が10件以上のとき | 1時間 × 3期間のうち2期間 |
| 審査の却下率 | `review_rejected` / (成功 + 失敗) が30%超。同じ最小サンプル | 6時間 × 1期間 |

### 完走性（終端しない要求の検出）

終端イベントは、終端した要求にしか出ない。Lean 検証後に結果が利用者へ届かず、要求が「検証中」のまま残る場合、イベントは0件で、PQO-006 の分母にも入らない。2026年11月6日の約1,522秒は、クリックから失敗表示の初回観測までの間隔であり、非終端のDB状態やイベント欠落を確認した値ではない。次の要求で、終端しない要求を成功率とは別に検出する。

| ID | Requirement |
|---|---|
| PQO-026 | 受け付けた要求を `ProofRequestsAccepted` として数える。成功率とは別に、受付数に対する終端数の差を見られるようにする。 |
| PQO-027 | 終端していない要求の件数と、受付から最古の要求の経過秒数を、D4の5監視状態別のゲージ `ProofRequestsInFlight`、`ProofRequestOldestAgeSeconds` として5分ごとに出す。各状態へ排他的に分類し、0件の状態も件数0・経過秒数0を出す。状態の欠落や集計失敗を0で埋めない。DBの状態と監視状態の対応はT018で検証し、データベースの状態列と時刻だけを読む。質問本文・Lean ソース・回答本文は読まない。 |
| PQO-028 | Lean ジョブが終了済みなのに API が結果を適用していない件数と、その最古の経過秒数を、PQO-027 とは別のゲージ `LeanJobsUnreconciled`、`LeanJobsUnreconciledOldestAgeSeconds` として出す。 |
| PQO-029 | 非終端の最古の経過秒数に対するアラームを、各 `State` と `Environment` の完全一致で選び、状態別の期限で作る。未適用ジョブの経過秒数は `Environment` だけの別アラームで選ぶ。D11の比較・期間・欠測の契約に従い、ゲージ自体が途絶えたときも異常とみなす（`breaching`）。pending、欠測、期限超過を、正常として扱わない。 |
| PQO-030 | 診断コードが空の `lean_verification_failed`（ジョブの取り消し、ワーカーの中断など）を、`model.could_not_prove` へ入れない。診断が無いものは `unclassified` に置き、PQO-015 の警報にする。 |
| PQO-031 | 実際の証明を最後まで通す合成プローブは、この仕様の範囲に含めない。モデル費用が継続して発生するため、オーナーが継続費用を承認した場合にだけ、別 Issue で扱う。承認までは PQO-026〜PQO-029 を追加モデル呼出しのない代替とする。DB集計・CloudWatchの費用が0という意味ではない。 |

PQO-029 の初期値は、実測がないため暫定とする。期限の根拠は design の D11 に置く。

### 精度

| ID | Requirement |
|---|---|
| PQO-017 | 評価の実行ごとに、1つの評価イベントを発行する。含める値は、`Suite`、`ModelConfig`、ケース数、成功数、成功率、分類ごとの失敗数、所要時間、費用、リビジョン、台帳の行 ID とする。台帳への追記と CloudWatch への発行は同じ関数から行い、片方だけが残らないようにする。 |
| PQO-018 | ダッシュボードで、`Suite` と `ModelConfig` ごとの成功率を時系列の折れ線にし、精度の向上を確認できるようにする。CloudWatch の導入前の評価結果は取り込まない（EMF が受け付けるのは過去2週間以内の時刻に限られる）。過去の推移は #216 の台帳とグラフが担う。 |

### 読み取りとダッシュボード

| ID | Requirement |
|---|---|
| PQO-019 | 外部の読み取り機能（dot）が使う権限は、最小権限の読み取り専用にする。許可は CloudWatch のメトリクス・アラーム・ダッシュボードの読み取りと、品質イベント用ロググループへの Logs Insights の実行に限る。`ReadOnlyAccess` などの広い管理ポリシーは使わない。書き込み、S3、SSM、DB、KMS、IAM、他のロググループには触れさせない。読む経路は [design.md](design.md#d7-読み取りの経路) の比較で決める。権限を引き受ける主体は変数で与え、空のままなら Terraform はロールを作らない。 |
| PQO-020 | 運用手順に、メトリクスの取得と Logs Insights の文書化したクエリ、およびダッシュボードの見方を載せる。各クエリは、読み取りの権限で実際に実行できることを受け入れ条件にする。dot 側の資格情報の扱い、失効時の挙動、監査ログは、確認できるまで未確認事項として手順に残す。 |
| PQO-021 | ダッシュボード `pals-prod-proof-quality` を Terraform で作る。構成は [design.md](design.md) の配置に従う。 |

### 運用と費用

| ID | Requirement |
|---|---|
| PQO-022 | CloudWatch のリソースは、`pals-infra` の Terraform で管理する。コンソールでの手作業は残さない。`terraform apply` と本番配備はオーナーの承認を要する。 |
| PQO-023 | 追加費用の見積もりと上限を、下の「Cost」に置く。実測が上限を超えたら、ディメンションを減らす。 |
| PQO-024 | 擬似的な失敗を注入し、メトリクス、アラーム、ダッシュボード、読み取りロールのクエリが動くことを、実測で記録する。 |
| PQO-025 | 既存の CloudWatch 関連リソース（CloudFormation の machine-auth モニター、SNS トピック `pals-macmini-auth-alerts`、AWS Budgets）は変更しない。 |

## Acceptance criteria

- 擬似的な失敗を、分類ごとに1件ずつ発行すると、対応するメトリクスが5分以内に `ProofRequestsFailed` の該当ディメンションに現れる（PQO-003、PQO-004）。
- 質問本文、回答本文、Lean ソースのダミー文字列を要求に含めて実行したとき、発行された品質イベントのどこにも、その文字列が含まれない（PQO-008）。
- 分類の語彙にある全コードが、いずれかの `FailureClass` に対応する。対応表にないコードを注入すると `unclassified` になり、PQO-015 のアラームが `ALARM` になる（PQO-001）。
- 同じ終端状態を2回配信しても、`ProofRequestsSettled` は1回しか増えない（PQO-002）。
- 発行先が使えなくても、証明要求は成功し、`QualityEventsDropped` が増える（PQO-009）。
- `policy_refusal` を発行しても、どのアラームも `ALARM` にならない（PQO-011）。
- 検証器の失敗を1件注入すると、検証器のアラームが `ALARM` になり、SNS などへの通知は出ない（PQO-012、PQO-016）。
- 最小サンプル未満では、失敗率が100%でも率のアラームは `OK` のままである（PQO-013）。
- ハートビートを止めると、15分以内にアラームが `ALARM` になる（PQO-014）。
- 検証中のまま残る要求を1件作ると（結果の適用を止める）、終端イベントが0件でも、`ProofRequestsInFlight` と `ProofRequestOldestAgeSeconds` に現れ、期限後にアラームが `ALARM` になる。ゲージの発行を止めても `ALARM` になる（PQO-026〜PQO-029）。
- 5状態に異なる件数・経過秒数を与えると、状態ごとの系列とアラーム選択が一致する。未知・欠落・重複の状態、追加ディメンション、負数・非有限値・整数でない件数は拒否され、他状態の系列へ混ざらない。0件を確認できた状態だけ0を出す（PQO-005、PQO-027、PQO-029）。
- 診断コードが空の失敗を注入すると、`model.could_not_prove` ではなく `unclassified` に数えられる（PQO-030）。
- 評価実行を2回行うと、ダッシュボードの折れ線に2点が現れ、台帳の行 ID と対応する（PQO-017、PQO-018）。
- 読み取りの権限で、文書化した全クエリが成功し、書き込み系の API は `AccessDenied` になる（PQO-019、PQO-020）。
- `terraform plan` が、新規リソースの作成だけを示し、既存リソースの変更も破壊も含まない。ただしホストの user data を変える場合は、その差分を別に明示する（PQO-022、PQO-025）。
- 月の実測費用が、下の上限を超えない（PQO-023）。

## Constraints and assumptions

- 本番は `ap-northeast-1` の単一 EC2 ホストに、API、ワーカー、検証器、web、Caddy などのコンテナを同居させる構成である。ホストの user data を変えると、Terraform の設定（`user_data_replace_on_change = true`）により、ホストが置き換わる。
- 現在のホストの IAM ロールには、CloudWatch への書き込み権限がない。ワーカーのロールは、SQS の受信、`s3:PutObject`、それに付随する権限に限られ、その固定を Terraform のテスト（PFI-AG-006）が検査している。この仕様はワーカーのロールを広げない。
- 本番で動いているのは `prod` だけである。`dev` と `staging` は変数の上で許されるが、本番相当の環境は確認していない。注入テストは `Environment=probe` の値と、使い捨てのアラームで行う。
- dot について確認できているのは、第三者の記事に書かれた範囲に限る。各 dot はクラウド上の PC とブラウザを持つ。ChatGPT のプラグインと同じ接続を使い、権限は行為単位（例: 読み取りのみ）で絞れる。時刻・タイムゾーン・通知ルールを指定した定期実行ができる。サイトへのログインは、モデルが認証情報を見ないプライベートなフォームで行う。AWS への直接のコネクタ、MCP やカスタムコネクタへの対応、API、ポーリングの間隔、認証情報の失効時の挙動、監査ログは確認できていない。
- 設計時点で AWS の認証情報がなかったため、既存リソースの現状は Terraform と README の記述で確認した。AWS 上の実在は未確認である。
- 単価は設計時点の想定であり、`terraform apply` の前に AWS の料金ページで確認する。

## Cost

| 項目 | 想定 |
|---|---|
| 要求数 | 1日500件の終端要求 |
